# Risk Analysis — Newsletter Email Subscription

Created: 2026-09-19

## สรุปจำนวน Test Case แยกตาม Priority
P0: 1
P1: 3
P2: 5
P3: 2

## P0 — วิกฤต

### TC-001: สมัครรับข่าวสารสำเร็จด้วยอีเมลรูปแบบถูกต้องที่ยังไม่เคยสมัคร
เหตุผล: เป็น Happy Path หลักของฟีเจอร์ทั้งหมด — ถ้า Fail แปลว่าฟีเจอร์นี้ใช้งานไม่ได้เลยสำหรับผู้ใช้ส่วนใหญ่ ไม่มีทางเลี่ยงอื่น

## P1 — สำคัญ

### TC-002: กรอกอีเมลรูปแบบไม่ถูกต้อง (ไม่มี @)
เหตุผล: เป็น Business Rule หลัก (BR-001) ที่ป้องกันข้อมูลขยะเข้าระบบ — ถ้า Fail ระบบจะรับข้อมูลผิดรูปแบบเข้า subscriber ได้ กระทบคุณภาพข้อมูลโดยตรง แต่ผู้ใช้ยังสมัครสำเร็จด้วยอีเมลถูกต้องได้ตามปกติ (มีทางเลี่ยง)

### TC-004: สมัครซ้ำด้วยอีเมลเดิมทุกตัวอักษร (exact match)
เหตุผล: เป็น Business Rule หลัก (BR-002/REQ-F-003) ของฟีเจอร์ — ถ้า Fail ข้อมูล subscriber จะซ้ำซ้อนได้ กระทบคุณภาพข้อมูลที่ทีม Marketing จะใช้ต่อโดยตรง แต่ไม่ได้ทำให้ฟีเจอร์ใช้งานไม่ได้ทั้งหมด

### TC-005: สมัครซ้ำด้วยอีเมลเดิมแต่ตัวพิมพ์เล็ก-ใหญ่ต่างกัน
เหตุผล: ผูกกับ RISK-001 ระดับ High ที่ Requirement Review ระบุไว้ — ถ้า Fail (คือระบบยอมให้สมัครซ้ำได้จริงตามพฤติกรรมปัจจุบัน) จะกระทบคุณภาพข้อมูล subscriber และความน่าเชื่อถือของฟีเจอร์ในสายตาผู้ใช้ที่คาดหวัง behavior แบบ case-insensitive ตามปกติของอีเมล ให้ P1 ไม่ใช่ P0 เพราะไม่ได้ทำให้ฟีเจอร์ใช้งานไม่ได้และไม่กระทบความปลอดภัย/เงินโดยตรง เป็นปัญหาคุณภาพข้อมูลเป็นหลัก

## P2 — ปานกลาง

### TC-003: กรอกอีเมลรูปแบบไม่ถูกต้อง (มี @ แต่ไม่มีโดเมน)
เหตุผล: เป็นเคสเสริมของ TC-002 ที่ทดสอบ Business Rule เดียวกันด้วย input ต่างรูปแบบ — ความเสี่ยงซ้ำกับ TC-002 แต่โอกาสเกิด edge case แบบนี้ในการใช้งานจริงต่ำกว่า

### TC-006: กดปุ่ม "สมัครรับข่าวสาร" ซ้ำระหว่างระบบกำลังประมวลผล
เหตุผล: กระทบ UX และอาจทำให้เกิดข้อมูลซ้ำได้ในทางเทคนิค แต่เป็นเงื่อนไขที่ต้องอาศัยจังหวะเวลาเฉพาะ (กดซ้ำเร็วมาก) โอกาสเกิดในการใช้งานจริงไม่สูง และไม่ block การใช้งานหลัก

### TC-007: กดปุ่มสมัครโดยไม่กรอกอีเมลเลย (ช่องว่าง)
เหตุผล: เป็น edge case ของ Validation ที่ผู้ใช้พบเจอได้ไม่ยาก (เช่นกดปุ่มพลาดโดยไม่ได้กรอกอะไร) แต่ผลกระทบจำกัดแค่ UX ไม่ใช่ข้อมูลเสียหาย

### TC-010: ตรวจสอบว่า Footer widget แสดงผลและทำงานถูกต้องข้าม Browser หลัก
เหตุผล: Compatibility กระทบผู้ใช้บาง Browser เท่านั้น ไม่ block ฟีเจอร์โดยรวม และยังเป็นสมมติฐานชั่วคราว (รอ OQ-03) จึงยังไม่ควรยกเป็น P1

### TC-011: ระบบบันทึกอีเมลลง subscriber ล้มเหลวจากสาเหตุฝั่งระบบเอง
เหตุผล: เป็นสถานการณ์ที่พบไม่บ่อย (infra failure) แต่ถ้าเกิดขึ้นจริงและ UX แย่ (เช่น error message สื่อผิด หรือหน้าเว็บค้าง) จะกระทบความน่าเชื่อถือได้ — ให้ P2 เพราะความถี่ในการเกิดต่ำ แม้ผลกระทบเมื่อเกิดจะปานกลางถึงสูง

## P3 — เล็กน้อย

### TC-008: กรอกอีเมลที่มีช่องว่างนำหน้า/ตามหลัง
เหตุผล: edge case ที่พบยากมากในการใช้งานจริง (ผู้ใช้ทั่วไปไม่ค่อยพิมพ์ช่องว่างแถมในอีเมล) และแม้ Fail ก็ไม่ได้กระทบการทำงานหลักของระบบ

### TC-009: กรอกอีเมลที่ยาวผิดปกติ
เหตุผล: boundary case ที่แทบไม่เกิดในการใช้งานจริง เป็นการทดสอบเชิงป้องกันมากกว่าสถานการณ์ที่คาดว่าจะเจอจริง

## หมายเหตุ

- TC-005 และ TC-011 ยังอ้างอิงสมมติฐาน/Open Question ที่ยังไม่ปิดจบ (RISK-001 และข้อสังเกตใหม่ข้อ 4 ใน `02-e2e-flow.md` ตามลำดับ) — กำหนด Priority ตามความเสี่ยงที่คาดว่าน่าจะเป็นไปได้มากที่สุดไว้แล้วตามหลักการของ Skill นี้ ไม่ได้ปล่อยว่างรอคำตอบ หากภายหลังทีมยืนยันคำตอบที่ต่างจากสมมติฐาน อาจต้องทบทวน Priority ใหม่อีกครั้ง
- REQ-NF-003/REQ-NF-004 ที่ถูก Defer ไว้ตั้งแต่ Coverage Review ยังไม่มี Test Case ให้ประเมิน Priority ในรอบนี้ (ไม่มีแถวในชีต Test Case ให้กำหนดค่า)
