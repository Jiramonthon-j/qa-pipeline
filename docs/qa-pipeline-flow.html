QA Pipeline · ทดสอบจริงกับ Discount Code Application · 2026-09-16

แผนผัง QA Pipeline — 15 Skill

ลำดับการทำงานทั้งสายตั้งแต่รวบรวม Requirement จนถึงปิด Ticket ใน Redmine จริง แต่ละกล่องคือ 1 Skill พร้อมสิ่งที่ต้องป้อนเข้าไปและผลลัพธ์ที่ได้ ทุกขั้นตอนผ่านการรันจริงมาแล้วอย่างน้อย 1 รอบเต็ม

🤖 Claude ทำเองได้ทั้งหมด 🧑 ต้องมีคนอนุมัติ/เซ็นจริง 🔁 วนซ้ำได้จนกว่าจะผ่าน
A

วิเคราะห์ Requirement

เก็บข้อมูลต้นทาง → วางแผนทดสอบ → สกัดกฎ/Flow → ออกแบบ Test Case → ตรวจความครบถ้วน → จัดลำดับความเสี่ยง

  1. 00
    pre

    source-ingest

    Stage 00-pre🧑 ต้องรีวิว

    รวบรวมแหล่งข้อมูลต้นทางทั้งหมด (สเปก, เธรด Slack, บันทึกประชุม ฯลฯ) มาสรุปเป็นชุดเดียว พร้อมชี้จุดที่ข้อมูลขัดแย้งหรือยังไม่มีคำตอบให้เห็นตั้งแต่ต้นสาย

    ป้อนข้อมูล
    • ไฟล์ต้นฉบับดิบ: สเปกฟีเจอร์, ข้อความ/เธรด Slack, สรุปประชุม ฯลฯ
    ผลลัพธ์
    • 00-pre-source-ingest.md (+ .docx)
  2. 00

    test-plan

    Stage 00🧑 ต้องรีวิว

    วางแผนการทดสอบทั้งรอบ: ขอบเขต, Exit Criteria, Environment, ตารางเวลา, ความเสี่ยงของแผนเอง — เอกสารที่ Skill ถัดไปทั้งสายจะอ้างอิง Deadline จากตรงนี้

    ป้อนข้อมูล
    • 00-pre-source-ingest.md
    • Deadline / กำหนดการจริงจากผู้ใช้
    ผลลัพธ์
    • testplans/TP-…-.md (+ .docx)
  3. 01

    requirement-review

    Stage 01🤖

    สกัด Business Rule (BR-xxx) ทุกข้อและรวบรวม Open Question ที่ยังไม่มีคำตอบชัดเจนจาก Requirement ต้นทาง

    ป้อนข้อมูล
    • 00-pre-source-ingest.md
    • testplans/… (Deadline/ความเสี่ยง)
    ผลลัพธ์
    • 01-requirement-review.md
  4. 02

    e2e-flow-designer

    Stage 02🤖

    ออกแบบ User Flow ทุกเส้นทาง (FLOW-xxx) ทั้ง Main Flow และ Error State จาก Business Rule ที่สกัดไว้

    ป้อนข้อมูล
    • 01-requirement-review.md
    ผลลัพธ์
    • 02-e2e-flow.md
  5. 03

    test-case-generator

    Stage 03🤖

    สร้าง Test Case ทุกเคส (Positive / Negative / Edge Case) ครอบคลุมทุก BR และ Flow ลงใน Workbook กลางที่ทุก Skill ถัดไปจะอ่าน/เขียนต่อ

    ป้อนข้อมูล
    • 01 + 02
    • ค่า Env & Config จริง (URL, Browser, Device) จากผู้ใช้
    ผลลัพธ์
    • 03-test-case-workbook.xlsx (ชีต Test Case / Env & Config / Requirement Matrix)
  6. 04

    coverage-review

    Stage 04🤖

    ตรวจว่า Test Case ที่ออกแบบไว้ครอบคลุมทุก BR/Flow ครบไหม มีจุดตกหล่น/ซ้ำซ้อน/ขัดแย้งหรือไม่

    ป้อนข้อมูล
    • Workbook (03) เทียบกับ 01 + 02
    ผลลัพธ์
    • 04-coverage-review.md (+ แก้ Remarks ใน Workbook ถ้าจำเป็น)
  7. 05

    risk-analysis

    Stage 05🤖

    กำหนดลำดับความสำคัญ (Priority P0–P3) ให้ทุก Test Case ตามความเสี่ยงจริงของแต่ละเคส ใช้ตัดสิน Go/No-Go ในขั้นท้ายสาย

    ป้อนข้อมูล
    • Workbook (03)
    ผลลัพธ์
    • 05-risk-analysis.md (+ อัปเดตคอลัมน์ Priority ใน Workbook)
B

เตรียมข้อมูล & รันทดสอบจริง

แปลงเป็นข้อมูลทดสอบจริง → รัน Automation จริงบน Environment จริง → สรุปผล → ตรวจ Traceability

  1. 06

    test-data-generator

    Stage 06🤖

    แปลงคอลัมน์ Test Data ของทุกเคสให้เป็นข้อมูลที่ใช้ทดสอบได้ทันที (โค้ดส่วนลด, บัญชีทดสอบ, วันหมดอายุที่คำนวณสัมพัทธ์กับวันรันจริง ฯลฯ)

    ป้อนข้อมูล
    • Workbook (03)
    ผลลัพธ์
    • 06-test-data.md
  2. 06a

    qa-automation-script

    Stage 06a🤖

    เขียน + รัน Playwright script จริงทีละ Test Case บน Environment ที่ระบุไว้ จับภาพหน้าจอพร้อมวงไฮไลท์จุดที่ตรวจ แล้วเขียนผล Pass/Fail/Blocked กลับ Workbook

    ป้อนข้อมูล
    • Workbook (03) + 06-test-data.md
    • Environment ที่รันได้จริง (URL ใช้งานได้จริง)
    • Browser ตามที่ Env & Config กำหนด
    ผลลัพธ์
    • automation/*.py, screenshots/<Browser>/*.png
    • อัปเดต Status / Actual Result / Photo ใน Workbook
  3. 07

    result-analysis

    Stage 07🤖

    สรุปผลรวมทุกเคส วิเคราะห์ Root Cause ของ Fail/Blocked แยกตามหมวด (Functional Bug / Script Error / Open Question ที่ยังไม่ปิด)

    ป้อนข้อมูล
    • Workbook (03) หลัง 06a รันเสร็จ
    ผลลัพธ์
    • 07-result-analysis.docx
    • 07-photo-evidence.docx
  4. RTM

    qa-reconcile

    Stage RTM🤖

    คำนวณ Requirement Traceability Matrix ใหม่สดจากข้อมูลจริงเสมอ (ไม่เชื่อชีตเดิม) หา Orphan Requirement/Test Case ที่ไม่มีอะไรโยงถึงกัน

    ป้อนข้อมูล
    • 01 + 02 + Workbook (03) — อ่านสดทุกครั้ง
    ผลลัพธ์
    • RTM-traceability-matrix.xlsx
C

สรุปผล & ตัดสินใจ

รวมทุกอย่างเป็นรายงานเดียวเสนอผู้อนุมัติ

  1. 08

    qa-report-generator

    Stage 08🧑 ต้องเซ็นจริง

    รวมผลจาก Result Analysis + RTM + Workbook ทั้งหมดเป็นรายงานฉบับเดียว สรุป Go / Conditional Go / No-Go พร้อม Known Issues และช่องเซ็นอนุมัติ — ต้องเช็คว่า Stage 07 ไม่ Partial และ RTM Complete ก่อนเสมอ

    ป้อนข้อมูล
    • 07 + RTM + Workbook (03) + Deadline
    ผลลัพธ์
    • 08-qa-report.docx (ช่องเซ็น QA Lead / PM เว้นว่างไว้ให้เซ็นจริงเสมอ)
จุดตัดสินใจ: อ่านผลสรุปจาก 08-qa-report.docx
✅ ไม่มีบั๊กเหลือ → ปิด Feature ได้เลย จบ Pipeline
⚠️ มี Test Case Fail ค้าง → ไป Phase D เพื่อเปิด/ติดตาม Ticket แก้บั๊ก
D

ปิดบั๊ก (วนซ้ำจนกว่าจะ Pass ครบ)

เปิด Ticket → รอ Dev แก้ → Retest จริง → ปิด/คอมเมนต์ Ticket จริง — วนกลับได้เรื่อยๆ จนกว่า Fail จะหมด

  1. 09

    redmine-logging

    Stage 09🤖

    เปิด Ticket ใน Redmine จริงให้ทุกเคสที่ Fail พร้อมแนบภาพหลักฐาน แล้วส่งอีเมลแจ้ง Dev

    ป้อนข้อมูล
    • Workbook (เคสที่ Fail)
    • อีเมล Dev ที่จะแจ้ง (ไม่ใช่ข้อมูลลับ)
    ผลลัพธ์
    • Ticket จริงใน Redmine, 09-redmine-log.md
    • อัปเดตคอลัมน์ Issue link ใน Workbook + ส่งอีเมลแจ้ง Dev
    🔐 ต้องถาม Redmine URL / API Key และ SMTP credentials สดใหม่ทุกครั้งที่รัน — ไม่เก็บ/แคชไว้ในไฟล์ใดๆ ทั้งสิ้น
  2. 10

    qa-retest

    Stage 10🤖

    หลัง Dev แจ้งว่าแก้แล้ว กลับไปรัน Automation ซ้ำเฉพาะ Test Case ที่มี Issue link เทียบผลใหม่กับ Expected Result

    ป้อนข้อมูล
    • Workbook (เคสที่มี Issue link)
    • Environment ที่ Dev แก้ไขแล้ว
    ผลลัพธ์
    • 10-tc-issue-map.json, 10-retest-run-result.json
    • อัปเดตผล Retest ใน Workbook
    🔐 เช็คสถานะ Ticket ผ่าน Redmine URL / API Key สดใหม่เช่นกัน
  3. 10a

    qa-retest-closure

    Stage 10a🤖

    เอาผล Retest ไปจัดการ Ticket จริงใน Redmine: Pass → คอมเมนต์ผล + แนบภาพ + ปิด Ticket, Fail → คอมเมนต์ผลอย่างเดียวแล้วส่งอีเมลแจ้ง Dev ต่อ

    ป้อนข้อมูล
    • ผล Retest จาก Stage 10
    • ชื่อ Status ที่จะใช้ปิด (เช่น "จบ")
    ผลลัพธ์
    • ปิด/คอมเมนต์ Ticket จริงใน Redmine
    • 10a-closure-result.json
    🔐 Redmine URL / API Key สดใหม่ทุกครั้งเหมือน Stage 09/10
🔁 ถ้ายังมี Test Case สถานะ Fail เหลืออยู่ → วนกลับไปทำ Stage 09 (เปิด/อัปเดต Ticket) → 10 (Retest) → 10a (ปิด Ticket) ใหม่ ซ้ำไปเรื่อยๆ จนกว่า Fail จะหมด

✅ เมื่อ Pass ครบทุกเคสและปิด Ticket หมดแล้ว → จบ Pipeline

✅ Feature หนึ่งจะ "ปิดสมบูรณ์" ได้ก็ต่อเมื่อ

Stage 01–10a ทั้งหมด = Complete, ไม่มี Test Case สถานะ Fail ค้าง, Stage 00-pre และ 00 ได้รับการอนุมัติจริงจากคน (ไม่ใช่ AI), และช่องเซ็น QA Lead / PM ใน 08-qa-report.docx ถูกเซ็นจริงแล้ว

🔒 กฎความปลอดภัยที่ใช้ตลอดทั้งสาย (Stage 09 / 10 / 10a)
  • Redmine URL และ API Key ต้องถูกถามใหม่ทุกครั้งที่เรียก Skill — ห้ามแคช/บันทึกไว้ในไฟล์ใดๆ ตั้งค่าผ่าน Environment Variable เท่านั้น (ห้ามส่งผ่าน argument ตรงๆ)
  • กฎเดียวกันนี้ใช้กับ SMTP credentials สำหรับส่งอีเมลแจ้ง Dev
  • อีเมล Dev ไม่ถือเป็นข้อมูลลับ ใช้ซ้ำได้ตามปกติ
