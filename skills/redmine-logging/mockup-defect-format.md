# Mockup — Format ของ Defect Ticket ที่จะเปิดใน Redmine

ก่อนเริ่มออกแบบ มีจุดหนึ่งที่ต้องเช็คกับคุณก่อน: **Redmine มี text formatting 2 แบบ** คือ Textile (ค่าเริ่มต้นของ Redmine ส่วนใหญ่) กับ Markdown (บาง instance ตั้งค่าเปลี่ยนไปใช้) — วิธีทำตัวหนา/หัวข้อ/list เขียนไม่เหมือนกัน (Textile ใช้ `*text*` ตัวหนา, Markdown ใช้ `**text**`) ถ้าใช้ syntax ผิดฝั่ง Ticket ที่เปิดจะมีเครื่องหมายดอกจันเพี้ยนๆ ปนอยู่ในเนื้อหาแทนที่จะ render สวยๆ — ด้านล่างนี้ผมร่างเป็น 2 เวอร์ชันไว้ให้ดูเทียบกัน (Mockup นี้ใช้ syntax แบบ **Markdown**) บอกผมด้วยว่า Redmine ของคุณใช้แบบไหน

---

## 1) Subject (หัวเรื่อง Ticket)

```
[<Priority>] <Test Case ID>: <Test Scenario>
```

**ตัวอย่างจริงจาก TC-017:**
```
[P2] TC-017: ลบโค้ด A แล้วใส่โค้ด B ต่อทันที — กรณีสมมติฐานว่านับสิทธิ์โค้ด A ทันทีตอนกด "ใช้โค้ด" ครั้งแรก
```

## 2) Description (เนื้อหา Ticket) — โครงสร้างที่เสนอ

| ลำดับ | Field | มาจากไหน | ทำไมต้องมี |
|---|---|---|---|
| 1 | Summary บรรทัดเดียว | Test Scenario | ให้คนอ่านเร็วรู้ว่าเจออะไร ก่อนลงรายละเอียด |
| 2 | Priority / Test Case ID / Module | Workbook | Traceability กลับไปหา Workbook ได้ทันที |
| 3 | Environment | Env & Config sheet | บั๊กบางตัวเกิดเฉพาะ Browser/Device |
| 4 | Steps to Reproduce | Test Step (แปลงเป็น numbered list) | ให้ Dev ทำซ้ำบั๊กได้เอง |
| 5 | Test Data ที่ใช้ | Test Data | ค่าจริงที่ใช้ตอนทดสอบ (ไม่ใช่แค่คำอธิบาย) |
| 6 | Expected Result | Expected Result | คาดว่าอะไรควรเกิดขึ้น |
| 7 | Actual Result | Actual Result | จริงๆ เกิดอะไรขึ้น |
| 8 | Root Cause (ถ้ามี) | 07-result-analysis.docx | ถ้า QA วิเคราะห์เจอสาเหตุแล้วให้ Dev ไม่ต้องขุดใหม่ |
| 9 | หลักฐาน/Screenshot | screenshots/ | อ้าง path รูปให้เปิดดูเอง |
| 10 | อ้างอิง | Workbook + เอกสารอื่น | ให้ตามไปดูบริบทเต็มได้ |

**คำถาม**: อยากได้ครบทั้ง 10 field นี้ไหม หรือมีอยากตัด/เพิ่ม/เรียงลำดับใหม่?

## 3) ตัวอย่างเต็ม — เปิดจากข้อมูลจริงของ TC-017

**Subject:**
```
[P2] TC-017: ลบโค้ด A แล้วใส่โค้ด B ต่อทันที — กรณีสมมติฐานว่านับสิทธิ์โค้ด A ทันทีตอนกด "ใช้โค้ด" ครั้งแรก
```

**Description:**

> การนับสิทธิ์การใช้โค้ดส่วนลดผิดจากที่คาดไว้ เมื่อผู้ใช้ลบโค้ด A แล้วใส่โค้ด B ต่อทันทีโดยไม่เคย checkout สำเร็จด้วยโค้ด A เลย
>
> **Priority:** P2
>
> **Test Case ID:** TC-017
>
> **Module:** ตะกร้าสินค้า - โค้ดส่วนลด
>
> **Environment:** Staging (mock) — ทดสอบผ่าน Chromium
>
> **Steps to Reproduce:**
> 1. กดปุ่ม "ลบโค้ด" สำหรับโค้ด A (ONETIME10, usage_limit_per_user=1, ใช้งานอยู่ในออเดอร์นี้แล้ว)
> 2. กรอกโค้ด B (FLAT100)
> 3. กดปุ่ม "ใช้โค้ด"
> 4. ตรวจสอบสิทธิ์การใช้โค้ด A ที่เหลือของผู้ใช้คนนี้ในภายหลัง
>
> **Test Data:** code_a=ONETIME10 (usage_limit=1), code_b=FLAT100, cart_total=1000
>
> **Expected Result:** โค้ด B ถูกใช้สำเร็จ และสิทธิ์การใช้โค้ด A ของผู้ใช้ถูกนับไปแล้ว 1 ครั้ง แม้จะลบออกและไม่เคย checkout สำเร็จด้วยโค้ด A เลย (ตามสมมติฐาน A)
>
> **Actual Result:** โค้ด B ใช้สำเร็จ แต่สิทธิ์การใช้โค้ด A วัดค่าได้ `usage_confirmed=0` — ระบบเลือกนับเฉพาะตอน checkout สำเร็จเท่านั้น (สมมติฐาน B) ไม่ตรงกับที่เคสนี้คาดหวัง (สมมติฐาน A)
>
> **Root Cause:** การนับสิทธิ์การใช้โค้ดเมื่อลบแล้วใส่ใหม่ยังไม่มีกฎที่ยืนยันจากทีม (BR-008 / Open Question ข้อ 4 ใน 01-requirement-review.md) — ต้องให้ทีมยืนยันแนวทางที่ถูกต้องก่อนแก้โค้ด ไม่ใช่บั๊กที่เดาสาเหตุได้ตรงๆ
>
> **หลักฐาน:** screenshots/Chromium/TC-017.png (ดูรูปเต็มใน 07-photo-evidence.docx หน้า TC-017)
>
> **อ้างอิง:** 03-test-case-workbook.xlsx (Test Case ID: TC-017)

## จุดที่อยากให้ยืนยันก่อนใส่ลง Skill จริง

1. **Textile หรือ Markdown?** (ดูหัวข้อบนสุด)
2. **10 field ด้านบนโอเคไหม** หรืออยากตัด/เพิ่ม (เช่น อยากเพิ่ม field "Severity" แยกจาก "Priority", หรือ field "Assignee suggestion")
3. **Summary บรรทัดเดียว** (บรรทัดแรกสุดของ Description ก่อนตาราง field) — อยากให้เขียนเองทุกครั้ง หรือให้ AI สรุปจาก Actual Result ให้อัตโนมัติแบบนี้?
4. **หัวข้อ "Root Cause"** — ใส่เฉพาะตอนที่ Skill 07 วิเคราะห์ไว้แล้วเท่านั้น ถ้าไม่มีให้ตัดหัวข้อนี้ทิ้งไปเลย หรือใส่ไว้เป็น "ยังไม่วิเคราะห์" เสมอ?
