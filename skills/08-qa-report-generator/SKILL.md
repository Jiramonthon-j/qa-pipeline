# qa-report-generator

Skill นี้เป็น**ขั้นตอนที่ 8 ที่บังคับ** ของ QA Pipeline หน้าที่คือรวบรวมทุกอย่างที่ผ่านมาตลอดทั้งสาย (Requirement, Coverage, Risk, ผลทดสอบจริง, Traceability) ให้เป็นรายงานฉบับเดียวที่อ่านจบแล้วตัดสินใจได้ทันทีว่า Feature นี้พร้อมปล่อย (Go) หรือยัง (No-Go) — เป็นรายงานที่ตั้งใจให้ส่งต่อ PM/ผู้บริหารเพื่อขออนุมัติ ไม่ใช่รายงานเชิงเทคนิคสำหรับทีม QA เอง (รายงานเชิงเทคนิคคือ `07-result-analysis.docx` ที่มีอยู่แล้ว)

**สำคัญ**: Skill นี้ต้องการ environment ที่รันโค้ด Python ได้จริง (ใช้ `python-docx` สร้างไฟล์ Word จริง) เหมือน Skill 06a/07 — ถ้า environment รันโค้ดไม่ได้ ให้เตรียมเนื้อหาเป็น Markdown ไว้ก่อนแล้วแจ้งผู้ใช้ว่าต้องไปแปลงเป็น Word เอง

## ขั้นตอนที่ 1 — ระบุ Feature และตรวจสอบขั้นตอนก่อนหน้า

1. หาโฟลเดอร์ Project Root และโฟลเดอร์ Feature เหมือน Skill อื่นๆ ในสาย
2. อ่านไฟล์ `_pipeline-manifest.md`
3. **เช็ค Gate**: ต้องรันต่อจาก `result-analysis` (07) **และ** `qa-reconcile` (RTM) เสมอ — เช็คทั้งสอง Stage ตามลำดับนี้ (ถ้าไม่มี manifest เลยก็ถือว่าทั้งคู่ยังไม่เสร็จเช่นกัน ต้องถามผู้ใช้เสมอ ห้ามสรุปเอาเอง) **ห้ามเช็คแค่ RTM อย่างเดียวแล้วข้ามการเช็ค 07 ไปเด็ดขาด** เพราะ RTM Complete บอกแค่ว่า Traceability ตรวจครบ ไม่ได้แปลว่าผลทดสอบที่ RTM เอาไปอ้างอิงนั้นครบสมบูรณ์ด้วย — ทั้งสอง Stage เป็นเงื่อนไขที่ตรวจแยกอิสระจากกัน คนละสาเหตุ คนละความเสี่ยง จึงต้องเช็คทั้งคู่:

   **3a. ตรวจสถานะ Stage `07 result-analysis`**:
   - **ถ้า `Complete` แบบเต็ม (ไม่มีคำว่า "Partial" ต่อท้ายสถานะ)**: ผ่าน ไปเช็ค 3b ต่อ
   - **ถ้าสถานะมีคำว่า "Partial" ต่อท้าย (เช่น `Complete (Partial — ดู Notes)`)**: หมายความว่า Root Cause/สรุปผลใน 07 เองถูกสร้างจากผลทดสอบที่ยังไม่ครบ (เช่น ทดสอบไม่ครบทุก Browser/Device ตามที่ Env & Config กำหนด) — หยุดและถามผู้ใช้ว่า (a) ต้องการกลับไปทำ `qa-automation-script` (06a)/`result-analysis` (07) ให้ครบสมบูรณ์ก่อนไหม (แนะนำ) หรือ (b) ต้องการสรุปรายงานโดยอิงข้อมูล Partial นี้ไปก่อน — ถ้าเลือก (b) ต้องระบุในรายงานอย่างชัดเจนว่าอิงผลทดสอบที่ยังไม่ครบ Environment/Browser ตามที่กำหนด และ **Go/No-Go ที่สรุปออกมาต้องถือเป็นแบบชั่วคราว (Provisional) เช่นเดียวกับกรณี RTM ไม่ครบด้านล่าง**
   - **ถ้ายังไม่ `Complete` เลย (Not Started/In Progress/Pending Review)**: หยุดและถามผู้ใช้ว่าต้องการไปรัน `result-analysis` ให้เสร็จก่อนไหม (แนะนำอย่างยิ่ง เพราะขั้นตอนที่ 2.3 ของ Skill นี้ต้องใช้ Root Cause ที่ 07 จัดกลุ่มไว้แล้วเป็นอินพุตหลัก การข้าม 07 ไปเลยจะทำให้ต้องมานั่งวิเคราะห์ข้อมูลดิบเองใหม่หมด) หรือจะข้ามไปสรุปเองจากข้อมูลดิบ — ถ้าเลือกข้ามให้ระบุ Provisional เช่นเดียวกัน

   **3b. ตรวจสถานะ Stage `RTM qa-reconcile`**:
   - **ถ้า `Complete`**: ไปต่อขั้นตอนที่ 2
   - **ถ้ายังไม่ `Complete`**: หยุดและถามผู้ใช้ว่า (a) ต้องการไปรัน `qa-reconcile` ให้เสร็จก่อนไหม (แนะนำ) หรือ (b) ต้องการสรุปรายงานเท่าที่มีอยู่ตอนนี้ไปก่อน — ถ้าเลือก (b) ต้องระบุในรายงานอย่างชัดเจนว่า RTM ยังไม่เสร็จ และ **Go/No-Go ที่สรุปออกมาต้องถือเป็นแบบชั่วคราว (Provisional) เท่านั้น** เพราะยังไม่ผ่านการตรวจ Traceability เต็มรูปแบบ

   **หมายเหตุ**: ถ้าทั้ง 3a และ 3b ผู้ใช้เลือกแบบ (b) พร้อมกัน (หรือ Gate ข้อใดข้อหนึ่งไม่ผ่านแต่อีกข้อผ่าน) ให้รวมเหตุผล Provisional ทุกข้อที่เกี่ยวข้องไว้ในรายงานให้ครบ ไม่ใช่เขียนแค่เหตุผลเดียวแล้วละเลยอีกข้อ (ดูขั้นตอนที่ 4.2)

## ขั้นตอนที่ 2 — รวบรวมข้อมูลจากทุกขั้นตอนก่อนหน้า

1. `01-requirement-review.md` — Deadline (จาก Header), Feature Overview
2. Test Case Workbook ชีต "Test Case" **อ่านสดจากไฟล์จริง** ด้วย `python3 scripts/read_workbook.py read-cases --path "<path>"` — ห้ามเชื่อตัวเลขที่เคยสรุปไว้ใน `07-result-analysis.docx` เพราะอาจมีการรัน `qa-automation-script` เพิ่มเติมหลังจากนั้น
3. `07-result-analysis.docx` (หรือข้อมูลดิบที่ใช้สร้างมัน) — สำหรับ Root Cause ที่จัดกลุ่มไว้แล้ว
4. `RTM-traceability-matrix.xlsx` ชีต "Findings" — Accepted Gap และ Assumption ที่ยังค้างอยู่
5. วันที่ปัจจุบัน (วันที่สร้างรายงานนี้) เทียบกับ Deadline จากข้อ 1

## ขั้นตอนที่ 3 — ตัดสินใจ Go / No-Go

ใช้กฎการตัดสินใจนี้เสมอ (เรียงลำดับตรวจตามนี้ — เจอเงื่อนไขไหนก่อนให้หยุดที่เงื่อนไขนั้น อย่าตรวจข้ามไปเงื่อนไขถัดไป):

1. **No-Go — ยังทดสอบไม่ครบ**: ถ้ามี Test Case สถานะ `not start` เหลืออยู่ (ไม่ว่า Priority ใด) → **No-Go** เหตุผล "ยังทดสอบไม่ครบทุกเคส"
2. **No-Go — บั๊กจริงระดับ P0 ยังไม่ปิด**: ถ้ามี Test Case Priority `P0` ที่ Status เป็น `Fail` (บั๊กจริง ไม่ใช่ Blocked) → **No-Go** เหตุผล "พบบั๊กจริงระดับวิกฤต (P0) ที่ยังไม่ได้แก้"
3. **Conditional Go — บั๊กจริงระดับ P1 ยังไม่ปิดแต่มีทางเลี่ยง**: ถ้าไม่มี P0 ค้าง แต่มี Test Case Priority `P1` ที่ Status เป็น `Fail` → **Conditional Go** เหตุผล "มีปัญหาสำคัญ (P1) ที่ยังไม่แก้ แต่ไม่ใช่เส้นทางหลัก — ต้องมี Known Issue ระบุไว้ชัดเจนและได้รับการยอมรับจากผู้อนุมัติก่อนปล่อย"
4. **Go**: ถ้า P0/P1 ทั้งหมด Pass หรือไม่มี Fail ค้าง (มีแค่ P2/P3 ที่ยัง Fail หรือไม่มีเลย) → **Go**
5. **Blocked ไม่นับเป็นเหตุผล No-Go โดยตรง** (เพราะไม่ใช่บั๊กจริง) แต่ต้องระบุไว้ในรายงานเสมอว่ามีกี่เคสที่ `Blocked` และแนะนำให้แก้ปัญหา Environment/Script แล้วรันซ้ำก่อนปิด Feature จริง เนื่องจากเคสเหล่านั้นยังไม่มีผลสรุปที่แท้จริง
6. **Deadline overlay**: ไม่ว่าผลข้อ 1–4 จะเป็นอะไรก็ตาม ถ้าวันที่ปัจจุบัน**เลย Deadline ไปแล้ว** ให้เพิ่มคำเตือนเด่นชัดในรายงานเสมอว่า "เลย Deadline ที่กำหนดไว้แล้ว (Deadline: ..., วันนี้: ...)" โดยไม่เปลี่ยนผล Go/No-Go ที่คำนวณได้จากข้อ 1–4 (Deadline overlay เป็นข้อมูลประกอบการตัดสินใจของผู้อนุมัติ ไม่ใช่กฎที่ override ผลทดสอบ) — เมื่อเตรียมข้อมูลให้สคริปต์ `build_final_report.py` **ต้องส่งค่า `deadline_passed: true` เสมอเมื่อเลย Deadline แล้ว** (ไม่ใช่แค่เขียนคำว่า "เลย Deadline" ไว้ในข้อความ `days_vs_deadline` เฉยๆ) เพื่อให้สคริปต์แสดงคำเตือนเป็นตัวหนา/สีแดงจริงในไฟล์ Word ที่สร้างออกมา ไม่ใช่แค่ข้อความปกติที่กลืนไปกับเนื้อหาอื่น

**เหตุผลที่ต้องมีลำดับตรวจชัดเจนแบบนี้**: ถ้าไม่ตรวจ "ยังทดสอบไม่ครบ" เป็นเงื่อนไขแรกก่อนเสมอ อาจเกิดกรณีที่ทดสอบไปแค่ 3 จาก 17 เคสแล้วทั้ง 3 เคสนั้นผ่านหมด ทำให้สรุปผิดว่า "Go" ทั้งที่ยังไม่ได้ทดสอบอีก 14 เคสเลย

## ขั้นตอนที่ 4 — สร้างรายงานฉบับสุดท้าย (`08-qa-report.docx`)

ใช้สคริปต์ที่ bundle มาด้วย (`scripts/build_final_report.py`) สร้างไฟล์ Word ตามโครงสร้างนี้เสมอ:

1. **หน้าปก/หัวรายงาน**: ชื่อ Feature, วันที่ออกรายงาน, Deadline, Environment ที่ทดสอบ
2. **ผลสรุป Go/No-Go**: ใส่ไว้เด่นชัดที่สุดในหน้าแรก (ตัวใหญ่/สี) พร้อมเหตุผลจากขั้นตอนที่ 3 — ถ้าเป็น Provisional (RTM ยังไม่เสร็จ และ/หรือ Stage 07 result-analysis ยังเป็น Partial ตามข้อ 3a/3b ของขั้นตอนที่ 1) ต้องระบุคำว่า "ชั่วคราว (Provisional)" กำกับไว้ชัดเจน **พร้อมระบุสาเหตุให้ครบทุกข้อที่เกี่ยวข้อง** (กรณีเข้าเงื่อนไข Provisional จากทั้ง 07 และ RTM พร้อมกัน ห้ามเขียนแค่สาเหตุเดียว)
3. **Test Coverage**: กี่ % ของ Test Case ที่ทดสอบแล้ว, ตาราง Pass/Fail/Blocked/Rejected แยกตาม Priority
4. **Known Issues / ความเสี่ยงที่ยังค้างอยู่**: รวมทั้ง (ก) Test Case P2/P3 ที่ยัง Fail, (ข) Test Case ที่ยัง Blocked, (ค) Accepted Gap จาก RTM Findings, (ง) Business Rule ที่ยังมี Assumption ค้าง — แต่ละข้อระบุ Priority/ความเสี่ยง และสิ่งที่แนะนำให้ทำต่อ (ตารางนี้ `build_final_report.py` กำหนดความกว้างคอลัมน์ไว้ตายตัวแล้ว — ยืนยันผ่าน Mockup — ห้ามแก้ให้กลับไปหารความกว้างเท่ากันทั้ง 5 คอลัมน์ เพราะจะทำให้คอลัมน์รายละเอียด/คำแนะนำแคบเกินไปจนข้อความแตกเป็นบรรทัดสั้นๆ ทีละ 1-2 คำ อ่านยาก)
5. **Environment/เวอร์ชันที่ทดสอบ**: Browser/Device ที่ทดสอบจริง (จาก Env & Config), ระบุด้วยว่าครบตามที่กำหนดไว้หรือยัง (ถ้า `qa-automation-script` ยัง In Progress เพราะ Browser ไม่ครบ ต้องระบุตรงนี้)
6. **วันที่เสร็จจริงเทียบ Deadline**: ระบุตัวเลขจำนวนวันที่เหลือ/เกิน Deadline ชัดเจน
7. **Next Steps**: รายการสิ่งที่ต้องทำก่อนปล่อยจริง (ถ้า No-Go/Conditional Go) หรือขั้นตอนถัดไปในสาย pipeline (ถ้า Go — แนะนำ `redmine-logging` (09) สำหรับบั๊กที่ยังไม่ได้เปิด Ticket, ถ้าไม่มีบั๊กเหลือเลยให้แนะนำปิด Feature ได้)
8. **ช่องเซ็นอนุมัติ**: ตารางช่องเซ็นชื่อ (Role, ชื่อ, ลายเซ็น, วันที่) อย่างน้อย 2 แถว: QA Lead และ PM/Product Owner — เว้นว่างไว้ให้เซ็นจริง ไม่ใส่ชื่อคนแทน

## ขั้นตอนที่ 5 — อัปเดต Manifest และรายงานสรุป

1. อัปเดต `_pipeline-manifest.md`: ตั้งค่า Stage `08 qa-report-generator` เป็น `Complete` เมื่อสร้างรายงานเสร็จ (Complete หมายถึง Skill นี้สรุปรายงานเสร็จแล้ว ไม่ได้แปลว่าผล Go/No-Go เป็น Go เสมอไป — No-Go ก็ถือว่า Skill ทำงานเสร็จสมบูรณ์เช่นกัน)
2. แจ้งผู้ใช้ผลสรุป Go/No-Go พร้อมเหตุผลหลัก แล้วแนะนำขั้นตอนถัดไปตามผล (ไปต่อ `redmine-logging` (09) ถ้ามีบั๊กเหลือ, หรือปิด Feature ได้ถ้าไม่มีบั๊กเหลือและ Go)

## ข้อควรระวัง

- **ห้ามข้ามการตรวจ "ยังทดสอบไม่ครบ" เป็นเงื่อนไขแรกเด็ดขาด** (ดูเหตุผลท้ายขั้นตอนที่ 3)
- Deadline overlay เป็นแค่คำเตือนประกอบ ห้ามใช้เปลี่ยนผล Go/No-Go ที่คำนวณจากเงื่อนไข P0/P1
- Skill นี้**ห้ามแก้ไข Test Case Workbook เด็ดขาด** เป็น Skill อ่านและสรุปผลเท่านั้น
- ถ้า Gate ข้อใดข้อหนึ่งไม่ผ่าน (RTM ยังไม่ Complete และ/หรือ Stage 07 ยังเป็น Partial) และผู้ใช้เลือกสรุปแบบ Provisional ต้องย้ำคำว่า Provisional ในทุกจุดที่พูดถึง Go/No-Go ในรายงาน ไม่ใช่แค่ที่เดียว และต้องระบุสาเหตุ Provisional ให้ครบทุกข้อที่เกี่ยวข้อง (อย่าเขียนแค่สาเหตุเดียวถ้าจริงๆ เข้าเงื่อนไขมากกว่า 1 ข้อ)
- **ห้ามเช็ค Gate แค่ RTM อย่างเดียว**: RTM Complete ไม่ได้แปลว่าผลทดสอบที่ใช้อ้างอิงครบสมบูรณ์ด้วย — ต้องเช็ค Stage 07 (ข้อ 3a) แยกต่างหากเสมอ ก่อนเช็ค RTM (ข้อ 3b)
