# result-analysis

Skill นี้เป็น**ขั้นตอนที่ 7 ที่บังคับ** ของ QA Pipeline หน้าที่คือนำผลการทดสอบจริงที่ `qa-automation-script` (06a) เขียนกลับเข้า Test Case Workbook แล้ว มาวิเคราะห์และสรุปเป็นรายงาน 2 ไฟล์: (1) รายงานสรุปผลภาพรวม และ (2) ไฟล์ Photo Evidence ที่รวมหลักฐานภาพของทุก Test Case ไว้ในที่เดียว เพื่อให้อ่าน/ส่งต่อได้ง่ายกว่าเปิดดู Workbook + โฟลเดอร์ภาพแยกกัน

**สำคัญ**: Skill นี้ต้องการ environment ที่รันโค้ด Python ได้จริง (ใช้ไลบรารี `python-docx` สร้างไฟล์ Word จริง) เหมือนกับ Skill 06a — ถ้า environment ที่ใช้งานอยู่รันโค้ดไม่ได้ ให้เตรียมเนื้อหารายงานเป็น Markdown ไว้ก่อนแล้วแจ้งผู้ใช้ว่าต้องไปแปลงเป็น Word ในเครื่อง/environment ที่มี Python ติดตั้งอยู่

## ขั้นตอนที่ 1 — ระบุ Feature และตรวจสอบขั้นตอนก่อนหน้า

1. หาโฟลเดอร์ Project Root และโฟลเดอร์ Feature เหมือน Skill อื่นๆ ในสาย
2. อ่านไฟล์ `_pipeline-manifest.md`
3. **เช็ค Gate**: ต้องรันต่อจาก `qa-automation-script` (06a) เสมอ — ตรวจสอบสถานะ Stage `06a qa-automation-script` (ถ้าไม่มี manifest เลยก็ถือว่ายังไม่เสร็จเช่นกัน ต้องถามผู้ใช้เสมอ ห้ามสรุปเอาเอง):
   - **ถ้า `Complete`**: ไปต่อขั้นตอนที่ 2 ตามปกติ
   - **ถ้าเป็น `In Progress`** (เช่น รันอัตโนมัติแล้วแต่ยังไม่ครบทุก Browser ที่ Env & Config กำหนด): หยุดและถามผู้ใช้ว่า (a) ต้องการไปรัน `qa-automation-script` ให้ครบก่อนไหม (แนะนำ) หรือ (b) ต้องการวิเคราะห์ผลเท่าที่มีอยู่ตอนนี้ไปก่อน (partial) — ถ้าเลือก (b) ให้บันทึกไว้ในรายงานอย่างชัดเจนว่าเป็นการวิเคราะห์แบบ partial ยังไม่ครบทุก Environment
   - **ถ้ายังไม่เริ่มเลยหรือไม่มี manifest**: หยุดและถามผู้ใช้ว่า (a) ต้องการไปรัน `qa-automation-script` ให้เสร็จก่อนไหม (แนะนำ) หรือ (b) ต้องการใช้ Skill นี้แบบ standalone — ถ้าเลือก (b) ให้ขอ Test Case Workbook ที่มีผลทดสอบกรอกไว้แล้ว และโฟลเดอร์ `screenshots/` มาจากผู้ใช้โดยตรง

## ขั้นตอนที่ 2 — อ่านข้อมูลผลทดสอบทั้งหมด

1. อ่าน Test Case Workbook **ฉบับล่าสุดจริงๆ** ด้วย `python3 scripts/read_workbook.py read-cases --path "<path>"` (ห้ามเชื่อความจำเก่า — Workbook อาจถูกแก้ไขเพิ่มเติมหลัง 06a รันจบ)
2. อ่านชีต "Env & Config" (Browser/Device ที่ต้องเทส, Environment) และ "Priority & Risk Matrix" (นิยาม P0–P3) เพื่อใช้ตีความผลลัพธ์
3. อ่านโฟลเดอร์ `screenshots/<Browser>/` ทั้งหมด — นี่คือแหล่งภาพที่แท้จริง (มีครบทั้ง Pass/Fail/Blocked ไม่ใช่แค่ Fail แบบคอลัมน์ Test Photo ใน Workbook)

## ขั้นตอนที่ 3 — วิเคราะห์และจัดกลุ่มผล

1. **Test Coverage ที่แท้จริง**: คำนวณ % ของ Test Case ที่ถูกรันจริงแล้ว (Status ≠ `not start`) เทียบกับจำนวน Test Case ทั้งหมด — Test Case ที่ยัง `not start` ต้องถูกระบุแยกไว้ชัดเจนว่า "ยังไม่ได้ทดสอบ" ไม่ใช่ถูกนับปนกับ Pass/Fail
2. **จัดกลุ่มตาม Status × Priority**: ตารางไขว้ Pass/Fail/Blocked/Rejected/not start กับ P0–P3 เพื่อให้เห็นภาพว่าปัญหาที่ยังค้างอยู่กระทบ Priority ระดับไหนบ้าง (ข้อมูลนี้ Skill 08 จะใช้ต่อสำหรับตัดสิน Go/No-Go)
3. **จัดกลุ่ม Root Cause ของทุกเคสที่ Fail/Blocked**: อ่านคอลัมน์ `Actual Result` และ `Remarks` ของแต่ละเคส แล้วจัดหมวดตามวิจารณญาณ (ไม่มีสูตรตายตัว เพราะข้อความมาจากหลายรูปแบบ) เป็นหมวดที่พบบ่อย เช่น:
   - **Functional Bug จริง** (พฤติกรรมระบบไม่ตรง Expected Result)
   - **Accessibility Issue** (มาจาก axe-core scan)
   - **Script/Environment Error** (เคสที่เป็น `Blocked` — ไม่ใช่บั๊กจริง แยกกลุ่มออกมาให้ชัดเจนเสมอ ห้ามปนกับ Functional Bug)
4. **หา Root Cause ที่ซ้ำกันข้ามหลาย Test Case**: ถ้าหลายเคส Fail ด้วยเหตุผลเดียวกัน (เช่น component ที่ใช้ร่วมกันทุกหน้ามีปัญหา accessibility เดียวกัน — ตามที่ `qa-automation-script` (06a) มักจะระบุไว้ใน Remarks อยู่แล้วว่าเป็นปัญหาเดิมที่กระทบหลายเคส) **ต้องรวมเป็นประเด็นเดียวในรายงาน ไม่ใช่นับเป็นบั๊กแยกกันหลายจุด** — ระบุว่ากระทบ Test Case ID ใดบ้าง เพื่อไม่ให้ตัวเลข "จำนวนบั๊ก" ในรายงานบวมเกินจริง

## ขั้นตอนที่ 4 — สร้างรายงานสรุปผล (`07-result-analysis.docx`)

ใช้สคริปต์ที่ bundle มาด้วย (`scripts/build_docx_reports.py`) เพื่อสร้างไฟล์ Word จริงตามโครงสร้างนี้เสมอ:

1. **หัวรายงาน**: ชื่อ Feature, วันที่วิเคราะห์, Environment ที่ทดสอบ (Browser/Device จาก Env & Config), หมายเหตุถ้าเป็นการวิเคราะห์แบบ partial (จากขั้นตอนที่ 1)
2. **สรุปภาพรวม**: ทดสอบไปกี่เคสจากทั้งหมดกี่เคส (Test Coverage %), ตารางไขว้ Status × Priority
3. **ปัญหาหลักที่พบ (Root Cause)**: แต่ละประเด็นระบุ Root Cause, Test Case ID ที่กระทบ, Priority ที่กระทบสูงสุด, ระดับความรุนแรง (อ้างอิงจาก Priority ของเคสที่กระทบ — เคสที่กระทบ P0 ถือว่าความรุนแรงสูงสุดของประเด็นนั้น)
4. **ประเด็นที่ต้องแก้ก่อนปิดจบ**: กรองเฉพาะประเด็นที่กระทบเคส P0/P1 ที่ยัง Fail จริง (ไม่รวม Blocked เพราะไม่ใช่บั๊ก) ให้เห็นชัดแยกจากประเด็นอื่น
5. **หมายเหตุปิดท้าย**: แนะนำให้ไปต่อ `qa-reconcile` (RTM)

## ขั้นตอนที่ 5 — สร้างไฟล์ Photo Evidence (`07-photo-evidence.docx`)

ใช้สคริปต์เดียวกันสร้างไฟล์ที่สอง โดย **1 หน้าต่อ 1 Test Case ครบทุกเคสในทั้ง Workbook** (รวมเคสที่ยัง `not start` ด้วย ไม่ใช่แค่เคสที่รันแล้ว — เพื่อให้ไฟล์นี้เป็นหลักฐานฉบับสมบูรณ์ครบทุกเคสของ Feature) แต่ละหน้าประกอบด้วย:

1. **Test Case ID** + Test Scenario (บรรทัดเดียวสั้นๆ)
2. **คำอธิบายผล**: ถ้า Fail/Blocked ใช้ข้อความจาก Actual Result/Remarks, ถ้า Pass ใช้ Actual Result, **ถ้ายัง `not start` ให้เขียนชัดเจนว่า "ยังไม่ได้ทดสอบ" ห้ามเว้นว่างหรือใส่ข้อความอื่นที่ทำให้เข้าใจผิดว่าทดสอบแล้ว**
3. **จุดที่ผิด**: สรุปสาเหตุสั้นๆ ถ้า Fail/Blocked, ใส่ `-` ถ้า Pass, ใส่ `ยังไม่ได้ทดสอบ` ถ้า not start — ถ้าเคสนั้นมีหลายประเด็นที่แยกจากกันได้ชัดเจน (เช่น Accessibility 1 จุด + Performance 1 จุด + Keyboard nav 1 จุด) **ห้ามเขียนรวมเป็นข้อความยาวข้อความเดียว** ให้เตรียม `issue_point` เป็น list ของแต่ละประเด็นแทน (`scripts/build_docx_reports.py` จะแยกแต่ละจุดขึ้นบรรทัดของตัวเองพร้อม bullet ให้อัตโนมัติ) ส่วนเคสที่มีจุดผิดจุดเดียวยังคงส่งเป็น string ปกติเหมือนเดิมได้ ไม่ต้องห่อเป็น list
4. **รูปไฮไลท์**: ดึงจาก `screenshots/<Browser>/<Test Case ID>.png` (ถ้ามีมากกว่า 1 Browser ให้แสดงทุก Browser ในหน้าเดียวกัน แยกป้ายกำกับ Browser ใต้แต่ละภาพ) **ถ้าไม่มีภาพเลย (เช่นเคสยัง not start) ให้ใส่ข้อความ "ไม่มีภาพ — ยังไม่ได้ทดสอบ" แทนที่ว่างเปล่า ห้าม error หรือข้ามเคสนั้นไปเงียบๆ**
5. **Priority**: ค่า P0–P3 ของเคสนั้น

## ขั้นตอนที่ 6 — อัปเดต Manifest และสรุปให้ผู้ใช้

1. อัปเดต `_pipeline-manifest.md`: ตั้งค่า Stage `07 result-analysis` เป็น `Complete` เมื่อสร้างทั้ง 2 ไฟล์เสร็จ (Complete หมายถึง Skill นี้วิเคราะห์และสรุปข้อมูลที่มีอยู่เสร็จแล้ว **ไม่ได้แปลว่าผลทดสอบทั้งหมดผ่าน** — ถ้าข้อมูลที่วิเคราะห์เป็นแบบ partial ตามขั้นตอนที่ 1 ให้ระบุไว้ใน Notes ของ manifest ด้วย)
2. แจ้งผู้ใช้สรุปสั้นๆ: Test Coverage %, จำนวนประเด็น Root Cause ที่พบ, ประเด็นที่กระทบ P0/P1 (ถ้ามี) แล้วแนะนำให้ไปต่อ `qa-reconcile` (RTM)

## ข้อควรระวัง

- ห้ามนับ Test Case ที่ `Blocked` (Script/Environment Error) รวมกับ `Fail` (บั๊กจริง) ในการสรุปจำนวนบั๊กที่พบ — ต้องแยกให้ชัดเจนเสมอตลอดทั้งรายงาน
- ห้ามละเว้น Test Case ที่ยัง `not start` ออกจากไฟล์ Photo Evidence — ต้องมีครบทุกเคสตามที่ระบุไว้ในขั้นตอนที่ 5 แม้จะยังไม่มีผลก็ตาม
- Skill นี้เป็น**สกิลอ่านและสรุปผลเท่านั้น ห้ามแก้ไข Test Case Workbook เด็ดขาด**
