# requirement-review

Skill นี้เป็น**ขั้นตอนที่ 1 ที่บังคับ** ของ QA Pipeline (ต่างจาก `source-ingest` และ `test-plan` ซึ่งเป็น optional) หน้าที่คือวิเคราะห์ Requirement ของ Feature หนึ่งๆ ในเชิง QA อย่างละเอียด แล้วสร้างไฟล์ QA Review Report เป็น `.md` ที่ Skill ถัดไปในสาย pipeline (โดยเฉพาะ `e2e-flow-designer` และ `test-case-generator`) จะใช้เป็นอินพุตหลัก คุณภาพของไฟล์นี้จึงสำคัญมาก — ยิ่งวิเคราะห์ละเอียด Skill ถัดไปก็จะทำงานได้แม่นยำขึ้น

**สำคัญ**: คำสั่งในไฟล์นี้เขียนขึ้นให้ใช้ได้กับทั้ง Claude และ Gemini 3.6 — ห้ามอ้างอิงชื่อ tool เฉพาะของแพลตฟอร์มใดแพลตฟอร์มหนึ่ง ให้อธิบายเป็นขั้นตอนที่โมเดลไหนก็ทำตามได้

## ขั้นตอนที่ 1 — ระบุ Feature และโฟลเดอร์โปรเจค

1. **หาโฟลเดอร์รากของโปรเจค (Project Root)**: ถ้ายังไม่ทราบตำแหน่งโฟลเดอร์ "QA Pipeline Project" ให้ถามผู้ใช้ก่อนว่า Project Root อยู่ที่ path ไหน
2. ถามผู้ใช้ว่ากำลังทำ Requirement Review ให้ Feature ชื่ออะไร
3. **เช็คโฟลเดอร์ Feature ที่มีอยู่แล้วก่อนสร้างใหม่เสมอ**: ลิสต์รายชื่อโฟลเดอร์ย่อยทั้งหมดใต้ Project Root แล้วเทียบกับชื่อที่ผู้ใช้พิมพ์มาแบบไม่สนตัวพิมพ์เล็ก/ใหญ่และช่องว่างส่วนเกิน ถ้าเจอชื่อใกล้เคียงกันมาก ให้ถามผู้ใช้ยืนยันก่อนว่าเป็นโฟลเดอร์เดิมหรือจะสร้างใหม่ **ห้ามสร้างโฟลเดอร์ใหม่ซ้ำซ้อนกับของเดิมโดยไม่ถามผู้ใช้**
4. เช็คว่ามีไฟล์ `_pipeline-manifest.md` อยู่ในโฟลเดอร์ Feature นั้นหรือไม่
   - **ถ้ามีอยู่แล้ว**: อ่าน manifest เพื่อดูสถานะปัจจุบันของทุก Stage (ดูว่า `source-ingest`/`test-plan` เคยรันไปหรือยัง และ output อยู่ที่ไฟล์ไหน) ถ้า `requirement-review` เคยรันไปแล้ว (Complete) ให้แจ้งผู้ใช้และถามว่าจะรันซ้ำหรือไม่
   - **ถ้ายังไม่มี**: นี่คือ Feature ใหม่ (ผู้ใช้ข้าม `source-ingest` และ `test-plan` มาเริ่มที่นี่โดยตรง) — สร้างโฟลเดอร์ (ที่ `<Project Root>/<ชื่อ Feature>/`) และไฟล์ manifest ใหม่ (โครงสร้างเดียวกับที่ระบุไว้ใน Skill `source-ingest`) โดยตั้งค่า Stage `00-pre source-ingest` และ `00 test-plan` เป็น `Skipped` ทันที

## ขั้นตอนที่ 2 — รวบรวมอินพุตทั้งหมดที่มี

อ่าน manifest แล้วรวบรวมทุกอย่างที่มีอยู่แล้วสำหรับ Feature นี้ ก่อนเริ่มวิเคราะห์:

1. **Requirement**: ถ้า `source-ingest` เคยรันแล้ว (`Complete` หรือ `Pending Review`) ให้อ่านไฟล์ `00-pre-source-ingest.md` เป็นหลัก (ดูข้อควรระวังเรื่องสถานะ `Pending Review` ท้ายไฟล์นี้ด้วย)
   - ถ้า `source-ingest` มีสถานะ `In Progress` หรือ `Not Started` (คือเริ่มแล้วแต่ยังไม่เสร็จ หรือยังไม่มีใครเริ่มเลย — คนละกรณีกับ `Skipped` ที่แปลว่าตั้งใจข้าม) **ห้ามอ่านไฟล์ output ของ stage นั้นมาใช้ทันทีเหมือนเป็นข้อมูลที่สมบูรณ์แล้ว** ให้ทำตามข้อควรระวังเรื่องสถานะ `In Progress` ท้ายไฟล์นี้ (แจ้งผู้ใช้ว่า stage ยังไม่เสร็จ แล้วถามว่าจะรอหรือจะนำเข้า Requirement ทางอื่นไปพลางก่อน)
   - ถ้า `source-ingest` ไม่เคยรัน (Skipped) แต่ `test-plan` เคยรันแล้ว (`Complete` หรือ `Pending Review`) ให้เช็คในไฟล์ output ของ test-plan (path อยู่ในคอลัมน์ Output File ของ manifest — รูปแบบ `testplans/<test_plan_id>-<slug>.md` ไม่ใช่ชื่อไฟล์ตายตัว) ก่อนว่ามีเนื้อหา Requirement ต้นทางที่ผู้ใช้เคยให้ไว้ตอนทำ Test Plan ฝังอยู่หรือไม่ (ดูบรรทัด "Requirement อ้างอิงจาก:" ที่หัวไฟล์) ถ้ามี ให้หยิบมาใช้เป็นจุดเริ่มต้น แล้วถามผู้ใช้แค่ยืนยันว่าเนื้อหานั้นครบถ้วน/เป็นปัจจุบันหรือยัง หรือมีอะไรเพิ่มเติมอีกหรือไม่ — **อย่าให้ผู้ใช้ต้องพิมพ์ Requirement ที่เคยให้ไปแล้วซ้ำใหม่ทั้งหมดโดยไม่จำเป็น**
   - ถ้าไม่มีทั้งจาก `source-ingest` และ `test-plan` เลย ให้ถามผู้ใช้ว่าจะนำเข้า Requirement มาให้ตรงๆ (ไฟล์/ข้อความ) แบบไหน
2. **Test Plan (ถ้ามี)**: ถ้า `test-plan` เคยรันแล้ว (`Complete` หรือ `Pending Review`) ให้อ่านไฟล์ output ของมัน (path จากคอลัมน์ Output File ของ manifest) ด้วย โดยเฉพาะ**ค่า Deadline ที่กำหนดไว้ในนั้น** — ต้องนำมาใช้ต่อที่นี่ (ดูขั้นตอนที่ 4) ไม่ใช่ถามผู้ใช้ซ้ำถ้ามีอยู่แล้ว ถ้า `test-plan` มีสถานะ `In Progress` ให้ทำตามข้อควรระวังเรื่องสถานะ `In Progress` เช่นเดียวกับ source-ingest
3. **จุดที่ยังไม่ชัดเจน/ขัดแย้งกัน**: ถ้าไฟล์ source-ingest มีหัวข้อ "จุดที่ข้อมูลขัดแย้งหรือเป็นช่องว่าง (ต้องเติมก่อนหรือรับทราบก่อนไปขั้น 01)" หรือไฟล์ test-plan มีประเด็นอยู่ใน "## 10. ความเสี่ยงของแผนทดสอบ" หรือ "## 11. Open Questions" ให้**จดบันทึกไว้** เพื่อดึงกลับมาใส่ในรายงานของ Skill นี้ด้วย (ดูขั้นตอนที่ 4) — **ห้ามปล่อยให้ประเด็นเหล่านี้หายไปเงียบๆ**

อ่านทุกไฟล์ที่รวบรวมมาอย่างละเอียดครบถ้วนก่อนเริ่มวิเคราะห์จริง

## ขั้นตอนที่ 3 — วิเคราะห์ในเชิง QA

วิเคราะห์ Requirement ที่ได้มาอย่างละเอียด นี่คือขั้นตอนที่สำคัญที่สุดของ Skill นี้ เพราะ `e2e-flow-designer` และ `test-case-generator` จะอ่านผลลัพธ์นี้ต่อโดยตรง — ยิ่งวิเคราะห์ทะลุปรุโปร่งเท่าไหร่ Test Case ที่ออกแบบทีหลังจะครอบคลุมมากขึ้นเท่านั้น ให้ครอบคลุมประเด็นเหล่านี้:

- **สรุปสำหรับ QA**: หลังวิเคราะห์ทุกหัวข้อเสร็จแล้ว นับจำนวน Functional Requirements, Business Rules, Risks, Open Questions และสรุปสั้นๆ ว่าจุดไหนที่ QA ควรอ่านก่อนเป็นพิเศษ (ทำเป็นขั้นตอนสุดท้ายของการวิเคราะห์ เพราะต้องรู้ตัวเลขจริงก่อน)
- **Feature Overview**: ภาพรวมว่า Feature นี้คือเรื่องอะไร ทำอะไร ใครใช้ เป้าหมายทางธุรกิจคืออะไร
- **Stakeholders**: ใครเกี่ยวข้องบ้าง (Product Owner, Business Contact, ทีมที่ตัดสินใจ) ถ้าไม่มีชื่อบุคคลระบุในเอกสารต้นทาง ให้ใส่ "ไม่ระบุในเอกสารต้นทาง — QA ต้องเติมเอง" แทนการเดาชื่อ
- **Scope**: In-scope / Out-of-scope / ยังไม่ตัดสินใจว่าจะรวมในขอบเขตหรือไม่ — ถ้า `test-plan` เคยรันมาก่อน ให้ตรวจว่าขอบเขตตรงกันหรือขัดแย้งกันหรือไม่ (ดูขั้นตอนที่ 2)
- **Functional Requirements**: แจกแจงเป็นข้อๆ พร้อม ID (REQ-F-xxx), Priority (Must/Should/Could ตามหลัก MoSCoW) และเหตุผลสั้นๆ ว่าทำไมถึงเป็น Priority ระดับนั้น
- **Non-Functional Requirements**: แยกตามหมวด (Performance, Security, Usability, Compatibility, Reliability, Accessibility, Compliance/Legal, Localization ฯลฯ) พร้อม ID (REQ-NF-xxx) — หมวดไหนไม่มีข้อมูลในเอกสารต้นทาง ให้เติมเป็นสมมติฐานชั่วคราวพร้อม flag ไว้ใน Open Questions แทนการข้ามหมวดไปเงียบๆ
- **Business Rules & Validation Rules**: กฎ/เงื่อนไขที่เป็นตัวกำหนดพฤติกรรมของระบบโดยตรง (ไม่ใช่ Functional Requirement ระดับ flow แต่เป็นกฎย่อยที่ validate ค่า/สถานะ) พร้อม ID (BR-xxx)
- **User Roles & Permissions**: มีผู้ใช้กี่ประเภท แต่ละประเภททำอะไรได้บ้าง ต่างจาก Role อื่นตรงไหน ต้องขออนุมัติเพิ่มสำหรับ action ไหนหรือไม่
- **User Flow**: แยก Main Flow (เส้นทางหลักที่สำเร็จ) กับ Alternative / Error Flow (กรณี error/edge case ทั้งหมดที่มองเห็น) ออกจากกันชัดเจน
- **UI Reference**: ถ้ามีรูป/screenshot ที่ได้รับมา ให้อ้างอิงตรงนี้ ถ้าไม่มีให้ใส่ "ไม่มี UI reference ในรอบนี้"
- **Data / Field Specification**: field ที่เกี่ยวข้องกับ Feature นี้ พร้อม Type, Length/Range, Format, Mandatory, หมายเหตุ — field ไหนไม่มีระบุตรงในเอกสารต้นทางให้ flag เป็นสมมติฐานชั่วคราว
- **Dependencies & Integration**: ระบบ/บริการภายนอกที่เกี่ยวข้อง (เช่น third-party service, ระบบเดิมของแอปพลิเคชัน, API)
- **Related / Overlapping Requirements**: เช็คว่ามีไฟล์ Requirement Review อื่นในโฟลเดอร์ Feature เดียวกันที่เนื้อหาทับซ้อนกันหรือไม่
- **Assumptions**: สมมติฐานที่ต้องตั้งไว้เพราะ Requirement ไม่ได้ระบุชัด — ทุกข้อต้องมีที่มา (เช่น "จาก Slack thread วันที่ X") ห้ามเขียนลอยๆ โดยไม่มีที่มา
- **Open Questions**: แยกเป็น 2 กลุ่ม — (1) ข้อที่เดาไม่ได้จริง ต้องตอบก่อน Approve (checkbox ☐) และ (2) ข้อที่เติมสมมติฐานชั่วคราวไว้แล้วเพื่อเป็น audit trail (checkbox ☒ พร้อมบอกว่าเติมไว้ที่หัวข้อไหน) — รวมทั้งจุดที่เจอเองตอนวิเคราะห์รอบนี้ และจุดที่ดึงมาจาก `source-ingest`/`test-plan` ตามขั้นตอนที่ 2 ห้ามเดาคำตอบเอง
- **Risks**: พร้อม ID (RISK-xxx), หมวด, Likelihood, Impact, Risk Level และข้อเสนอแนะ/Mitigation — **คอลัมน์ "รายละเอียด" และ "ข้อเสนอแนะ/Mitigation" ต้องสั้นกระชับเสมอ (1-3 บรรทัด)** รายละเอียดยาวให้แยกเป็นย่อหน้าท้ายตารางแทนการยัดในเซลล์เดียว
- **Draft Acceptance Criteria (Given-When-Then)**: เขียนอย่างน้อย 1 AC ต่อ Functional Requirement ทุกข้อ (ไม่ใช่แค่บางข้อ) เพื่อให้ `test-case-generator` มีจุดเริ่มต้นครบทุก Requirement — เป็นแค่ Draft สั้นๆ ระดับ Given-When-Then เท่านั้น รายละเอียด edge case เต็มรูปแบบเป็นหน้าที่ของ Skill 03
- **QA Readiness Assessment**: ประเมินว่า Requirement นี้พร้อมส่งต่อให้ `e2e-flow-designer` เลยหรือยัง หรือมีช่องว่างที่ควรเคลียร์ก่อน

**หมายเหตุสำคัญ**: เขียนทุกหัวข้อด้านบนเสมอในไฟล์ผลลัพธ์ แม้หัวข้อนั้นจะไม่มีข้อมูลอะไรเลยก็ตาม — ให้ใส่ "ไม่มี" หรือ "ไม่ระบุในเอกสารต้นทาง" แทนการข้ามหัวข้อไปเงียบๆ เพื่อให้ Skill ถัดไปที่อ่านไฟล์นี้ต่อคาดเดาโครงสร้างได้เหมือนกันทุกครั้ง และเพื่อให้ QA ที่มาอ่านทีหลังรู้ว่านี่คือหัวข้อที่วิเคราะห์แล้วไม่มีข้อมูลจริง ไม่ใช่ลืมเขียน

## ขั้นตอนที่ 4 — กำหนด Deadline

ถามตัวเองก่อนว่ามีค่า Deadline อยู่แล้วหรือยัง:
- ถ้า `test-plan` มีการระบุ Deadline ไว้ในไฟล์ output ของมัน (ตามขั้นตอนที่ 2 — path จากคอลัมน์ Output File ของ manifest) ให้**ใช้ค่านั้นเลย** และแจ้งผู้ใช้ว่ากำลังใช้ค่าที่มาจาก Test Plan
- ถ้าไม่มี ให้ถามผู้ใช้ตรงๆ ว่า Deadline ของ Feature นี้คือวันไหน — **ห้ามเดาหรือปล่อยว่าง** เพราะ `qa-report-generator` (Skill 08) ต้องใช้ค่านี้ตัดสิน Go/No-Go ทีหลัง

## ขั้นตอนที่ 6 — บันทึกไฟล์และอัปเดต Manifest

1. บันทึกไฟล์ผลลัพธ์ที่ `<โฟลเดอร์ Feature>/01-requirement-review.md`
2. อัปเดตไฟล์ `_pipeline-manifest.md`: ตั้งค่า Stage `01 requirement-review` เป็น **`Pending Review`** (ไม่ใช่ `Complete` — ดูเหตุผลที่ "การอัปเดตสถานะเป็น Complete หลัง Sign-off" ท้ายขั้นตอนนี้), ใส่ path ของไฟล์ output, ใส่วันที่เสร็จ
3. แจ้งผู้ใช้ว่าเสร็จแล้ว สรุปสั้นๆ ว่าพบ Open Questions/Risks กี่ข้อ (ถ้ามี ให้เตือนว่าควรไปสอบถามให้ชัดเจนก่อนไปต่อ) แนะนำให้ไปต่อที่ `e2e-flow-designer` (Skill 02) และเตือนสั้นๆ ว่าสถานะยังเป็น `Pending Review` จนกว่าจะมีคนรีวิวและกรอก `## 20. QA Review & Sign-off` เป็น approved
4. **(เพิ่มเติมเพื่อความสะดวกในการอ่าน — ไม่กระทบขั้นตอนอื่นในสาย pipeline)** สร้างไฟล์ Word (.docx) คู่กับไฟล์ .md ที่บันทึกไว้ในข้อ 1 โดยใช้ชื่อไฟล์เดียวกัน (เปลี่ยนแค่นามสกุล) เก็บไว้ในโฟลเดอร์เดียวกัน — รัน 4 คำสั่งนี้ตามลำดับ:
   ```
   pandoc "<path .md>" -f markdown+hard_line_breaks -o "<path .docx ชื่อเดียวกัน>" --standalone
   python3 "<path skill>/scripts/resize_table_columns.py" "<path .docx>"
   python3 "<path skill>/scripts/add_table_borders.py" "<path .docx>"
   python3 "<path skill>/scripts/fix_page_breaks.py" "<path .docx>"
   ```
   ขั้นแรกแปลง .md เป็น .docx ขั้นที่สอง**ปรับความกว้างคอลัมน์ของทุกตารางตามเนื้อหาจริง พร้อมลดขนาดฟอนต์ในตารางลงเหลือ 10pt** (ยืนยันแล้วผ่าน Mockup — pandoc หารความกว้างเท่ากันทุกคอลัมน์โดย default ทำให้คอลัมน์ข้อความยาว เช่น "รายละเอียด"/"หมายเหตุ"/"ข้อเสนอแนะ" แคบเกินไปจนคำถูกตัดกลางคำอ่านยาก โดยเฉพาะตารางคอลัมน์เยอะอย่าง Risks 7 คอลัมน์ — สคริปต์นี้คำนวณความกว้างจากความยาวเนื้อหาจริงในแต่ละคอลัมน์ ไม่ได้ hardcode ตามชื่อหัวตาราง เพราะไฟล์นี้มีหลายตารางโครงสร้างต่างกัน **และตรวจจับคำภาษาอังกฤษ/ตัวเลขคำเดียวยาวๆ (เช่น "Likelihood", "Operational", ชื่อ field แบบ `max_discount_cap`) ที่ column แคบเกินไปจะตัดกลางคำ แล้วกันความกว้างขั้นต่ำให้คำนั้นอยู่บรรทัดเดียวได้ — ไม่กันความกว้างให้ข้อความไทยเพราะภาษาไทยตัดบรรทัดตรงไหนก็ยังอ่านได้ปกติอยู่แล้ว** พบปัญหานี้ตอนแก้ Format รอบสองหลังทดสอบกับตาราง Risks จริง คอลัมน์อย่าง Likelihood/Impact ที่ก่อนหน้านี้แคบจนตัดคำกลางคำ (เช่น "Likeliho"/"od") ขั้นที่สามใส่กรอบให้ทุกตาราง (มีหลายตารางในรอบนี้ — Executive Summary, Stakeholders, Functional/Non-Functional Requirements, Business Rules, User Roles, Data/Field Specification, Risks, Revision History) และกันแถวตารางแตกข้ามหน้า ขั้นที่สี่ป้องกันไม่ให้หัวข้อลอยเดี่ยวท้ายหน้าโดยเนื้อหาไปขึ้นหน้าถัดไป — ทั้งสามสคริปต์แก้เฉพาะไฟล์ `.docx` เท่านั้น ไม่แตะไฟล์ `.md` ต้นทาง ไฟล์ `.docx` นี้เป็นเพียง**สำเนาเพื่อความสะดวกในการอ่านเท่านั้น** — ไฟล์ `.md` ยังคงเป็นไฟล์หลัก (source of truth) ที่ Skill ถัดไปในสาย pipeline ใช้อ่านต่อเสมอ ไม่ใช่ `.docx` และไม่ต้องอัปเดตคอลัมน์ Output File ใน Manifest เพิ่มเติม ถ้าเครื่องที่ใช้งานไม่มีคำสั่ง `pandoc` หรือ python พร้อม `python-docx` ติดตั้งไว้ ให้แจ้งผู้ใช้แล้วข้ามขั้นตอนที่ทำไม่ได้ไปได้เลย ไม่ถือเป็นตัวบล็อกการทำงานของ Skill นี้

### การอัปเดตสถานะเป็น Complete หลัง Sign-off

`Pending Review` แปลว่า "ไฟล์สร้างเสร็จแล้ว แต่ยังไม่มีใครรีวิว/อนุมัติ" — สถานะนี้จะเปลี่ยนเป็น `Complete` ได้ก็ต่อเมื่อผู้ใช้แจ้งกลับมาว่าได้เปิดไฟล์นี้รีวิวแล้ว และกรอก `## 20. QA Review & Sign-off` ท้ายไฟล์เป็น **"การตัดสินใจ: approved"** เท่านั้น (ผู้ใช้ต้องเป็นคนกรอกเอง — ดูข้อควรระวังเรื่องห้าม AI กรอกแทน) เมื่อได้รับการยืนยันแบบนี้ ให้กลับมาอัปเดต `_pipeline-manifest.md` เปลี่ยน Stage `01 requirement-review` จาก `Pending Review` เป็น `Complete`

ถ้าผู้ใช้แจ้งว่ากรอกเป็น "rejected" หรือ "needs revision" ให้สถานะคงเป็น `Pending Review` ต่อไป (ไม่ใช่ Complete) จนกว่าจะแก้ไขและได้รับการอนุมัติใหม่ — การแก้ไขให้ทำตาม "การรันซ้ำ/อัปเดต Requirement Review เดิม" ด้านล่าง

**ข้อสำคัญ**: นี่ไม่ใช่กลไกบังคับแบบเถียงไม่ได้ในตัว Skill นี้เอง — เป็นแค่การรักษาความถูกต้องของ manifest ให้สื่อความจริง อย่างไรก็ตาม `e2e-flow-designer` (Skill 02) **มีการเช็คสถานะนี้จริง**: ถ้าไฟล์นี้ยังเป็น `Pending Review` (สร้างเสร็จผ่าน Pipeline แล้วแต่ยังไม่ได้ approve) Skill 02 จะ Hard Block ไม่ให้ทำงานต่อจนกว่าจะกรอก `## 20. QA Review & Sign-off` เป็น approved ก่อน (ดูรายละเอียดที่ขั้นตอนที่ 1 ของ `e2e-flow-designer`) — ดังนั้นในทางปฏิบัติ ถ้าผู้ใช้ต้องการไปต่อ Skill 02 ทันที จำเป็นต้อง approve ไฟล์นี้ก่อนจริงๆ (ต่างจาก `source-ingest`/`test-plan` ที่ยังไม่มีการเช็คสถานะแบบนี้)

### การรันซ้ำ/อัปเดต Requirement Review เดิม

ถ้าผู้ใช้ขอแก้ไข Requirement Review ที่มีอยู่แล้ว (ไม่ใช่ทำฉบับใหม่ทั้งหมด — เช่น Requirement ต้นทางมีการเปลี่ยนแปลงหลัง Pipeline เดินหน้าไปแล้ว):

- เขียนทับไฟล์ `.md` เดิมด้วยเนื้อหาที่อัปเดตแล้วทั้งฉบับ (ไม่ใช่แค่แก้บางส่วน) เพื่อให้ไฟล์นี้เป็นภาพล่าสุดที่ครบถ้วนเสมอ
- เพิ่มบรรทัด `Updated: <วันที่รันซ้ำ>` ต่อท้ายบรรทัด `Created:` เดิมในหัว Header (ห้ามลบ/แก้ `Created:` เดิม)
- เพิ่มแถวใหม่ต่อท้ายตาราง `## 19. Revision History` เดิม (ห้ามลบแถวเก่า) — เลข Version เรียงต่อจากแถวล่าสุด (เช่น 1.0 → 1.1) ช่อง "สรุปการเปลี่ยนแปลง" เขียนสั้นๆ ตรงๆ ว่ารอบนี้แก้อะไร
- ทบทวนทุกหัวข้อที่อาจได้รับผลกระทบจากการเปลี่ยนแปลง โดยเฉพาะ `## 15. Open Questions` และ `## 16. Risks` — เงื่อนไข/สมมติฐานที่เคยเปิดค้างไว้อาจถูกยืนยันแล้วหรือมีของใหม่เพิ่มมา
- `## 20. QA Review & Sign-off` ให้เว้นว่างใหม่ทุกครั้งที่เขียนไฟล์ใหม่ทั้งฉบับ (checkbox ยังไม่ติ๊ก, Reviewer comment/การตัดสินใจยังว่าง) เพราะเนื้อหาเปลี่ยนไปจากรอบก่อน ต้องให้คนตรวจสอบใหม่เสมอ
- อัปเดต manifest ให้ Stage `01 requirement-review` กลับไปเป็น `Pending Review` เสมอ (แม้ก่อนรันซ้ำจะเคยเป็น `Complete` แล้วก็ตาม) เพราะเนื้อหาเปลี่ยนไปแล้ว ต้องรอการอนุมัติใหม่

## ข้อควรระวัง

- ห้ามเดาหรือแต่งเนื้อหา Requirement ที่ไม่มีอยู่ในอินพุตที่ได้รับมา ถ้าไม่ชัดเจนให้ใส่ไว้ใน Open Questions แทนการเดาเอง
- ถ้า Requirement ต้นทางมีจุดขัดแย้งที่ยังไม่ได้รับการยืนยัน (เช่นจาก `source-ingest`) ห้ามเลือกฝั่งใดฝั่งหนึ่งเองแล้วเขียนราวกับว่าเป็นข้อสรุปที่แน่นอน ต้องคงความไม่ชัดเจนนั้นไว้ใน Open Questions
- ถ้าผู้ใช้แจ้งว่า Requirement มีการเปลี่ยนแปลงหลังจาก Pipeline เดินหน้าไปแล้ว (เช่น Test Case ถูกสร้างไปแล้วที่ Skill 03) การแก้ไขที่ถูกต้องคือรัน Skill นี้ใหม่ทั้งหมดสำหรับ Feature นั้น ไม่ใช่พยายามแก้เฉพาะจุด (ดู "การรันซ้ำ/อัปเดต Requirement Review เดิม" ในขั้นตอนที่ 6)
- ถ้า manifest ระบุว่า `source-ingest` หรือ `test-plan` มีสถานะ `In Progress` หรือ `Not Started` (เริ่มทำแล้วแต่ยังไม่เสร็จ หรือยังไม่มีใครเริ่มเลย — ไม่ใช่ Complete และไม่ใช่ Skipped) ห้ามอ่านไฟล์ output ของ stage นั้นมาใช้ทันทีเหมือนเป็นข้อมูลที่สมบูรณ์แล้ว ให้แจ้งผู้ใช้ก่อนว่า stage นั้นยังไม่เสร็จ แล้วถามว่าจะรอให้ทำ stage นั้นให้เสร็จก่อน หรือจะนำเข้า Requirement ทางอื่น/ที่มีอยู่บางส่วนไปพลางก่อน
- ถ้า manifest ระบุว่า `source-ingest` หรือ `test-plan` มีสถานะ `Pending Review` (ไฟล์สร้างเสร็จแล้ว แต่ QA ยังไม่ได้รีวิว/อนุมัติผ่าน QA Review & Sign-off ในไฟล์นั้น) ให้อ่านไฟล์นั้นมาใช้ได้ตามปกติ แต่ต้องแจ้งผู้ใช้ก่อนเริ่มวิเคราะห์ว่าต้นทางยังไม่ได้รับการอนุมัติอย่างเป็นทางการ แล้วถามว่าจะรอให้ QA อนุมัติก่อน หรือจะใช้เนื้อหาที่มีอยู่ตอนนี้ไปพลางก่อน — ถ้าเลือกใช้ต่อเลย ให้บันทึกไว้ใน `## 15. Open Questions` ของ Skill นี้ด้วยว่า Requirement ต้นทางยังไม่ได้ approve อย่างเป็นทางการ เผื่อมีการแก้ไขตามมาทีหลัง
- คอลัมน์ "รายละเอียด" และ "ข้อเสนอแนะ/Mitigation" ในตารางความเสี่ยง (ข้อ 16) ต้องสั้นกระชับเสมอ — รายละเอียดยาวให้แยกเป็นย่อหน้าท้ายตารางแทนการยัดในเซลล์เดียว
- ทุกข้อที่เป็นสมมติฐาน (ไม่ใช่ความเสี่ยง) ต้องมีที่มาเสมอ (เช่น "จาก Slack thread วันที่ X" หรือ "ระบุตรงในสเปก") ห้ามเขียนสมมติฐานลอยๆ โดยไม่มีที่มา และห้ามใช้เป็นทางลัดในการ "เดา" สิ่งที่ไม่มีมูลอะไรรองรับเลย
- `## 20. QA Review & Sign-off` ท้ายไฟล์คือช่องให้คน (QA/ผู้ตรวจสอบ) กรอกเอง — AI สร้างได้แค่โครง checkbox เปล่ากับหัวข้อ "Reviewer comment:" และ "การตัดสินใจ:" เท่านั้น **ห้ามเดา/เติมคำตอบลงไปเองเด็ดขาด**
