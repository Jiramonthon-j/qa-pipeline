# qa-retest

Skill นี้เป็น**ขั้นตอนที่ 10** ของ QA Pipeline หน้าที่คือปิด loop ระหว่าง QA กับ Dev: เช็คว่า Ticket ที่เปิดไว้ใน `redmine-logging` (09) มีอันไหนที่ Dev แจ้งว่าแก้เสร็จแล้วบ้าง วิเคราะห์คอมเมนต์ของ Dev เทียบกับ Test Case เดิม ตัดสินใจว่าต้องปรับ Test Data ก่อน Retest ไหม แล้วรัน Automation Script จริงเฉพาะเคสที่เกี่ยวข้อง จากนั้นเขียนผลกลับ Workbook — **Skill นี้อ่านข้อมูลจาก Redmine จริง (เชื่อมต่อระบบภายนอก) เหมือน Skill 09 จึงใช้กฎความปลอดภัยเรื่อง credential ชุดเดียวกัน** และ**ไม่แตะต้อง Comment/Status ของ Ticket ใน Redmine เลย** (เรื่องคอมเม้นต์กลับ + ปิด Ticket จะแยกไปทำใน Skill 10a ในอนาคต ผู้ใช้ยืนยันแล้วว่าต้องการแยก Skill นี้ให้ทำแค่ "เช็ค → วิเคราะห์ → Retest → บันทึกผล" เท่านั้น)

## ขั้นตอนที่ 1 — ตรวจสอบขั้นตอนก่อนหน้าและกำหนดขอบเขต (Scope)

1. หาโฟลเดอร์ Project Root และโฟลเดอร์ Feature เหมือน Skill อื่นๆ ในสาย อ่าน `_pipeline-manifest.md`
2. **เช็ค Gate**: ต้องมี Ticket จริงที่เปิดไปแล้วอย่างน้อย 1 ใบจาก `redmine-logging` (09) เสมอ — ตรวจสอบสถานะ Stage `09 redmine-logging`:
   - **`Complete`** (เปิด Ticket จริงไปแล้ว อาจมี failed บางเคสก็ได้): ผ่าน Gate ไปขั้นตอนถัดไป
   - **`Complete (Export เท่านั้น — ...)`**: **ไม่ผ่าน Gate** เพราะยังไม่มี Ticket จริงให้เช็ค Status เลย (แค่ Export ไฟล์ Excel) — แจ้งผู้ใช้ตรงๆ ว่าต้องกลับไปเปิด Ticket จริงใน `redmine-logging` (09) ก่อน (Action 1/2) ถึงจะใช้ Skill นี้ได้
   - **`ยังไม่เปิด Ticket (ผู้ใช้ยกเลิก ...)`** หรือยังไม่มี Stage 09 เลย: **ไม่ผ่าน Gate** — แจ้งผู้ใช้ให้ไปรัน `redmine-logging` (09) ให้เสร็จก่อน
3. **ถ้า Stage `10 qa-retest` เคยรันไปแล้ว**: แจ้งผู้ใช้ว่าเคยรันล่าสุดเมื่อไหร่ (ดูวันที่ใน manifest) แล้วถามว่าต้องการรันซ้ำเพื่อเช็คว่ามี Ticket ไหนที่ Dev เพิ่งแจ้งแก้ใหม่หรือไม่ — Skill นี้ออกแบบให้รันซ้ำได้เรื่อยๆ อย่างปลอดภัย (idempotent) เพราะ Scope ต่อไปนี้จะกรองเฉพาะเคสที่ยังเป็น `Fail` อยู่จริงเท่านั้น เคสที่เคย Retest แล้ว Pass จะหลุดออกจาก Scope โดยอัตโนมัติในรอบถัดไป ไม่ต้องมีสถานะพิเศษอะไรมาแยกอีก
4. **กำหนด Scope**: อ่าน Test Case Workbook ชีต "Test Case" **สดจากไฟล์จริงเสมอ** ด้วย `python3 scripts/qa_workbook.py read-cases --path "<path>"` แล้วกรองเฉพาะ Test Case ที่เข้าเงื่อนไข**ทั้งสองข้อ**พร้อมกัน:
   - `Status = "Fail"` (ยังไม่ผ่าน — ถ้า Pass ไปแล้วไม่ต้อง Retest ซ้ำ)
   - คอลัมน์ "Issue link" **ไม่ว่างเปล่า** (แปลว่าเคยเปิด Ticket จริงไปแล้วจาก Skill 09 — ถ้า Fail แต่ไม่มี Issue link แปลว่ายังไม่เคยแจ้ง Dev เลย ไม่ใช่ Scope ของ Skill นี้ ให้ผู้ใช้ไปรัน `redmine-logging` (09) ก่อน)

   นี่คือ Scope ที่ผู้ใช้ยืนยันแล้ว ("เช็คทุก Ticket ที่เคยเปิดไว้และยังไม่ถูก Retest") — **ไม่ต้องเก็บ state แยกว่า "เคยเช็ครอบไหนแล้วบ้าง"** เพราะเงื่อนไข Status=Fail เพียงพอแล้วที่จะบอกว่ายัง "ค้าง" อยู่จริง

   **ถ้ากรองแล้วว่างเปล่า (ไม่มีเคสที่ต้อง Retest เลย)**: แจ้งผู้ใช้ว่าไม่มีอะไรต้องทำในรอบนี้ (อาจเป็นเพราะยังไม่มี Fail ที่มี Ticket เลย หรือ Retest ไปหมดแล้วทุกเคสก่อนหน้านี้) ตั้ง Stage `10 qa-retest` เป็น `Complete (ไม่มีเคสที่ต้อง Retest ในรอบนี้)` แล้วจบ Skill ทันที

## ขั้นตอนที่ 2 — เช็ค Status และ Comment ของ Ticket จาก Redmine จริง

1. สร้างไฟล์ `tc-issue-map.json` จากรายการ Scope ในขั้นตอนที่ 1 รูปแบบ `[{"tc_id": "TC-xxx", "issue_url": "<ค่าจริงจากคอลัมน์ Issue link>"}, ...]`
2. **ถามผู้ใช้ตรงๆ ทุกครั้งที่รัน Skill นี้ (ห้ามจำ/เก็บค่าจากรอบก่อนไว้ใช้ซ้ำ ห้ามเขียนค่าเหล่านี้ลงไฟล์ใดๆ ในโปรเจคเด็ดขาด)** — กฎเดียวกับ `redmine-logging` (09) ทุกประการ:
   - Redmine URL
   - Redmine API Key
   - **Redmine Status value ไหนบ้างที่นับว่า "Dev แก้เสร็จแล้ว พร้อม Retest"** (เช่น `Resolved`, `Fixed` — ต้องถามเพราะแต่ละ Redmine instance ตั้งชื่อ Status ไม่เหมือนกัน เหตุผลเดียวกับที่ต้องถามชื่อ Tracker ใน Skill 09) รับได้หลายค่าคั่นด้วย comma
3. ตั้ง `REDMINE_URL`/`REDMINE_API_KEY` เป็น environment variable ก่อนเรียกสคริปต์เสมอ **ห้ามส่งเป็น `--argument` ตรงๆ** แล้วรัน:
   ```
   python3 scripts/check_redmine_status.py check --tc-issue-map "<path>.json" --resolved-statuses "<ค่าจากข้อ 2>" --out "<result>.json"
   ```
4. อ่านผลลัพธ์ (`ready`/`waiting`/`failed`) แล้วรายงานผู้ใช้ทราบครบทุกกรณี:
   - **`ready`**: Ticket ที่ Status ตรงกับที่ผู้ใช้ระบุว่า "แก้เสร็จแล้ว" — ไปทำขั้นตอนที่ 3 ต่อเฉพาะกลุ่มนี้
   - **`waiting`**: Ticket ที่ยังไม่ตรง (Dev ยังไม่แจ้ง หรือแจ้งไปที่ Status อื่น) — **ไม่ใช่ error** แจ้งผู้ใช้ว่ายังรอ Dev อยู่กี่ใบ พร้อม Status ปัจจุบันของแต่ละใบ ข้ามไปก่อน ไม่ต้อง Retest
   - **`failed`**: ดึงข้อมูล Ticket ไม่สำเร็จ (เชื่อมต่อ Redmine ไม่ได้, permission ไม่พอ, Ticket ถูกลบ ฯลฯ) — แจ้ง error จริงที่ได้กลับมา ถ้ามีคำว่า "403"/"Forbidden" จาก proxy (ไม่ใช่จาก Redmine เอง) ให้สงสัยไว้ก่อนว่าอาจเป็นเพราะ network egress ของ environment ยังไม่ได้ allowlist โดเมน Redmine ไว้ (ปัญหาประเภทเดียวกับที่เจอใน Skill 09) ไม่ใช่เดาสาเหตุอื่น

   **ถ้า `ready` ว่างเปล่าทั้งหมด**: แจ้งผู้ใช้สรุปว่ายังไม่มี Ticket ไหนพร้อม Retest ในรอบนี้ ตั้ง Stage `10 qa-retest` เป็น `In Progress (รอ Dev แก้อยู่ N ใบ)` แล้วจบ Skill ทันที ไม่ต้องทำขั้นตอนถัดไป

## ขั้นตอนที่ 3 — วิเคราะห์ Comment ของ Dev เทียบกับ Test Case ล่าสุด

สำหรับแต่ละ Ticket ใน `ready`:

1. อ่าน Comment (`comments` list ที่ได้จากขั้นตอนที่ 2 — เรียงตาม `created_on` จากเก่าไปใหม่อยู่แล้ว) **โฟกัสที่ Comment ล่าสุดเป็นหลัก** (Comment เก่าอาจเป็นแค่การอัปเดตความคืบหน้าระหว่างทาง ไม่ใช่คำตอบสุดท้าย) แต่อ่าน Comment ก่อนหน้าประกอบด้วยถ้าจำเป็นต่อความเข้าใจบริบท
2. **อ้างอิงจาก Test Case ล่าสุดที่มีการ Test จริง** (Test Step, Test Data ปัจจุบันในคอลัมน์ Workbook, Expected/Actual Result, Root Cause ถ้ามีใน `07-result-analysis.docx`) วิเคราะห์ว่า Dev แก้อะไรไปบ้าง แล้วตัดสินใจ 1 ใน 2 กรณีต่อ Test Case:
   - **(A) ใช้ Test Data เดิมได้เลย**: Dev แก้ที่ตัว Logic/โค้ดของระบบ ไม่ได้เปลี่ยนเงื่อนไข/ค่าที่ Test Case ต้องใช้ทดสอบ (เช่น "แก้ validation logic ให้เช็ค usage_limit ถูกต้องแล้ว" โดย Test Data เดิมยังทดสอบเคสเดิมได้ตรงจุด)
   - **(B) ต้องสร้าง Test Data ใหม่**: Comment ของ Dev บ่งชี้ว่า Test Data เดิมใช้ไม่ได้แล้ว (เช่น ค่าที่เคยใช้ทดสอบถูกลบ/หมดอายุไปแล้วในระบบจริง, Dev ขอให้ทดสอบด้วยเงื่อนไขที่ต่างจากเดิมเพื่อยืนยันการแก้ไข, หรือค่าเดิมกระทบกับการแก้ไขจนใช้ซ้ำไม่ได้) — ถ้าเลือกกรณีนี้ต้องเตรียมค่า Test Data ใหม่ที่ยังคง**ทดสอบ Expected Result เดิมของ Test Case นั้น** (แก้แค่ค่าที่ใช้ ไม่ใช่เปลี่ยนเป้าหมายของ Test Case)
3. **ถ้า Comment ของ Dev ไม่ชัดเจนพอจะตัดสินได้ (เช่น เขียนกำกวม, พูดถึงแค่บางส่วนของ Test Case, หรือใช้ศัพท์เทคนิคที่ไม่แน่ใจว่าหมายถึงอะไร)**: **ห้ามเดา** — หยุดแล้ว paste ข้อความ Comment จริงให้ผู้ใช้ดู พร้อมอธิบายว่าติดตรงไหน แล้วถามผู้ใช้ตรงๆ ว่าควรตีความว่าอย่างไร (ใช้ข้อมูลเดิมหรือสร้างใหม่ และถ้าสร้างใหม่ค่าควรเป็นอะไร) — Test Case ไหนที่ยังตัดสินใจไม่ได้ ให้ข้ามไปก่อน ไม่ต้องบล็อกเคสอื่นที่วิเคราะห์ได้ชัดเจนแล้ว
4. สรุปผลการวิเคราะห์ทุกเคสเป็นรายการ (`tc_id`, `decision: same_data | new_data`, เหตุผลสั้นๆ, ค่า Test Data ใหม่ถ้าเป็นกรณี (B)) แล้ว**แสดงสรุปนี้ให้ผู้ใช้ดูก่อนไปขั้นตอนที่ 4** เพื่อให้ตรวจทานได้ก่อนจะแก้ไฟล์จริง (การแก้ Automation Script เป็นการแก้โค้ด ควรให้ผู้ใช้เห็นก่อนเสมอ ไม่ใช่แค่ Workbook)

## ขั้นตอนที่ 4 — ปรับ Test Data (เฉพาะเคสที่เป็นกรณี B) ให้ Workbook กับ Script ตรงกัน

**หมายเหตุสถาปัตยกรรมที่สำคัญมาก (ยืนยันจากการอ่านโค้ดจริงของ `qa-automation-script` (06a))**: ค่า Test Data ของแต่ละ Test Case ถูก hardcode เป็น literal argument ตรงๆ ในไฟล์ `automation/<TC-ID>.py` ของเคสนั้น (เช่น `lib.api_seed_code(base_url, "ONETIME10", "fixed", 10, ...)`) **ไม่ได้อ่านจากไฟล์ข้อมูลภายนอก** ส่วนคอลัมน์ "Test Data" ใน Workbook เป็นแค่คำอธิบาย/บันทึกค่าที่ใช้จริงแบบข้อความล้วน (documentation) คนละที่เก็บกับค่าที่ script ใช้จริง — **สองที่นี้ไม่ sync กันอัตโนมัติ ถ้าแก้ที่เดียวแล้วลืมอีกที่ Retest จะทดสอบด้วยค่าเก่าที่ไม่ตรงกับที่บันทึกไว้ (หรือ Workbook จะโกหกว่าใช้ค่าใหม่ทั้งที่ script ยังรันค่าเดิมอยู่)** ผู้ใช้เตือนเรื่องนี้ไว้ตรงๆ ตอนออกแบบ Skill นี้ ต้องแก้ทั้ง 2 จุดพร้อมกันเสมอสำหรับกรณี (B) เท่านั้น:

1. **แก้ Workbook**: รวมทุกเคสกรณี (B) เป็นไฟล์ JSON เดียว `[{"tc_id": "...", "field": "Test Data", "value": "<คำอธิบาย Test Data ใหม่>"}]` แล้วอัปเดตครั้งเดียว (ไม่ทำทีละเคส เหตุผลเดียวกับ Skill 06a):
   ```
   python3 scripts/qa_workbook.py update-fields-batch --path "<path Workbook>" --updates-json "<path>.json" --editor "qa-retest" --note "ปรับ Test Data ใหม่ตามที่ Dev แจ้งแก้ไข ก่อน Retest <จำนวน> เคส"
   ```
2. **แก้ Automation Script**: เปิดไฟล์ `automation/<TC-ID>.py` ของแต่ละเคสกรณี (B) ด้วย Edit tool ตรงๆ แก้เฉพาะค่า literal ของ Test Data ให้ตรงกับค่าใหม่ที่วิเคราะห์ไว้ในขั้นตอนที่ 3 **ห้ามแก้ Logic การ Assert หรือโครงสร้างอื่นของไฟล์โดยไม่จำเป็น** (แก้เฉพาะค่าที่เป็น Test Data เท่านั้น) แล้วรัน `python3 -m py_compile automation/<TC-ID>.py` ตรวจว่าไฟล์ยัง valid หลังแก้ทุกครั้ง
3. **เคสกรณี (A) (ใช้ Test Data เดิม)**: ไม่ต้องแก้อะไรทั้ง Workbook และ Script — ใช้ค่าปัจจุบันที่มีอยู่แล้วรัน Retest ได้เลยตามที่ผู้ใช้ยืนยันไว้ตอนออกแบบ Skill นี้ ("ในกรณีที่ไม่มีการเปลี่ยน Test Data ก็ใช้ Test Script เดิมได้เลย")

## ขั้นตอนที่ 5 — Retest จริงด้วย Playwright

1. **เก็บ Screenshot เดิมไว้ก่อนถูกเขียนทับ** (audit trail — เหตุผลเดียวกับที่ Pipeline นี้เก็บ Document Control History ทุกจุด): ก่อนรัน ให้ย้ายไฟล์ `screenshots/<Browser>/<TC-ID>.png` เดิม (ถ้ามี) ไปไว้ที่ `screenshots/<Browser>/_history/<TC-ID>_<วันที่รันรอบก่อน หรือถ้าไม่รู้ให้ใช้วันนี้ก่อนรัน>.png` แล้วค่อยรัน Retest ทับที่ path เดิม
2. **Browser ที่ Retest**: รันซ้ำ**ทุก Browser ที่ระบุไว้ใน Env & Config** สำหรับทุกเคสที่วิเคราะห์แล้วในขั้นตอนที่ 3 (ทั้งกรณี A และ B ที่ตัดสินใจได้แล้ว) — **เป็นค่า default ที่เลือกไว้เพื่อความปลอดภัย** ไม่จำกัดแค่ Browser ที่เคย Fail เท่านั้น เพราะการแก้โค้ดฝั่ง Dev หรือการเปลี่ยน Test Data อาจกระทบ Browser ที่เคย Pass ด้วยเช่นกัน (regression ข้าม Browser เกิดขึ้นได้จริง) ถ้าผู้ใช้ต้องการจำกัดเฉพาะ Browser ที่เคย Fail เพื่อความเร็ว สามารถแจ้ง Claude ให้ปรับได้ในแต่ละรอบ
3. รันด้วย runner กลางตัวเดียวกับ Skill 06a ผ่าน stub ของ Skill นี้ กรองเฉพาะเคสที่วิเคราะห์แล้วด้วย `--tc`:
   ```
   python3 scripts/run_automation.py --automation-dir "<Feature>/automation" --base-url "<URL จาก Env & Config>" --screenshots-dir "<Feature>/screenshots" --browser <browser> --tc TC-xxx TC-yyy ...
   ```
   (รันซ้ำคำสั่งนี้เปลี่ยน `--browser` ไปทีละตัวตามจำนวน Browser ใน Env & Config — พฤติกรรม Pass/Fail/Blocked, การวาด Highlight, และการสแกน Accessibility ทั้งหมดเหมือน Skill 06a ขั้นตอนที่ 3-4 ทุกประการเพราะใช้ runner ตัวเดียวกัน)
4. เก็บผลลัพธ์ (`Status`, `Actual Result`, `Remarks`) ของทุกเคส/ทุก Browser ไว้รวมกัน ยังไม่ต้องเขียนกลับ Workbook ทีละรายการ

## ขั้นตอนที่ 6 — เขียนผลกลับ Workbook, อัปเดต Manifest, และรายงานสรุป

0. **กฎรวมผลข้าม Browser เป็น 1 Status ต่อ 1 Test Case**: ใช้กฎเดียวกับ `qa-automation-script` (06a) ขั้นตอนที่ 5 ข้อ 2 เป๊ะๆ (Fail ถ้ามีอย่างน้อย 1 Browser ยัง Fail > Blocked ถ้าไม่มี Fail แต่มี Blocked > Pass ก็ต่อเมื่อทุก Browser Pass ทั้งหมด) รวมถึงกฎการระบุชื่อ Browser กำกับใน Actual Result เมื่อผลต่างกันข้าม Browser และการใส่ path หลายไฟล์คั่นด้วย `;` ในคอลัมน์ Test Photo ถ้า Fail มากกว่า 1 Browser — สำคัญมากเพราะ `qa-retest-closure` (10a) จะอ่าน Status/Actual Result เดียวนี้ไปตัดสินว่าจะปิด Ticket หรือคอมเมนต์แจ้ง Dev ต่อ ถ้าสรุปผิดจะปิด Ticket ทั้งที่ยัง Fail อยู่ใน Browser อื่น
1. รวมผลของทุกเคสที่ Retest ในรอบนี้เป็นไฟล์ JSON เดียว แล้วอัปเดตครั้งเดียวด้วย `update-fields-batch` (ไม่ทำทีละเคส เหตุผลเดียวกับ Skill 06a):
   ```
   python3 scripts/qa_workbook.py update-fields-batch --path "<path>" --updates-json "<path>.json" --editor "qa-retest" --note "Retest หลัง Dev แจ้งแก้ไข <จำนวน> เคส (Pass=.. Fail=..)"
   ```
   อัปเดต `Status`, `Actual Result`, `Remarks` (ถ้ามี), และ **`Execution Date`** เป็นวันที่รัน Retest จริงวันนี้ (ทับวันที่รันครั้งก่อน — Workbook เก็บแค่ผลล่าสุด ส่วนประวัติเก่าดูได้จาก Document Control History ที่ `update-fields-batch` บันทึกไว้อัตโนมัติ)
2. **คอลัมน์ Test Photo**: กฎเดียวกับ Skill 06a — ใส่ path รูปเฉพาะเคสที่ผลยังเป็น **Fail** อยู่หลัง Retest เท่านั้น ถ้าเปลี่ยนเป็น Pass แล้วให้ลบค่าเดิมออกจากคอลัมน์นี้ (ไม่ต้องชี้ไปที่ภาพเก่าที่ไม่ตรงกับผลปัจจุบันแล้ว)
3. **ไม่ต้องแตะคอลัมน์ "Issue link" เลย** ในขั้นตอนนี้ (ไม่ว่าผลจะ Pass หรือยัง Fail อยู่ก็ตาม) — การคอมเมนต์กลับ Redmine หรือปิด Ticket เป็นหน้าที่ของ `qa-retest-closure` (Skill 10a ซึ่งสร้างเสร็จแล้ว) **Skill นี้จบแค่การรัน Test ซ้ำและบันทึกผลใน Workbook เท่านั้น ไม่แตะ Redmine เลยแม้แต่การอ่าน-เขียนใดๆ เพิ่มเติมนอกจากขั้นตอนที่ 2** — หลังจบ Skill นี้ให้แนะนำผู้ใช้ไปต่อที่ `qa-retest-closure` (10a) เพื่อ Recheck แล้วคอมเมนต์/ปิด Ticket จริง (ความสัมพันธ์ระหว่าง 10 กับ 10a เป็นแบบวนลูปได้ — ถ้า 10a คอมเมนต์แจ้ง Dev ว่ายัง Fail แล้ว Dev แก้ใหม่อีกรอบ ก็จะวนกลับมาเรียก Skill นี้ใหม่อีกครั้ง ดู SKILL.md ของ 10a สำหรับรายละเอียด)
4. อัปเดต `_pipeline-manifest.md`: ตั้งค่า Stage `10 qa-retest` เป็น:
   - `Complete` ถ้า Retest ครบทุกเคสใน `ready` (นับว่า Complete ได้แม้ผลจะยัง Fail อยู่บางเคส ตราบใดที่ได้ Retest จริงและบันทึกผลครบแล้ว)
   - `In Progress (รอ Dev แก้อยู่ N ใบ, Retest ไปแล้ว M ใบ)` ถ้ายังมีเคสใน `waiting` ค้างอยู่ — Skill นี้ไม่มีสถานะ "จบสมบูรณ์ตลอดกาล" เพราะ Ticket ใหม่จาก 09 หรือ Comment ใหม่จาก Dev อาจเข้ามาเพิ่มได้เรื่อยๆ
   - ถ้ามีเคสที่ Comment ไม่ชัดเจน (ขั้นตอนที่ 3 ข้อ 3) ค้างรอผู้ใช้ตัดสินใจ ให้ระบุจำนวนไว้ใน Notes ด้วย
5. แจ้งผู้ใช้สรุปผลให้ครบ: จำนวนที่ **Pass แล้ว** (บั๊กถูกแก้จริง), จำนวนที่ **ยัง Fail** (Dev แจ้งแก้แต่ปัญหายังอยู่ — ควรกลับไปแจ้ง Dev ต่อ), จำนวนที่ **ยังรอ Dev** (`waiting` จากขั้นตอนที่ 2), และจำนวนที่ **รอผู้ใช้ตัดสินใจ** (Comment กำกวม) แนะนำขั้นตอนถัดไปตามผล — ถ้ามีเคสที่ยัง Fail หลัง Retest แนะนำให้กลับไปที่ Ticket เดิมใน Redmine เพื่อแจ้ง Dev เพิ่ม (ยังไม่มี Skill ที่ทำส่วนคอมเมนต์กลับอัตโนมัติ ต้องทำเองก่อน หรือรอ Skill 10a)

## ข้อควรระวัง

- **ห้ามเก็บ/cache Redmine URL, API Key, หรือรายการ Status value ที่นับว่า "แก้เสร็จแล้ว" ไว้ข้ามรอบการรัน** ต้องถามผู้ใช้ใหม่ทุกครั้งเหมือน `redmine-logging` (09) ทุกประการ — ห้ามเขียนลง `_pipeline-manifest.md`, ไฟล์ log, หรือ commit message ใดๆ
- **Skill นี้ไม่คอมเมนต์กลับหรือปิด Ticket ใน Redmine เด็ดขาด** (ดูขั้นตอนที่ 6 ข้อ 3) — เป็นการตัดสินใจที่ผู้ใช้ยืนยันไว้ตอนออกแบบ Skill นี้เพื่อแยกไปทำใน Skill 10a ในอนาคต ถ้าถูกขอให้ทำส่วนนั้นระหว่างใช้ Skill นี้ ให้แจ้งว่ายังไม่ใช่ Scope ของ Skill 10 และเสนอให้สร้าง Skill 10a แยกแทนที่จะยัดเข้ามาใน Skill นี้
- **ห้ามเดา**ว่า Comment ของ Dev หมายถึงอะไรถ้าไม่ชัดเจนพอ (ดูขั้นตอนที่ 3 ข้อ 3) — ต้อง paste ข้อความจริงให้ผู้ใช้ดูแล้วถามตรงๆ เสมอ ผลของการตีความผิดคือ Retest ด้วยเงื่อนไขที่ไม่ตรงกับที่ Dev ตั้งใจแก้ ทำให้ผลลัพธ์ไม่น่าเชื่อถือ
- **เคสกรณี (B) ต้องแก้ทั้ง Workbook (คอลัมน์ Test Data) และไฟล์ `automation/<TC-ID>.py` พร้อมกันเสมอ** (ดูขั้นตอนที่ 4) ห้ามแก้แค่จุดเดียว — ผู้ใช้เตือนเรื่องนี้ไว้ตรงๆ ตอนออกแบบ Skill นี้ว่าเป็นความเสี่ยงหลักถ้าลืม
- **เคสกรณี (A) ห้ามแก้ไฟล์ script หรือ Workbook Test Data โดยไม่จำเป็น** — ใช้ของเดิมได้เลยตามที่ผู้ใช้ยืนยันไว้ (แก้เฉพาะกรณี B เท่านั้น)
- แยกแยะ Test Case Fail จริงกับ Script/Environment Error (Blocked) ให้ชัดเจนเหมือนกฎของ `qa-automation-script` (06a) ทุกประการ — Skill นี้ใช้ runner ตัวเดียวกันจึงมีพฤติกรรมเดียวกันโดยอัตโนมัติ ไม่ต้องเขียน logic แยกใหม่
- ถ้าเจอ error แบบ proxy/network block (403 Forbidden จากตัวกลาง ไม่ใช่จาก Redmine) ตอนเช็ค Ticket Status ในขั้นตอนที่ 2 ให้บอกผู้ใช้ตรงๆ ว่าน่าจะเป็นเพราะ network egress allowlist ของ environment ไม่ใช่ปัญหาที่ credential หรือ Redmine เอง (เหตุผลเดียวกับ Skill 09)
- **การเก็บ Screenshot เดิมไว้ก่อน Retest ทับ (ขั้นตอนที่ 5 ข้อ 1) เป็นการออกแบบเพื่อรักษา Audit Trail** ไม่ใช่ข้อบังคับจาก Redmine หรือ Workbook — ถ้าผู้ใช้ไม่ต้องการเก็บประวัติภาพเก่า (เช่น พื้นที่จำกัด) สามารถแจ้ง Claude ให้ข้ามขั้นตอนนี้ได้
- **ขอบเขต Browser ที่ Retest (ขั้นตอนที่ 5 ข้อ 2) ตั้ง default เป็นรันครบทุก Browser ใน Env & Config เพื่อความปลอดภัย** ไม่ใช่ข้อบังคับตายตัว — ถ้าผู้ใช้ต้องการจำกัดเฉพาะ Browser ที่เคย Fail เพื่อประหยัดเวลา สามารถแจ้งให้ปรับได้ในแต่ละรอบ ควรสอบถามความต้องการนี้กับผู้ใช้ตอนเริ่มขั้นตอนที่ 5 ถ้ายังไม่เคยตกลงกันไว้
