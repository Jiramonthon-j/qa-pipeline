# test-case-generator

Skill นี้เป็น**ขั้นตอนที่ 3 ที่บังคับ** ของ QA Pipeline และเป็น**หัวใจหลักของทั้งสาย Pipeline** หน้าที่คือ**ออกแบบ** Test Case เท่านั้น (ไม่รวมขั้นตอนการทดสอบจริง ซึ่งเป็นหน้าที่ของ `qa-automation-script` Skill 06a) โดยนำ QA Review Report จาก `requirement-review` (01) และ E2E Flow จาก `e2e-flow-designer` (02) มาวิเคราะห์ร่วมกันเพื่อออกแบบ Test Case ให้ครอบคลุมที่สุด

**สำคัญ**: คำสั่งในไฟล์นี้เขียนขึ้นให้ใช้ได้กับทั้ง Claude และ Gemini 3.6 ก็จริง แต่ Skill นี้ต่างจาก Skill ก่อนหน้าตรงที่ผลลัพธ์เป็นไฟล์ Excel (.xlsx) ที่มีการจัดรูปแบบ (สี, dropdown, กราฟ) ซึ่งต้องใช้สคริปต์ช่วยสร้างแทนการเขียนไฟล์ข้อความตรงๆ — ดูขั้นตอนที่ 4 ต้องใช้ environment ที่รันคำสั่ง/สคริปต์ได้ (เช่น Claude Code หรือ Gemini ผ่าน environment ที่มี code execution) จึงจะสร้างไฟล์ Excel จริงได้ ถ้า environment ที่ใช้งานอยู่รันโค้ดไม่ได้ ให้เตรียมเนื้อหา Test Case เป็นตารางแล้วแจ้งผู้ใช้ว่าต้องนำไปสร้างเป็น Excel ต่อเองหรือใช้ environment อื่นที่รันสคริปต์ได้

## ขั้นตอนที่ 1 — ระบุ Feature และตรวจสอบขั้นตอนก่อนหน้า

1. หาโฟลเดอร์รากของโปรเจค (Project Root) และโฟลเดอร์ Feature เหมือน Skill อื่นๆ ในสาย (fuzzy match ก่อนสร้างใหม่)
2. อ่านไฟล์ `_pipeline-manifest.md` ของ Feature นั้น
3. **เช็ค Gate**: Skill นี้ต้องรันต่อจาก `e2e-flow-designer` (Skill 02) เสมอ — ตรวจสอบสถานะ Stage `02 e2e-flow-designer` (ถ้าไม่มี manifest เลยก็ถือว่ายังไม่เสร็จเช่นกัน — **ห้ามสรุปเอาเองว่าหมายถึงตั้งใจข้าม ต้องถามผู้ใช้เสมอ**):
   - **ถ้า `Complete`**: ไปต่อขั้นตอนที่ 2 ตามปกติ
   - **ถ้า `Pending Review`** (ไฟล์ `02-e2e-flow.md` สร้างเสร็จแล้ว แต่ยังไม่มีใครกรอก `## QA Review & Sign-off` เป็น approved — ดู manifest): **นี่คือ Hard Block จริง ห้ามทำงานต่อไม่ว่ากรณีใด** และ**ห้ามเสนอทางเลือก standalone/ข้ามไปเลย** ในสถานการณ์นี้ (ต่างจากกรณีด้านล่าง) เพราะไฟล์ที่ต้องการมีอยู่แล้วจริง เพียงแต่ยังไม่ผ่านการอนุมัติเท่านั้น — ให้แจ้งผู้ใช้ตรงๆ ว่า Skill 02 เสร็จแล้วแต่ยังไม่ได้รับการอนุมัติ พร้อมบอกวิธีปลดล็อกชัดเจน: ไปเปิดไฟล์ `02-e2e-flow.md` อ่านทบทวน แล้วกรอก `## QA Review & Sign-off` เป็น **"การตัดสินใจ: approved"** เอง (คนต้องเป็นคนกรอก ไม่ใช่ AI) จากนั้นอัปเดต manifest ให้ Stage `02 e2e-flow-designer` เป็น `Complete` แล้วค่อยเรียก Skill นี้ใหม่อีกครั้ง — ถ้าผู้ใช้กรอกเป็น "rejected" หรือ "needs revision" แทน ให้แนะนำให้กลับไปแก้ `e2e-flow-designer` ใหม่ (ดู "การรันซ้ำ/อัปเดต E2E Flow เดิม" ใน Skill นั้น) ก่อนเรียก Skill นี้อีกครั้งเช่นกัน
   - **ถ้ายังไม่ `Complete` และไม่ใช่ `Pending Review`** (`Not Started`, `In Progress`, หรือไม่มี manifest เลย — คือยังไม่เคยรัน Skill 02 จนสร้างไฟล์เสร็จเลย): หยุดและถามผู้ใช้ว่า (a) ต้องการไปรัน `e2e-flow-designer` ให้เสร็จก่อนไหม (แนะนำ) หรือ (b) ต้องการใช้ Skill นี้แบบ standalone — ถ้าเลือก (b) ให้ขอทั้งไฟล์/เนื้อหา QA Review Report และ E2E Flow มาจากผู้ใช้โดยตรง (Skill นี้ต้องการทั้งสองอย่างเสมอ ไม่ใช่แค่อย่างใดอย่างหนึ่ง) แล้วถ้ายังไม่มี manifest ให้สร้างใหม่พร้อมตั้ง Stage ก่อนหน้าที่ถูกข้ามเป็น `Skipped` หลังผู้ใช้ยืนยันแล้ว
   - **ข้อสำคัญที่ต้องแยกให้ออก**: Hard Block ข้างต้นใช้เฉพาะกรณี "รัน Skill 02 ผ่าน Pipeline นี้แล้ว แต่ยังไม่อนุมัติ" (`Pending Review`) เท่านั้น — ถ้าผู้ใช้ไม่เคยรัน Skill 02 เลยและต้องการเรียก `test-case-generator` แบบเดี่ยวๆ ทันที (ทางเลือก b ด้านบน) ยังคงทำได้เสมอ **ไม่ถูกบล็อก** เพราะ Skill นี้ยังคงต้องใช้งานอิสระได้เหมือนเดิม การเพิ่ม Hard Block ครั้งนี้มีไว้ป้องกันเฉพาะกรณี "มีไฟล์อยู่แล้วแต่ยังไม่ได้ตรวจ" ไม่ได้มีไว้บังคับว่าต้องผ่าน Skill 02 ทุกครั้ง

## ขั้นตอนที่ 2 — อ่านอินพุต

1. อ่านไฟล์ `01-requirement-review.md` และ `02-e2e-flow.md` อย่างละเอียดครบทุก Flow และทุก Business Rule (หรือเนื้อหาที่ผู้ใช้ให้มาแทนถ้าเป็นกรณี standalone)
2. Skill นี้สร้าง Test Case Workbook เป็น **Excel (.xlsx) เสมอ** ผ่านสคริปต์ `qa_workbook.py` ที่แนบมาด้วย (ดูขั้นตอนที่ 4) — ใช้งานได้ทันทีไม่ต้องตั้งค่าอะไรเพิ่ม ไม่ต้องถามผู้ใช้ว่าจะเลือกรูปแบบไหน (ตัดสินใจไว้แล้วว่าไม่รองรับ Google Sheet เพื่อไม่ต้องพึ่ง Google Cloud Service Account credentials และให้ทุก Skill ในสาย pipeline อ่าน/เขียน Workbook ด้วยเครื่องมือเดียวกันเสมอ) — ถ้าผู้ใช้ต้องการดู/แชร์ผ่าน Google Sheets ในภายหลัง สามารถ Upload ไฟล์ .xlsx ที่ได้เข้า Google Drive แล้วเปิดด้วย Google Sheets ได้เองทันทีนอกสาย Pipeline นี้ ไม่ต้องมีขั้นตอนพิเศษอะไรมารองรับ

## ขั้นตอนที่ 3 — ออกแบบ Test Case

วิเคราะห์ทุก Flow ใน `02-e2e-flow.md` (รวมทั้ง Steps, Alternate/Error Paths) และทุก Business Rule ใน `01-requirement-review.md` แล้วออกแบบ Test Case ให้ครอบคลุม — อย่างน้อยต้องมี:
- Test Case สำหรับ**เส้นทางหลัก (happy path)** ของทุก Flow อย่างน้อย 1 เคสต่อ Flow
- Test Case สำหรับ**ทุก Alternate/Error Path** ที่ระบุไว้ใน E2E Flow
- Test Case ที่ครอบคลุม**ทุก Business Rule** ที่ระบุไว้ใน Requirement Review (ใช้ตรวจสอบผ่านชีต Requirement Matrix — ดูขั้นตอนที่ 4)
- Test Case เพิ่มเติมสำหรับ **edge case** ที่มองเห็นได้แม้ไม่ได้เขียนตรงๆ ใน Flow (เช่น ค่าขอบเขต, ค่าว่าง, ค่าที่ยาว/สั้นผิดปกติ)
- ถ้า Flow หรือ Business Rule ใดยังมี Open Question ที่ยังไม่ชัดเจน (carried forward มาจาก Skill 01/02) **ให้ยังคงออกแบบ Test Case ไปตามสมมติฐานที่สมเหตุสมผลที่สุดก่อน** แล้วระบุไว้ในคอลัมน์ `Remarks` ว่าอ้างอิงสมมติฐานอะไร เพื่อให้ปรับแก้ง่ายภายหลังเมื่อได้คำตอบที่ชัดเจน — **ห้ามข้าม Flow นั้นไปเฉยๆ**

**คุณภาพของคอลัมน์ `Remarks`**: เขียนโดยอ้างอิง ID ที่เจาะจงเสมอ (เช่น `BR-002`, `AC-003`, `REQ-F-005`, `FLOW-2`, `DP-1`, `RISK-3` — ดูความหมายแต่ละแบบในชีต Glossary) แทนคำอธิบายกว้างๆ ที่ไม่ชี้เฉพาะ (เช่น "อ้างอิงจาก requirement" หรือ "ตามที่ระบุไว้") เพราะ Remarks คือจุดเดียวที่คนอ่าน Workbook ทีหลัง (หรือ Skill `coverage-review`/`risk-analysis` ที่ทำงานต่อ) จะสืบย้อนกลับไปหาที่มาของ Test Case แต่ละเคสได้ — ถ้าเขียนกว้างเกินไปจะไล่ตรวจสอบไม่ได้ว่าเคสนี้มาจากข้อไหนจริงๆ กันแน่

**Test Case ID**: ใช้รูปแบบ `TC-<เลข 3 หลัก>` เรียงลำดับต่อเนื่องภายใน Feature เดียวกัน (เช่น TC-001, TC-002, ...) ไม่ต้องมี prefix ตาม Module เพิ่มเติม — ผูกกับ Feature เดียวเท่านั้น (ตาม Single-Feature-at-a-time operating model ของ Pipeline นี้) ถ้า Feature นี้เคยมี Test Case อยู่แล้ว (เช่นตอนสร้างซ้ำ หรือระหว่าง loop กับ `coverage-review`) ให้เรียงเลขต่อจากตัวสุดท้ายที่มีอยู่ ไม่ใช่เริ่มนับใหม่จาก 001

**Priority column**: ปล่อยว่างไว้เสมอในขั้นตอนนี้ (Skill `risk-analysis` (05) จะเป็นผู้กำหนดค่านี้ทีหลัง)

**Status column**: ตั้งเป็น `not start` เสมอตอนสร้างใหม่ ตัวเลือกทั้งหมดที่ใช้ได้คือ `not start`, `Pass`, `Fail`, `Blocked`, `Rejected / Not a Bug` — ค่า `Blocked` มีไว้ให้ `qa-automation-script` (06a) ใช้แยกกรณีสคริปต์ automation เอง error/crash (เช่น หา element ไม่เจอ, timeout, environment ล่ม) ออกจากกรณี Test Case Fail จริง (บั๊กจริง) เพื่อไม่ให้ปนกันตอนนับผลสรุปที่ Skill 08

## ขั้นตอนที่ 4 — สร้างไฟล์ Workbook (กรณีเลือก Excel)

ใช้สคริปต์ `scripts/qa_workbook.py` ที่แนบมากับ Skill นี้ (เขียนด้วย Python, ใช้ไลบรารี `openpyxl`) ทำตามลำดับนี้:

**หมายเหตุโครงสร้าง**: `scripts/qa_workbook.py` ของ Skill นี้เป็นแค่ stub บาง ๆ ที่โหลดฉบับจริงจาก `qa-pipeline-skills/_shared/qa_workbook.py` มารันให้อัตโนมัติ (คำสั่งใช้งานเหมือนเดิมทุกอย่าง ไม่กระทบผู้ใช้) — Skill อีก 4 ตัวในสาย (`qa-automation-script`, `coverage-review`, `test-data-generator`, `risk-analysis`) ใช้ไฟล์จริงตัวเดียวกันนี้ร่วมกัน ถ้าต้องแก้ logic ของสคริปต์ (เช่นแก้บั๊ก/เพิ่มคำสั่งใหม่) **ให้แก้ที่ `_shared/qa_workbook.py` ที่เดียวเท่านั้น** ห้ามแก้ที่ stub เพราะจะไม่มีผลอะไรเลย

1. **ถ้ายังไม่เคยมีไฟล์ Workbook สำหรับ Feature นี้**: สร้างไฟล์ใหม่ด้วยคำสั่ง
   ```
   python3 scripts/qa_workbook.py create --feature "<ชื่อ Feature>" --out "<โฟลเดอร์ Feature>/03-test-case-workbook.xlsx"
   ```
   คำสั่งนี้จะสร้างครบทั้ง 7 ชีตตามลำดับ: Executive Dashboard (มีกราฟ Pie/Bar อ้างอิงสูตรจากชีต Test Case อัตโนมัติ), Document Control (Version เริ่มที่ 1), Requirement Matrix, Env & Config, Priority & Risk Matrix (มีนิยาม P0–P3 พร้อมสีกำกับ), Glossary, Test Case (มี dropdown สีสำหรับ Test Type/Priority/Status พร้อมแล้ว) — ทุกชีตจัดฟอร์แมต (สี/กรอบ/wrap/ความสูงแถว) ให้เสร็จสมบูรณ์แล้วในตัว ไม่ต้องแต่งเพิ่ม

2. **เติมเนื้อหาชีต Requirement Matrix**: header อยู่แถว 1 เสมอ **ไม่มีแถวว่างคั่นหลังแถว 1** — ข้อมูลแถวแรกเริ่มที่แถว 2 ทันที เพิ่มแถวสำหรับทุก Business Rule จาก `01-requirement-review.md` และทุก Flow จาก `02-e2e-flow.md` ในคอลัมน์ "Requirement / Business Rule ID" และ "รายละเอียด" (คอลัมน์ "Test Case ID ที่ครอบคลุม" จะเติมพร้อมกับขั้นตอนที่ 3 หลังออกแบบ Test Case เสร็จ) — คอลัมน์ E เป็นช่องไฟบางๆ (เว้นว่างไว้เสมอ ห้ามเติมข้อมูล) และคอลัมน์ F แถว 2 มีข้อความหมายเหตุสีแดง `*...*` อธิบายชีตนี้อยู่แล้วอัตโนมัติจากคำสั่ง `create` (อยู่ข้างขวาของตาราง บรรทัดเดียวกับแถวข้อมูลแถวแรก) — **ไม่ต้องลบ ไม่ต้องย้าย** เขียนทับแทนที่ได้เฉพาะเมื่อต้องการเปลี่ยนเนื้อหาหมายเหตุจริงๆ เท่านั้น — **ห้ามปล่อยชีตนี้ว่างเปล่า/มีแค่ข้อความ placeholder เดิมโดยเด็ดขาด แม้ในกรณี standalone**: ถ้า `01-requirement-review.md` ไม่มีอยู่จริง (เข้าสาย pipeline แบบ standalone ตั้งแต่ Skill 02 ไม่ผ่าน Skill 01) ให้เติมเฉพาะแถว Flow จาก `02-e2e-flow.md` เข้าไปแทน (ข้ามส่วน Business Rule ID ไป ไม่ต้องคิด ID ปลอมขึ้นมาเอง) แล้วต่อท้ายข้อความหมายเหตุสีแดงที่คอลัมน์ F แถว 2 (ในเครื่องหมาย `*...*` เดิม) ด้วยประโยคว่า "Feature นี้เข้าสาย pipeline แบบ standalone ไม่ผ่าน requirement-review (01) จึงไม่มี Business Rule ID อย่างเป็นทางการ — ใช้ Flow จาก 02-e2e-flow.md แทน" เพื่อให้ Skill ถัดไปในสาย (โดยเฉพาะ `qa-reconcile` (RTM)) เข้าใจสถานะของชีตนี้ทันทีโดยไม่ต้องเดา (พบเป็นบั๊กจริงระหว่างทดสอบ RTM ที่ชีตนี้ถูกปล่อยว่างเป็น placeholder ไปเฉยๆ ในกรณี standalone — ดู BUG-13 ใน Test Report ของรอบ Skill 07/RTM/08)

3. **เติมเนื้อหาชีต Env & Config**: ถามผู้ใช้ถึง Environment/URL/Account/Browser/Device ที่ต้องเทส (ถ้ามีข้อมูลนี้อยู่แล้วใน `00-test-plan.md` ให้หยิบมาใช้ก่อน แล้วถามผู้ใช้แค่ยืนยัน/เพิ่มเติม)

   ขั้นตอนที่ 2 และ 3 ทั้งสองข้อนี้เป็นการเติมเซลล์ด้วยมือตรงๆ ผ่าน openpyxl (ไม่มีคำสั่ง CLI เฉพาะให้) — **หลังเติมเสร็จทั้งสองชีตแล้วต้องรันคำสั่งนี้เสมอ 1 ครั้งก่อนไปต่อขั้นตอนที่ 4**:
   ```
   python3 scripts/qa_workbook.py finalize-layout --path "<path Workbook>"
   ```
   เพื่อให้แถวที่เพิ่งเติมได้ wrap/border/ความสูงแถวที่คำนวณจากเนื้อหาจริง และ normalize เครื่องหมาย `'` เดี่ยวในข้อความเป็น `"` คู่ให้ครบเหมือนแถวที่มาจาก `add-cases`/`update-field` (คำสั่งสองตัวนั้น เรียก finalize ให้อัตโนมัติอยู่แล้ว จึงไม่ต้องเรียกซ้ำหลังใช้มัน — เรียกเองก็ต่อเมื่อแก้เซลล์ตรงๆ แบบนี้เท่านั้น)

4. **เพิ่ม Test Case ที่ออกแบบไว้**: เตรียมข้อมูล Test Case เป็นไฟล์ JSON (list ของ object โดยแต่ละ key ตรงกับชื่อคอลัมน์ทั้ง 17 คอลัมน์ — ดูตัวอย่างรูปแบบใน docstring ของสคริปต์) แล้วรัน
   ```
   python3 scripts/qa_workbook.py add-cases --path "<path Workbook>" --cases-json "<path .json>" --editor "test-case-generator" --note "<สรุปสั้นๆ ว่าเพิ่มอะไร>"
   ```
   คำสั่งนี้จะเพิ่มแถวต่อจากแถวสุดท้ายที่มีอยู่ ใส่สีตาม Test Type/Priority/Status อัตโนมัติ จัดฟอร์แมต (wrap/border/ความสูงแถว/normalize เครื่องหมายคำพูด) ให้ครบ **และ bump Version ของ Document Control ขึ้น 1 พร้อมบันทึก 1 บรรทัดใน History โดยอัตโนมัติ** — ไม่ต้องทำเองแยกต่างหาก เขียน Test Step แบบ "1) ... 2) ... 3) ..." และ Test Data แบบ "key1=val1, key2=val2" ตามปกติได้เลย สคริปต์จะแยกขึ้นบรรทัดใหม่ให้เองอัตโนมัติ ไม่ต้องใส่ line break เอง

5. ตรวจสอบว่าทุก Business Rule/Flow ในชีต Requirement Matrix มี Test Case ID อ้างอิงอย่างน้อย 1 รายการ ถ้ายังไม่มีให้กลับไปออกแบบเพิ่มก่อนบันทึกจบ

## ขั้นตอนที่ 5 — บันทึกและอัปเดต Manifest

1. ไฟล์ Workbook จะถูกบันทึกที่ `<โฟลเดอร์ Feature>/03-test-case-workbook.xlsx` โดยอัตโนมัติจากขั้นตอนที่ 4
2. อัปเดตไฟล์ `_pipeline-manifest.md`: ตั้งค่า Stage `03 test-case-generator` เป็น `Complete`, ใส่ path ของไฟล์ output, ใส่วันที่เสร็จ
3. แจ้งผู้ใช้ว่าเสร็จแล้ว สรุปจำนวน Test Case ที่สร้าง แยกตาม Test Type และ Version ปัจจุบันของ Document Control แล้วแนะนำให้ไปต่อที่ `coverage-review` (Skill 04) เพื่อตรวจสอบความครอบคลุม

## ข้อควรระวัง

- ห้ามข้ามขั้นตอนสร้าง Test Case สำหรับ Alternate/Error Path ใน E2E Flow แม้จะดูเป็นกรณีเล็กน้อย — เป้าหมายของ Skill นี้คือให้ Test Case ครอบคลุมที่สุดเท่าที่ข้อมูลที่มีจะรองรับได้
- ถ้า manifest ระบุว่า `e2e-flow-designer` สถานะ `In Progress` ห้ามอ่านไฟล์มาใช้ทันทีเหมือนเป็นข้อมูลสมบูรณ์ ให้เตือนผู้ใช้ก่อนเหมือน Skill ก่อนหน้า
- Skill นี้ ↔ `coverage-review` (04) เป็นคู่ loop กัน วนได้ไม่จำกัดจำนวนครั้งจนกว่าผู้ใช้จะพอใจกับความครอบคลุมของ Test Case — ทุกครั้งที่ Skill นี้ถูกเรียกซ้ำเพื่อ**เพิ่ม/แก้ไข**ระหว่าง loop นี้ ต้องใช้คำสั่ง `add-cases` หรือ `update-field` ของสคริปต์เสมอ (ไม่ใช่แก้ไฟล์ Excel ด้วยมือ) เพื่อให้ Version bump ถูกต้องอัตโนมัติทุกครั้ง
- ห้ามลบ/เขียนทับ Test Case เดิมที่ผู้ใช้อาจไปแก้ไขเองด้วยมือหลังจาก Skill นี้ทำงานไปแล้ว — ก่อนเพิ่ม Test Case ใหม่ในรอบถัดไป ต้อง **อ่าน Workbook ฉบับล่าสุดก่อนเสมอ** ด้วยคำสั่ง `read-cases` เพื่อดูว่ามีอะไรอยู่แล้วบ้าง แล้วค่อยตัดสินใจว่าจะเพิ่มอะไรเพิ่ม (Test Case ID ใหม่ต้องต่อจากตัวสุดท้ายที่มีอยู่จริง ไม่ใช่ต่อจากที่ Skill นี้จำไว้เองจากรอบก่อน)
- **เครื่องหมายคำพูดในข้อความ**: เขียนตามธรรมชาติได้เลย ไม่ต้องกังวลเรื่อง `'` เดี่ยว vs `"` คู่ — `add-cases`/`update-field`/`finalize-layout` normalize ให้เป็น `"` คู่ทั้งหมดอัตโนมัติทุกครั้งที่บันทึกไฟล์อยู่แล้ว (ยกเว้นในสูตร Excel ที่อ้างอิงชื่อชีต เช่น `'Test Case'!A2:A100000` ซึ่งต้องเป็น `'` เดี่ยวตาม syntax ของ Excel เอง — สคริปต์แยกแยะจุดนี้ให้แล้ว ไม่ไปแตะสูตร)
- ถ้าเผลอแก้ไฟล์ Workbook ด้วยมือผ่าน openpyxl ตรงๆ (ไม่ผ่านคำสั่งของสคริปต์เลย ไม่ว่าเหตุผลอะไรก็ตาม) ให้รัน `python3 scripts/qa_workbook.py finalize-layout --path "<path>"` เป็นขั้นตอนสุดท้ายเสมอ ก่อนแจ้งผู้ใช้ว่าทำงานเสร็จ — ไม่งั้นแถวที่เพิ่ง/แก้ใหม่จะไม่มี wrap/border/ความสูงแถวที่ถูกต้อง ซึ่งจะมองไม่เห็นตอนเปิดดูผ่าน PDF/LibreOffice preview แต่จะเห็นชัดเจนเป็นข้อความถูกตัดทิ้งเวลาเปิดใน Excel จริง
