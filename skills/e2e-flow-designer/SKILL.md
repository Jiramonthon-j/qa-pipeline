# e2e-flow-designer

Skill นี้เป็น**ขั้นตอนที่ 2 ที่บังคับ** ของ QA Pipeline หน้าที่คือนำ Flow การใช้งานหลักที่สรุปไว้แบบสั้นๆ ใน QA Review Report (จาก `requirement-review`) มาแตกละเอียดเป็น End-to-End Flow ทีละขั้นตอน ครอบคลุมทั้งเส้นทางหลัก (happy path), เส้นทางสำรอง, และเส้นทาง error ผลลัพธ์ของ Skill นี้คืออินพุตหลักที่ `test-case-generator` (Skill 03) จะใช้ออกแบบ Test Case ต่อ ดังนั้นยิ่งแตก Flow ละเอียดและครบเท่าไหร่ Test Case ที่ได้ก็จะครอบคลุมมากขึ้นเท่านั้น

**สำคัญ**: คำสั่งในไฟล์นี้เขียนขึ้นให้ใช้ได้กับทั้ง Claude และ Gemini 3.6 — ห้ามอ้างอิงชื่อ tool เฉพาะของแพลตฟอร์มใดแพลตฟอร์มหนึ่ง ให้อธิบายเป็นขั้นตอนที่โมเดลไหนก็ทำตามได้

## ขั้นตอนที่ 1 — ระบุ Feature และตรวจสอบขั้นตอนก่อนหน้า

1. **หาโฟลเดอร์รากของโปรเจค (Project Root)**: ถ้ายังไม่ทราบตำแหน่งโฟลเดอร์ "QA Pipeline Project" ให้ถามผู้ใช้ก่อน
2. ถามผู้ใช้ว่ากำลังออกแบบ E2E Flow ให้ Feature ชื่ออะไร แล้วหาโฟลเดอร์ Feature นั้นใต้ Project Root (ใช้การเทียบแบบไม่สนตัวพิมพ์เล็ก/ใหญ่และช่องว่างส่วนเกินเหมือน Skill อื่นๆ ถ้าไม่พบให้ถามผู้ใช้ยืนยันก่อนสร้างใหม่)
3. อ่านไฟล์ `_pipeline-manifest.md` ของ Feature นั้น
4. **เช็ค Gate**: Skill นี้เป็น Skill บังคับที่ต้องรันต่อจาก `requirement-review` (Skill 01) เสมอ — ตรวจสอบสถานะ Stage `01 requirement-review` ใน manifest (ถ้ายังไม่มีไฟล์ manifest เลย ให้ถือว่าสถานะเป็น "ยังไม่เสร็จ" เช่นกัน — **ห้ามสรุปเอาเองว่าการไม่มี manifest แปลว่าผู้ใช้ตั้งใจข้าม Skill 01 มา** เพราะผู้ใช้อาจแค่ไม่รู้ว่าต้องรัน Skill 01 ก่อน ต้องถามให้ชัดเสมอไม่ว่ากรณีไหน):
   - **ถ้า `Complete`**: ไปต่อขั้นตอนที่ 2 ตามปกติ
   - **ถ้า `Pending Review`** (ไฟล์ `01-requirement-review.md` สร้างเสร็จแล้ว แต่ยังไม่มีใครกรอก `## 20. QA Review & Sign-off` เป็น approved — ดู manifest): **นี่คือ Hard Block จริง ห้ามทำงานต่อไม่ว่ากรณีใด** และ**ห้ามเสนอทางเลือก standalone/ข้ามไปเลย** ในสถานการณ์นี้ (ต่างจากกรณีด้านล่าง) เพราะไฟล์ที่ต้องการมีอยู่แล้วจริง เพียงแต่ยังไม่ผ่านการอนุมัติเท่านั้น — ให้แจ้งผู้ใช้ตรงๆ ว่า Skill 01 เสร็จแล้วแต่ยังไม่ได้รับการอนุมัติ พร้อมบอกวิธีปลดล็อกชัดเจน: ไปเปิดไฟล์ `01-requirement-review.md` อ่านทบทวน แล้วกรอก `## 20. QA Review & Sign-off` เป็น **"การตัดสินใจ: approved"** เอง (คนต้องเป็นคนกรอก ไม่ใช่ AI) จากนั้นอัปเดต manifest ให้ Stage `01 requirement-review` เป็น `Complete` แล้วค่อยเรียก Skill นี้ใหม่อีกครั้ง — ถ้าผู้ใช้กรอกเป็น "rejected" หรือ "needs revision" แทน ให้แนะนำให้กลับไปแก้ `requirement-review` ใหม่ (ดู "การรันซ้ำ" ใน Skill นั้น) ก่อนเรียก Skill นี้อีกครั้งเช่นกัน
   - **ถ้ายังไม่ `Complete` และไม่ใช่ `Pending Review`** (`Not Started`, `In Progress`, หรือไม่มี manifest เลย — คือยังไม่เคยรัน Skill 01 จนสร้างไฟล์เสร็จเลย): **ห้ามดำเนินการต่อแบบเงียบๆ** ให้แจ้งผู้ใช้ว่า Skill 01 ยังไม่เสร็จ แล้ว**ถามผู้ใช้ก่อนเสมอ**ว่า:
     - (a) ต้องการไปรัน `requirement-review` ให้เสร็จก่อนไหม (แนะนำ) หรือ
     - (b) ต้องการใช้ `e2e-flow-designer` แบบ **standalone** (ข้ามขั้นตอนก่อนหน้าไปเลยโดยตั้งใจ — เช่น มี QA Review Report จากที่อื่นอยู่แล้ว หรือไม่ต้องการใช้ Pipeline นี้ตั้งแต่ Skill 01) — ถ้าเลือกแบบนี้ ให้ถามผู้ใช้ขอไฟล์/เนื้อหา QA Review Report มาให้ตรงๆ แทน (ผู้ใช้อาจมีอยู่แล้วจากที่อื่น หรือพิมพ์สรุปมาให้เอง) แล้วเดินหน้าต่อโดยใช้เนื้อหานั้นแทนไฟล์ `01-requirement-review.md`
   - ถ้าผู้ใช้เลือก (b) และยังไม่มีไฟล์ manifest เลย ให้สร้าง manifest ใหม่ (โครงสร้างเดียวกับ `source-ingest`) และตั้ง Stage `00-pre`, `00`, `01` เป็น `Skipped` ทั้งหมด **หลังจาก**ผู้ใช้ยืนยันแล้วเท่านั้น ไม่ใช่ก่อนถาม
   - **ข้อสำคัญที่ต้องแยกให้ออก**: Hard Block ข้างต้นใช้เฉพาะกรณี "รัน Skill 01 ผ่าน Pipeline นี้แล้ว แต่ยังไม่อนุมัติ" (`Pending Review`) เท่านั้น — ถ้าผู้ใช้ไม่เคยรัน Skill 01 เลยและต้องการเรียก `e2e-flow-designer` แบบเดี่ยวๆ ทันที (ทางเลือก b ด้านบน) ยังคงทำได้เสมอ **ไม่ถูกบล็อก** เพราะ Skill นี้ยังคงต้องใช้งานอิสระได้เหมือนเดิม การเพิ่ม Hard Block ครั้งนี้มีไว้ป้องกันเฉพาะกรณี "มีไฟล์อยู่แล้วแต่ยังไม่ได้ตรวจ" ไม่ได้มีไว้บังคับว่าต้องผ่าน Skill 01 ทุกครั้ง

## ขั้นตอนที่ 2 — อ่านอินพุต

อ่านไฟล์ `01-requirement-review.md` (หรือเนื้อหาที่ผู้ใช้ให้มาแทนถ้าเป็นกรณี standalone) อย่างละเอียด โดยเฉพาะ (เลขข้ออ้างอิงตาม Format ปัจจุบันของ `requirement-review` — 20 หัวข้อ):
- **User Flow** (ข้อ 9) — นี่คือจุดเริ่มต้นหลักที่ต้องเอามาแตกละเอียดต่อ
- **Functional Requirements** (ข้อ 5) และ **Business Rules & Validation Rules** (ข้อ 7) — ใช้ตรวจว่า Flow ที่แตกออกมาสอดคล้องกับกฎที่ระบุไว้ครบ และใช้เป็น ID อ้างอิงกลับ (REQ-F-xxx / BR-xxx) ในทุก Flow/Step ที่เขียนออกมา (ดูขั้นตอนที่ 4)
- **Non-Functional Requirements** (ข้อ 6) — โดยเฉพาะข้อที่เป็น cross-cutting (เช่น Accessibility, Performance ทั่วไป) ที่ไม่ได้ผูกกับ Flow ใดโดยเฉพาะ ต้องรู้ไว้ตั้งแต่ตอนนี้เพื่อไม่ให้หายไปตอนทำ Coverage (ดูขั้นตอนที่ 4)
- **User Roles & Permissions** (ข้อ 8)
- **Draft Acceptance Criteria** (ข้อ 17) — ใช้เป็นตัวอ้างอิง AC-xxx คู่กับ REQ-F-xxx ในทุก Flow/Step และตาราง Coverage
- **Open Questions** (ข้อ 15) และ **Risks** (ข้อ 16) — จุดไหนที่ยังไม่ชัดเจนและกระทบ Flow ใด ต้องติดตามมาด้วย (ดูขั้นตอนที่ 4)

ถ้าไฟล์ต้นทางเป็น Format เก่าที่ไม่มี ID กำกับ (REQ-F-xxx/BR-xxx/AC-xxx) — เช่นกรณี standalone ที่ผู้ใช้ส่งเนื้อหามาเองจากแหล่งอื่น — ให้ใช้การอ้างอิงแบบ "Business Rule ข้อ N" / "User Flow ข้อ N" แทน ID ตลอดทั้งไฟล์ผลลัพธ์ในขั้นตอนที่ 4 (คงรูปแบบเดียวกันทั้งไฟล์ ห้ามปนกันครึ่งๆ กลางๆ) พร้อมระบุไว้ในตาราง "สรุปสำหรับ QA" ว่าใช้การอ้างอิงแบบไม่มี ID เพราะเหตุใด

## ขั้นตอนที่ 3 — แตก Flow ให้ละเอียด

สำหรับ**แต่ละ User Flow** ที่พบใน Requirement Review ให้แตกออกเป็นรายละเอียดตามโครงสร้างนี้ — อย่ามองข้าม Flow ย่อยที่อาจไม่ได้เขียนตรงๆ ใน Requirement แต่อนุมานได้จาก Business Rules (เช่น "ถ้ากรอกผิดจะเกิดอะไรขึ้น" แม้ Requirement จะพูดถึงแค่เส้นทางที่ถูกต้อง):

- **Flow ID / ชื่อ Flow**: ตั้งชื่อสั้นๆ ให้จำง่าย
- **Actor**: ใครเป็นผู้ทำ Flow นี้
- **Trigger**: อะไรเป็นจุดเริ่มต้นของ Flow นี้
- **Pre-conditions**: ต้องมีเงื่อนไขอะไรพร้อมก่อน Flow นี้จะเริ่มได้
- **Steps**: แตกเป็นขั้นตอนย่อยเรียงลำดับ (1, 2, 3, ...) ระบุทั้ง action ของผู้ใช้และ response ของระบบในแต่ละ step — **ถ้า Flow เดียวกันมีเส้นทางย่อยที่แยกออกจากกันตั้งแต่ต้น** (Actor/Trigger/Pre-conditions เดียวกัน แต่ Steps แยกกันชัดเจนตามเงื่อนไขที่ผู้ใช้เลือกหรือข้อมูลที่ใส่เข้ามา เช่น "ไฟล์ผิดประเภท" กับ "ไฟล์ขนาดเกิน" ที่ต่างก็ทำให้ไฟล์ถูก reject แต่ด้วยเหตุผลคนละอย่าง) ให้แตกเป็น **"Steps (เส้นทางย่อย A — <ชื่อสั้นๆ>)"**, **"Steps (เส้นทางย่อย B — <ชื่อสั้นๆ>)"** ฯลฯ อยู่ภายใต้ Flow เดียวกัน แทนที่จะยัดรวมเป็น list เดียวที่มีเงื่อนไข "ถ้า...ถ้า..." ปนกัน หรือแยกเป็นคนละ Flow ทั้งที่จุดเริ่มต้นเดียวกัน — วิธีนี้ทำให้ทั้งคนอ่านและ `test-case-generator` เห็นชัดว่านี่คือสถานการณ์เดียวกันที่แตกสองทาง ไม่ใช่สองเรื่องที่ไม่เกี่ยวกัน
- **Post-condition / End State**: จบแล้วระบบอยู่ในสถานะไหน — ถ้า Flow มีเส้นทางย่อยและทุกเส้นทางจบที่สถานะเดียวกัน ให้เขียน Post-condition รวมครั้งเดียวพอ ถ้าจบต่างสถานะกันให้ระบุแยกตามเส้นทางย่อย
- **Alternate / Error Paths**: เส้นทางที่ไม่ใช่ happy path ทั้งหมดที่เป็นไปได้จาก Flow นี้ (เช่น input ผิด, timeout, ระบบภายนอกล่ม) — ต้องคิดให้ครบเท่าที่ Business Rules รองรับ
- **Related REQ-F / BR / AC**: อ้างอิงกลับไปยัง ID ใน Requirement Review ที่เกี่ยวข้องกับ Flow นี้เสมอ (REQ-F-xxx จาก Functional Requirements, BR-xxx จาก Business Rules, AC-xxx จาก Draft Acceptance Criteria) — ใส่ ID กำกับไว้ทั้งระดับ Flow และระดับ Step แต่ละอันเพื่อให้ตาราง Coverage ในขั้นตอนที่ 4 ตรวจสอบย้อนกลับได้จริง (ถ้าต้นทางไม่มี ID ให้ใช้ "Business Rule ข้อ N" / "User Flow ข้อ N" แทนตามที่ระบุในขั้นตอนที่ 2)
- **Decision Point**: ถ้า Flow มีจุดแตกแขนงตามเงื่อนไข (if/else ที่ผลลัพธ์ต่างกันจริง เช่น "ไฟล์ผ่าน validation หรือไม่") ให้ตั้งเป็น Decision Point แยกออกมา (DP-xxx) ระบุเงื่อนไขและผลลัพธ์ Yes/No ว่าไปต่อที่ Flow/Step ไหน — นี่คือตัวช่วยสำคัญให้ `test-case-generator` มองเห็น boundary/edge case ได้ตรงจุดโดยไม่ต้องเดาเอง
- **Carried-forward Open Questions**: ถ้า Open Questions หรือ Risks ข้อใดใน Requirement Review กระทบ Flow นี้โดยตรง ให้ระบุไว้ตรงนี้ด้วยเสมอ **ห้ามปล่อยให้หายไปเงียบๆ** — ให้ระบุด้วยว่ากระทบที่ step หรือ Decision Point ไหนโดยตรง (เช่น "กระทบ Flow นี้โดยตรงที่ step 5-6 และ DP-002") ไม่ใช่แค่บอกว่ากระทบเฉยๆ เพื่อให้สืบย้อนกลับไปแก้ Test Case ได้ตรงจุดทีหลัง — ทำแบบนี้กับ**ทุกข้อ**ใน Open Questions/Risks ของ Requirement Review ที่ยังไม่ปิด ไม่ใช่แค่ข้อที่เห็นชัดที่สุดข้อเดียว (จุดที่เคยพลาดระหว่างทดสอบ Format นี้คือหยิบมาแค่ 1 ใน 3 ข้อที่เกี่ยวข้องจริง)

  นอกจากนี้ การแตก Flow ละเอียดถึงระดับ step มักทำให้เจอช่องว่างที่**ไม่เคยถูกบันทึกไว้ใน Open Questions ของ Requirement Review เลย** (เพราะตอนนั้นยังมองแค่ภาพรวม Flow ไม่ได้ลงลึกถึง step) เช่น ไม่มีการระบุจำนวนครั้ง retry สูงสุด หรือไม่มี error message กำหนดไว้สำหรับกรณีล้มเหลวหนึ่งๆ — เจอแบบนี้ **ห้ามมองข้ามเพราะไม่ใช่ Open Question เดิม** ให้บันทึกไว้ในช่องนี้เช่นกัน แต่ต้องระบุให้ชัดว่าเป็น **"ข้อสังเกตใหม่"** (ไม่ใช่ carried-forward) พร้อมบอกว่าเจอระหว่างแตก Flow ไหน เพื่อให้ QA ตัดสินใจว่าจำเป็นต้องสอบถามทีมเพิ่มก่อนไปถึง Skill 03 หรือไม่ — ถ้าช่องว่างที่เจอนั้นใหญ่พอที่จะเป็นพฤติกรรมทั้งอัน (เช่น "ถ้าผู้ใช้ปิดหน้าเบราว์เซอร์ระหว่างรอผลกลางคัน จะเกิดอะไรขึ้น" ซึ่งไม่มี Flow ไหนครอบคลุมเลย) ให้เสนอเป็น Flow ใหม่ที่ยังไม่ยืนยัน (มีหมายเหตุกำกับว่ารอ confirm) แทนการฝังไว้แค่เป็นข้อความในช่องนี้เฉยๆ

- **Non-Functional Requirements แบบ cross-cutting**: REQ-NF-xxx บางข้อ (เช่น Accessibility, มาตรฐานความปลอดภัยทั่วไป) ใช้กับทุก Flow พร้อมกันโดยไม่มี trigger เฉพาะที่จะแตกเป็น Flow ของตัวเองได้ — **ห้ามตัดออกจากไฟล์ผลลัพธ์เงียบๆ** เพราะไม่มี Flow ให้ผูก ให้ระบุไว้ในตาราง Coverage ของขั้นตอนที่ 4 ด้วยเครื่องหมาย ⚠️ พร้อมหมายเหตุอธิบายเหตุผล เพื่อให้ `test-case-generator` (Skill 03) ออกแบบ Test Case แยกสำหรับข้อนี้โดยเฉพาะแทนที่จะมองว่าไม่มีการครอบคลุมเลย

## ขั้นตอนที่ 5 — บันทึกไฟล์และอัปเดต Manifest

1. บันทึกไฟล์ผลลัพธ์ที่ `<โฟลเดอร์ Feature>/02-e2e-flow.md`
2. อัปเดตไฟล์ `_pipeline-manifest.md`: ตั้งค่า Stage `02 e2e-flow-designer` เป็น **`Pending Review`** (ไม่ใช่ `Complete` — ดูเหตุผลที่ "การอัปเดตสถานะเป็น Complete หลัง Sign-off" ท้ายขั้นตอนนี้), ใส่ path ของไฟล์ output, ใส่วันที่เสร็จ

4. **(เพิ่มเติมเพื่อความสะดวกในการอ่าน — ไม่กระทบขั้นตอนอื่นในสาย pipeline)** สร้างไฟล์ Word (.docx) คู่กับไฟล์ .md ที่บันทึกไว้ในข้อ 1 โดยใช้ชื่อไฟล์เดียวกัน (เปลี่ยนแค่นามสกุล) เก็บไว้ในโฟลเดอร์เดียวกัน — รัน 4 คำสั่งนี้ตามลำดับ (Format นี้มีตารางเยอะ ต้องใส่กรอบและกันแถวแตกข้ามหน้าเหมือน `requirement-review`):
   ```
   pandoc "<path .md>" -f markdown+hard_line_breaks -o "<path .docx ชื่อเดียวกัน>" --standalone
   python3 "<path skill>/scripts/resize_table_columns.py" "<path .docx>"
   python3 "<path skill>/scripts/add_table_borders.py" "<path .docx>"
   python3 "<path skill>/scripts/fix_page_breaks.py" "<path .docx>"
   ```
   ขั้นแรกแปลง .md เป็น .docx ขั้นที่สอง**ปรับความกว้างคอลัมน์ของทุกตารางตามเนื้อหาจริง** (ยืนยันแล้วผ่าน Mockup — pandoc หารความกว้างเท่ากันทุกคอลัมน์โดย default ทำให้คอลัมน์ข้อความยาว เช่น "การกระทำ/ผลลัพธ์ของระบบ"/"System/API Touchpoint" ในตาราง Step ของแต่ละ Flow แคบเกินไปจน API path ถูกตัดกลางคำอ่านยาก — สคริปต์เดียวกับที่ใช้ใน `requirement-review` คำนวณความกว้างจากความยาวเนื้อหาจริงในแต่ละคอลัมน์ ไม่ได้ hardcode ตามชื่อหัวตาราง เพราะไฟล์นี้มีหลายตารางโครงสร้างต่างกัน) ขั้นที่สามใส่กรอบให้ทุกตาราง (สรุปสำหรับ QA, ภาพรวม Flow ทั้งหมด, ตาราง Step ของแต่ละ Flow, Decision Points, Coverage, Revision History) และกันแถวตารางแตกข้ามหน้า ขั้นที่สี่ป้องกันไม่ให้หัวข้อลอยเดี่ยวท้ายหน้าโดยเนื้อหาไปขึ้นหน้าถัดไป — ทั้งสามสคริปต์แก้เฉพาะไฟล์ `.docx` เท่านั้น ไม่แตะไฟล์ `.md` ต้นทาง ไฟล์ `.docx` นี้เป็นเพียง**สำเนาเพื่อความสะดวกในการอ่านเท่านั้น** — ไฟล์ `.md` ยังคงเป็นไฟล์หลัก (source of truth) ที่ Skill ถัดไปในสาย pipeline ใช้อ่านต่อเสมอ ไม่ใช่ `.docx` และไม่ต้องอัปเดตคอลัมน์ Output File ใน Manifest เพิ่มเติม (ยังอ้างอิงไฟล์ .md เหมือนเดิมตามข้อ 2) ถ้าเครื่องที่ใช้งานไม่มีคำสั่ง `pandoc` หรือ python พร้อม `python-docx` ติดตั้งไว้ ให้แจ้งผู้ใช้แล้วข้ามขั้นตอนที่ทำไม่ได้ไปได้เลย ไม่ถือเป็นตัวบล็อกการทำงานของ Skill นี้

### การอัปเดตสถานะเป็น Complete หลัง Sign-off

`Pending Review` แปลว่า "ไฟล์สร้างเสร็จแล้ว แต่ยังไม่มีใครรีวิว/อนุมัติ" — สถานะนี้จะเปลี่ยนเป็น `Complete` ได้ก็ต่อเมื่อผู้ใช้แจ้งกลับมาว่าได้เปิดไฟล์นี้รีวิวแล้ว และกรอก `## QA Review & Sign-off` ท้ายไฟล์เป็น **"การตัดสินใจ: approved"** เท่านั้น (ผู้ใช้ต้องเป็นคนกรอกเอง ห้าม AI กรอกแทนหรือเดาคำตอบ) เมื่อได้รับการยืนยันแบบนี้ ให้กลับมาอัปเดต `_pipeline-manifest.md` เปลี่ยน Stage `02 e2e-flow-designer` จาก `Pending Review` เป็น `Complete`

ถ้าผู้ใช้แจ้งว่ากรอกเป็น "rejected" หรือ "needs revision" ให้สถานะคงเป็น `Pending Review` ต่อไป (ไม่ใช่ Complete) จนกว่าจะแก้ไขและได้รับการอนุมัติใหม่ — การแก้ไขให้ทำตาม "การรันซ้ำ/อัปเดต E2E Flow เดิม" ด้านล่าง

**ข้อสำคัญ**: สถานะนี้ **ไม่ใช่แค่การรักษาความถูกต้องของ manifest เฉยๆ แบบที่ `requirement-review` เป็น** — `test-case-generator` (Skill 03) มีการเช็คสถานะนี้จริงและ **Hard Block** ไม่ให้ทำงานต่อถ้ายังเป็น `Pending Review` (ดูรายละเอียดที่ขั้นตอนที่ 1 ของ Skill นั้น) เหตุผลที่เข้มกว่า `requirement-review` เพราะ Skill 03 เป็น "หัวใจหลักของ Pipeline" ตามคำอธิบายของมันเอง — ถ้า Flow ที่ยังไม่ได้ตรวจถูกเอาไปสร้าง Test Case ทั้ง Workbook ต่อ ความเสี่ยงที่จะต้องทำซ้ำทั้งหมดสูงกว่าการปล่อยผ่านที่จุดอื่นๆ ของสาย

### การรันซ้ำ/อัปเดต E2E Flow เดิม

ถ้าผู้ใช้ขอแก้ไข E2E Flow ที่มีอยู่แล้ว (ไม่ใช่ทำฉบับใหม่ทั้งหมด — เช่น Requirement Review ต้นทางมีการแก้ไขหลัง Pipeline เดินหน้าไปแล้ว หรือพบว่า Flow ที่แตกไว้ไม่ครบ):

- เขียนทับไฟล์ `.md` เดิมด้วยเนื้อหาที่อัปเดตแล้วทั้งฉบับ (ไม่ใช่แค่แก้บางส่วน) เพื่อให้ไฟล์นี้เป็นภาพล่าสุดที่ครบถ้วนเสมอ
- เพิ่มแถวใหม่ต่อท้ายตาราง `## Revision History` เดิม (ห้ามลบแถวเก่า) — เลข Version เรียงต่อจากแถวล่าสุด (เช่น 1.0 → 1.1) ช่อง "สรุปการเปลี่ยนแปลง" เขียนสั้นๆ ตรงๆ ว่ารอบนี้แก้อะไร
- ทบทวนตาราง `## ตรวจสอบ Coverage` และ `## Open Questions` ใหม่ทั้งคู่ — Flow ที่เปลี่ยนอาจทำให้ Coverage เปลี่ยน หรือ Open Question บางข้อถูกปิดไปแล้ว/มีของใหม่เพิ่มมา
- `## QA Review & Sign-off` ให้เว้นว่างใหม่ทุกครั้งที่เขียนไฟล์ใหม่ทั้งฉบับ (checkbox ยังไม่ติ๊ก, Reviewer comment/การตัดสินใจยังว่าง) เพราะเนื้อหาเปลี่ยนไปจากรอบก่อน ต้องให้คนตรวจสอบใหม่เสมอ
- อัปเดต manifest ให้ Stage `02 e2e-flow-designer` กลับไปเป็น `Pending Review` เสมอ (แม้ก่อนรันซ้ำจะเคยเป็น `Complete` แล้วก็ตาม) เพราะเนื้อหาเปลี่ยนไปแล้ว ต้องรอการอนุมัติใหม่ — ถ้า `test-case-generator` เคยรันไปแล้วก่อนหน้านี้โดยอ้างอิง Flow ฉบับเก่า ให้แจ้งผู้ใช้ด้วยว่า Test Case ที่มีอยู่อาจต้องทบทวนใหม่เช่นกัน

## ข้อควรระวัง

- ห้ามเดาหรือแต่ง Flow ที่ไม่มีมูลจาก Requirement/Business Rules ที่ได้รับมา ถ้าไม่แน่ใจว่า Flow ใดควรมีจริงหรือไม่ ให้ถามผู้ใช้ก่อนแทนการเดาเอง
- ถ้า manifest ระบุว่า `requirement-review` มีสถานะ `In Progress` ห้ามอ่านไฟล์ output มาใช้ทันทีเหมือนเป็นข้อมูลที่สมบูรณ์แล้ว ให้แจ้งผู้ใช้ก่อนว่า Skill 01 ยังไม่เสร็จ แล้วถามว่าจะรอให้เสร็จก่อน หรือจะใช้ `e2e-flow-designer` แบบ standalone แทน
- ถ้าผู้ใช้แจ้งว่า Requirement มีการเปลี่ยนแปลงหลังจาก Pipeline เดินหน้าไปแล้ว การแก้ไขที่ถูกต้องคือรัน Pipeline ใหม่ทั้งหมดตั้งแต่ Skill 01 สำหรับ Feature นั้น (ตามกฎกลางของ Pipeline) ไม่ใช่แก้ไฟล์ E2E Flow นี้แบบเฉพาะจุด
- ตาราง Coverage (ขั้นตอนที่ 4) ต้องมีครบทุก REQ-F/REQ-NF/AC ระดับ Must/Should จริง — ห้ามตัด REQ-NF-xxx ออกทั้งหมดเพียงเพราะไม่มี Flow ให้ผูกตรงๆ (ดูวิธีจัดการ NFR แบบ cross-cutting ในขั้นตอนที่ 3)
- หัวข้อ Open Questions (ขั้นตอนที่ 4) ต้อง carried-forward มาจาก**ทุกข้อ**ที่ยังไม่ปิดใน Requirement Review ที่กระทบ Flow ในไฟล์นี้ ไม่ใช่แค่ข้อที่เด่นที่สุดข้อเดียว — ก่อนบันทึกไฟล์ให้ไล่ตรวจ Open Questions/Risks ทั้งหมดของ Requirement Review อีกรอบว่าครบหรือยัง
- ห้ามแนบเนื้อหา Requirement Review เต็มฉบับเข้ามาในไฟล์นี้ (เคยทดลองแล้วพบว่าทำให้อ่านยากขึ้นโดยไม่จำเป็น — ดูเหตุผลท้ายขั้นตอนที่ 4) ให้อ้างอิงกลับด้วย ID/เลขข้อผ่านตาราง "1. สรุปสำหรับ QA" แทน
- `## QA Review & Sign-off` ท้ายไฟล์คือช่องให้คน (QA/ผู้ตรวจสอบ) กรอกเอง — AI สร้างได้แค่โครง checkbox เปล่ากับหัวข้อ "Reviewer comment:" และ "การตัดสินใจ:" เท่านั้น **ห้ามเดา/เติมคำตอบลงไปเองเด็ดขาด** เพราะตอนนี้ผูกกับสถานะ `Pending Review` → `Complete` ที่ Skill 03 ใช้ Hard Block จริง การกรอกแทนจะทำให้ Skill 03 ทำงานทั้งที่ยังไม่ได้รับการตรวจสอบจริง
