# source-ingest

Skill นี้เป็น**ขั้นตอนแรกที่ไม่บังคับ (optional)** ของ QA Pipeline หน้าที่คือรวบรวม Requirement จากหลายแหล่งที่ผู้ใช้ส่งมา **พยายามดึงเนื้อหาจริงของแต่ละแหล่ง** เก็บสำเนาดิบแยกไว้ แล้วทำเป็น "สารบัญแหล่งข้อมูล" (catalog) ไฟล์เดียวที่บอกว่าแหล่งไหนดึงได้/ไม่ได้ อยู่ที่ไฟล์ไหน และมีช่องว่างอะไรที่ต้องรู้ก่อนไปขั้นถัดไป

**สำคัญ — ขอบเขตของ Skill นี้**: source-ingest มีหน้าที่รวบรวมแต่ละแหล่ง สรุปเนื้อหา ชี้จุดที่ขัดแย้ง/ซ้ำซ้อน แล้วร้อยเรียงเป็นภาพรวมท้ายไฟล์ให้อ่านจบแล้วเข้าใจฟีเจอร์ได้ — แต่ไม่ใช่หน้าที่ "ตัดสินว่าข้อมูลไหนถูก" หรือ "ฟันธงเลือกข้างเมื่อแหล่งขัดแย้งกัน" งานวิเคราะห์เชิงลึกแบบนั้น (ประเมินความเสี่ยง ตัดสินใจ scope สุดท้าย) ยังเป็นหน้าที่ของ `requirement-review` (ขั้น 01) อยู่เหมือนเดิม — ส่วน "สรุปภาพรวม (Synthesis)" ท้ายไฟล์เป็นการร้อยเรียงเนื้อหาให้อ่านง่ายขึ้นเท่านั้น ไม่ใช่การชี้ขาด จุดไหนที่แหล่งข้อมูลขัดแย้งกันหรือยังไม่มีคำตอบต้องคงไว้ตรงๆ ในย่อหน้านั้น (ทำตัวหนา) ห้ามเงียบแล้วเลือกข้างใดข้างหนึ่งเองเด็ดขาด

**สำคัญ**: คำสั่งในไฟล์นี้เขียนขึ้นให้ใช้ได้กับทั้ง Claude และ Gemini 3.6 — ห้ามอ้างอิงชื่อ tool เฉพาะของแพลตฟอร์มใดแพลตฟอร์มหนึ่ง ให้อธิบายเป็นขั้นตอนที่โมเดลไหนก็ทำตามได้ (อ่านไฟล์ / เขียนไฟล์ / ดึงเว็บด้วยเครื่องมือที่มีอยู่ในระบบที่ใช้งานอยู่ / ถามผู้ใช้)

## ขั้นตอนที่ 1 — ระบุ Feature และโฟลเดอร์โปรเจค

QA Pipeline นี้ทำงานทีละ 1 Feature เท่านั้น (ห้ามรันคู่ขนานหลาย Feature พร้อมกัน) ทุก output ของทุก Skill สำหรับ Feature หนึ่งๆ จะถูกเก็บรวมกันไว้ใน **1 โฟลเดอร์ต่อ 1 Feature**

1. **หาโฟลเดอร์รากของโปรเจค (Project Root)**: ถ้ายังไม่ทราบตำแหน่งโฟลเดอร์ "QA Pipeline Project" ในเครื่อง/ระบบไฟล์ที่ใช้งานอยู่ ให้ถามผู้ใช้ก่อนว่าโฟลเดอร์รากของโปรเจคอยู่ที่ path ไหน (ทุก Feature folder จะอยู่เป็นโฟลเดอร์ย่อยของ root นี้เสมอ)
2. ถามผู้ใช้ว่า Feature นี้ชื่ออะไร
3. **เช็คโฟลเดอร์ Feature ที่มีอยู่แล้วก่อนสร้างใหม่เสมอ**: ลิสต์รายชื่อโฟลเดอร์ย่อยทั้งหมดที่อยู่ใต้ Project Root แล้วเทียบกับชื่อ Feature ที่ผู้ใช้พิมพ์มาแบบไม่สนตัวพิมพ์เล็ก/ใหญ่และช่องว่างส่วนเกิน (case-insensitive, trim whitespace) — ถ้าเจอชื่อที่ใกล้เคียง/สะกดคล้ายกันมาก (เช่น "Login OTP" กับ "login-otp") ให้ถามผู้ใช้ยืนยันก่อนว่าหมายถึงโฟลเดอร์เดิมหรือจะสร้างใหม่จริงๆ **ห้ามสร้างโฟลเดอร์ใหม่ซ้ำซ้อนกับของเดิมโดยไม่ถามผู้ใช้**
4. เช็คว่ามีไฟล์ manifest `_pipeline-manifest.md` อยู่ในโฟลเดอร์ Feature นั้นหรือไม่
   - **ถ้ามีอยู่แล้ว**: อ่านไฟล์ manifest เพื่อดูว่า Feature นี้เดินหน้าไปถึงขั้นตอนไหนแล้ว ถ้า `source-ingest` เคยรันไปแล้ว (Status = Complete) ให้แจ้งผู้ใช้และถามว่าต้องการรันซ้ำหรือไม่ — ถ้ารันซ้ำเพื่อ**เติมแหล่งใหม่หรือแก้แหล่งที่เคย FAILED** ให้ทำตาม "การรันซ้ำ/อัปเดต Source Set เดิม" ท้าย ขั้นตอนที่ 6 (ใช้ `source_set_id` เดิม ไม่สร้างใหม่) ถ้าต้องการเริ่มรวบรวมชุดใหม่ทั้งหมดจริงๆ ค่อยสร้าง `source_set_id` ใหม่
   - **ถ้ายังไม่มี**: นี่คือ Feature ใหม่ ให้สร้างโฟลเดอร์ (ที่ `<Project Root>/<ชื่อ Feature>/`) และสร้างไฟล์ manifest ใหม่ (ดูโครงสร้าง manifest ท้ายไฟล์นี้)

## ขั้นตอนที่ 2 — รวบรวมแหล่งข้อมูล

ถามผู้ใช้ว่ามีเอกสาร Requirement จากแหล่งใดบ้างที่ต้องการรวม — รับได้หลายแหล่งพร้อมกัน ไม่จำกัดจำนวน และรับได้หลายรูปแบบ:

- ไฟล์ที่ผู้ใช้แนบมาโดยตรง
- ข้อความที่ผู้ใช้ paste มาตรงๆ (spec, chat log, meeting notes ฯลฯ)
- **ลิงก์ URL** — กรณีนี้ **ต้องพยายามดึงเนื้อหาจริงด้วยตัวเอง** ก่อน (ดูขั้นตอนที่ 3) ไม่ใช่แค่บันทึกลิงก์ไว้เฉยๆ

## ขั้นตอนที่ 3 — กำหนดรหัสและดึงเนื้อหาแต่ละแหล่ง

### 3.1 กำหนด `source_set_id`

รูปแบบ: `SRC-SET-<YYYYMMDD>-<NNN>` โดย `YYYYMMDD` คือวันที่วันนี้ และ `NNN` คือเลขรัน 3 หลักเริ่มที่ `001` — เช็คว่าใต้ `<โฟลเดอร์ Feature>/sources/` มี `source_set_id` ที่ขึ้นต้นด้วยวันที่วันนี้อยู่แล้วหรือไม่ ถ้ามีให้ใช้เลขถัดไป ถ้ายังไม่มีเลยของวันนี้ให้เริ่มที่ 001 (ถ้าเป็นการรันซ้ำเพื่ออัปเดต source set เดิม ให้ใช้ `source_set_id` เดิม ไม่ต้องสร้างใหม่ — ดูขั้นตอนที่ 6)

### 3.2 กำหนด ID ให้แต่ละแหล่ง

แต่ละแหล่งข้อมูลในรอบนี้ได้ ID เรียงลำดับ `SRC-001`, `SRC-002`, `SRC-003`, ... ตามลำดับที่ผู้ใช้ให้มา (เริ่มที่ 001 ใหม่ทุกครั้งที่เป็น source set ใหม่)

### 3.3 ดึงเนื้อหาแต่ละแหล่งและบันทึกไฟล์ดิบ

สำหรับ**แต่ละแหล่ง**:

1. **ถ้าเป็น URL**: ลองดึงเนื้อหาจริงด้วยเครื่องมือดึงเว็บที่มีอยู่ในระบบที่ใช้งานอยู่ ณ ตอนนี้ก่อนเสมอ
   - **ดึงสำเร็จ** → บันทึกเนื้อหาที่ได้ (ไม่ต้องสรุปย่อ เก็บเนื้อหาต้นฉบับให้ครบเพื่อใช้อ้างอิงย้อนกลับได้ ตัดได้เฉพาะส่วนที่ไม่เกี่ยวข้องจริงๆ เช่นเมนู/โฆษณาของหน้าเว็บ) ลงไฟล์ `<โฟลเดอร์ Feature>/sources/<source_set_id>/raw/<SRC-ID>-<slug>.md` (`<slug>` คือชื่อสั้นๆ อธิบายแหล่งนั้น เช่น `password-reset-wiki`) → สถานะ = **SUCCESS**
   - **ดึงไม่สำเร็จ** → บันทึกสถานะ = **FAILED** พร้อม**เหตุผลจริง**ที่ได้รับ (เช่น HTTP 403, timeout, ต้อง login, โดเมนเข้าไม่ถึงจาก environment นี้) ห้ามเดาสาเหตุถ้าไม่ทราบแน่ชัด ให้เขียนว่า "ไม่ทราบสาเหตุแน่ชัด" ตรงๆ **ห้ามแต่งเนื้อหาขึ้นมาแทนเด็ดขาด** แม้จะรู้สึกว่าพอเดาเนื้อหาได้จากความรู้ทั่วไปก็ตาม — ให้ปล่อยว่างแล้วส่งต่อเป็นช่องว่างในขั้นตอนที่ 4 แทน
   - ถ้าผู้ใช้บอกว่าดึงเองไม่ได้เหมือนกัน (เช่นต้อง login intranet) แต่ paste เนื้อหามาให้แทน ให้ถือว่า**สำเร็จ (SUCCESS)** เพราะได้เนื้อหามาจริง แต่ต้องบันทึกหมายเหตุไว้สั้นๆ ว่าได้มาโดยวิธีไหน (เช่น "QA copy เนื้อหามาวางให้ เพราะหน้านี้ต้อง login เข้า intranet ก่อน")
2. **ถ้าเป็นไฟล์แนบหรือข้อความที่ paste มาตรงๆ**: ถือว่าได้เนื้อหามาแล้ว บันทึกลงไฟล์ raw เช่นเดียวกับข้อ 1 (สถานะ = **SUCCESS** เสมอ เว้นแต่ไฟล์เปิดไม่ได้จริงๆ)
3. เก็บทุกไฟล์ดิบไว้ที่ `<โฟลเดอร์ Feature>/sources/<source_set_id>/raw/`

## ขั้นตอนที่ 4 — ทำสารบัญแหล่งข้อมูล เขียนสรุปสั้นต่อแหล่ง และหาช่องว่าง

หลังได้ไฟล์ raw ของทุกแหล่งแล้ว (หรือทราบว่าแหล่งไหน FAILED):

1. **ทำตาราง "สารบัญแหล่งข้อมูล"** หนึ่งแถวต่อแหล่ง คอลัมน์คือ ID / ประเภท / ที่มา (URL หรือชื่อไฟล์) / วันที่ดึง / สถานะ (**SUCCESS**/**FAILED**, ตัวหนา) / ไฟล์ที่บันทึก / หมายเหตุ — คอลัมน์ **หมายเหตุต้องสั้นมาก** เขียนแค่ "ได้มาโดยวิธีไหน" หรือ "ทำไมถึง FAILED" เท่านั้น (เช่น "ผู้ใช้แนบไฟล์มาโดยตรง" หรือ "HTTP 403 — โดเมนภายในเข้าไม่ถึงจาก environment นี้") **ห้ามใส่สรุปเนื้อหาของแหล่งนั้นลงในหมายเหตุเด็ดขาด** เพราะเนื้อหาแบบนั้นมีที่ของมันอยู่แล้วใน "สรุปจากแต่ละแหล่ง" ข้อ 2 — การใส่ซ้ำจะทำให้ cell ของตารางสูงเกินไปจนตารางแตกหน้าอ่านยาก
2. **ต่อแต่ละแหล่ง** เขียนสรุปเนื้อหาที่พบให้ครบพอที่คนอ่านสรุปนี้อย่างเดียว (ไม่เปิดไฟล์ raw เพิ่ม) จะเข้าใจสิ่งที่แหล่งนั้นพูดถึงได้จริง — จับ flow/กฎ/เงื่อนไข/ตัวเลข/ข้อยกเว้น/การตัดสินใจที่ระบุไว้ในแหล่งนั้น เขียนเป็นย่อหน้าต่อเนื่อง ไม่ใช่แค่ bullet บอก keyword ถ้าแหล่งนั้นมีหลายประเด็นย่อยที่แยกจากกันชัดเจน (เช่น flow การใช้งาน, error handling, ขอบเขตที่ไม่รวม) ให้ทำตัวหนาสั้นๆ นำหน้าแต่ละประเด็นเพื่อให้อ่านง่าย และให้ทำแบบเดียวกันนี้สม่ำเสมอทุกแหล่งที่มีลักษณะเนื้อหาคล้ายกัน (อย่าทำตัวหนาให้แหล่งหนึ่งแต่อีกแหล่งที่โครงสร้างคล้ายกันกลับไม่ทำ) **ยังคงเป็นการสรุปเนื้อหาของแหล่งนั้นๆ เท่านั้น ไม่ใช่การตัดสินว่าข้อมูลไหนถูกหรือเทียบกับแหล่งอื่น** (การเทียบแหล่งเป็นข้อถัดไป) แหล่งที่ FAILED ให้เขียนสั้นๆ ตรงๆ ว่าไม่มีเนื้อหาเพราะอะไร ไม่ต้องมีโครงสร้างย่อยแบบแหล่งอื่น
3. **หาความขัดแย้ง/ช่องว่างที่พบ**: ไล่ดูทุกแหล่งรวมกัน แล้วรวบรวมเป็นลิสต์เดียวสำหรับสิ่งต่อไปนี้ (ไม่ต้องแยกหมวดด้วย tag แบบ `[ขัดแย้ง]`/`[ช่องว่าง]` — ให้เขียนเป็นประโยคธรรมชาติที่บอกในตัวเองอยู่แล้วว่าเป็นแบบไหน โดยทำตัวหนาสั้นๆ นำหน้าแต่ละข้อ):
   - แหล่งที่ FAILED และยังไม่มีข้อมูลทดแทน
   - ตัวเลข/กฎ/การตัดสินใจสำคัญที่แหล่งต่างๆ **ขัดแย้งกัน** (เช่น ข้อเสนอ 2 ค่าที่ไม่ตรงกัน) — ระบุว่าแหล่งไหนเสนออะไร อย่าเลือกฝั่งใดฝั่งหนึ่งเองเด็ดขาด ปล่อยให้ QA/มนุษย์ตัดสินใจ
   - เรื่องที่ทุกแหล่งพูดตรงกันว่า "ยังไม่สรุป" หรือ "ยังไม่มีคำตอบ"
   - ข้อมูลที่คาดว่าจำเป็น (เช่น ชื่อผู้รับผิดชอบ, เกณฑ์ที่ใช้จริง) แต่ไม่ปรากฏในแหล่งใดเลย
   - (ถ้ามี) จุดที่ตัดสินใจไปแล้วอย่างชัดเจนแล้วแต่อาจดูเหมือนเป็นช่องว่าง ให้บันทึกไว้เป็นข้อสุดท้ายกันสับสน เขียนแบบเอียง (italics) นำหน้าด้วย "(ไม่ใช่ช่องว่าง แค่กันสับสน)" พร้อมเหตุผลสั้นๆ

## ขั้นตอนที่ 5 — รวมเป็นไฟล์ Requirement Intake เดียว

จัดทำไฟล์ตามโครงสร้างนี้:

```
# Requirement Intake — <ชื่อ Feature>

Created: <วันที่รัน>
แหล่งข้อมูลที่ใช้: (1) <ชื่อ/ประเภทแหล่งที่ 1 พร้อมรายละเอียดสั้นๆ ที่ช่วยระบุตัวตน เช่นวันที่แก้ไขล่าสุดถ้ามี>, (2) <แหล่งที่ 2> ...
```

## ขั้นตอนที่ 6 — บันทึกไฟล์และอัปเดต Manifest

1. บันทึกไฟล์ผลลัพธ์ที่ `<โฟลเดอร์ Feature>/00-pre-source-ingest.md`
2. อัปเดตไฟล์ `_pipeline-manifest.md` ในโฟลเดอร์เดียวกัน: ตั้งค่า Stage `00-pre source-ingest` เป็น **`Pending Review`** (ไม่ใช่ `Complete` — ดูเหตุผลที่ "การอัปเดตสถานะเป็น Complete หลัง Sign-off" ท้ายขั้นตอนนี้), ใส่ path ของไฟล์ output (`00-pre-source-ingest.md`), ใส่วันที่เสร็จ — ไฟล์ raw/ เป็นไฟล์ประกอบ ไม่ต้องอัปเดตคอลัมน์ Output File เพิ่ม
3. แจ้งผู้ใช้ว่าเสร็จแล้ว สรุปจำนวนแหล่ง SUCCESS/FAILED และจุดขัดแย้งที่เจอให้ฟังสั้นๆ แล้วถามว่าจะไปต่อที่ `test-plan` (ถ้าต้องการ) หรือข้ามไป `requirement-review` เลย — เตือนสั้นๆ ด้วยว่าสถานะยังเป็น `Pending Review` จนกว่าจะมีคนรีวิวและกรอก `## QA Review & Sign-off` เป็น approved
4. **(เพิ่มเติมเพื่อความสะดวกในการอ่าน — ไม่กระทบขั้นตอนอื่นในสาย pipeline)** สร้างไฟล์ Word (.docx) คู่กับไฟล์ `00-pre-source-ingest.md` โดยใช้ชื่อไฟล์เดียวกัน (เปลี่ยนแค่นามสกุล) เก็บไว้ในโฟลเดอร์เดียวกัน เพื่อให้คนที่ไม่สะดวกเปิด .md อ่านได้ง่ายขึ้น — รัน 3 คำสั่งนี้ตามลำดับ:
   ```
   pandoc "<path .md>" -f markdown+hard_line_breaks -o "<path .docx ชื่อเดียวกัน>" --standalone
   python3 "<path skill>/scripts/add_table_borders.py" "<path .docx>"
   python3 "<path skill>/scripts/fix_page_breaks.py" "<path .docx>"
   ```
   ขั้นแรกแปลง .md เป็น .docx ขั้นที่สองใส่กรอบตารางให้ตาราง "สารบัญแหล่งข้อมูล" อ่านง่ายขึ้น (และตั้งไม่ให้แถวตารางแตกข้ามหน้า) ขั้นที่สามป้องกันไม่ให้หัวข้อลอยเดี่ยวท้ายหน้าโดยเนื้อหาไปขึ้นหน้าถัดไป — ทั้งสองสคริปต์แก้เฉพาะไฟล์ `.docx` เท่านั้น ไม่แตะไฟล์ `.md` ต้นทาง ไฟล์ `.docx` นี้เป็นเพียง**สำเนาเพื่อความสะดวกในการอ่านเท่านั้น** — ไฟล์ `.md` ยังคงเป็นไฟล์หลัก (source of truth) ที่ Skill ถัดไปในสาย pipeline ใช้อ่านต่อเสมอ ไม่ใช่ `.docx` ถ้าเครื่องที่ใช้งานไม่มีคำสั่ง `pandoc` หรือ python พร้อม `python-docx` ติดตั้งไว้ ให้แจ้งผู้ใช้แล้วข้ามขั้นตอนที่ทำไม่ได้ไปได้เลย (เช่นได้แค่ pandoc แต่ไม่มี python-docx ก็ยังส่งไฟล์ .docx ที่ยังไม่มีกรอบตาราง/page-break ให้ผู้ใช้ได้ ไม่ถือเป็นตัวบล็อกการทำงานของ Skill นี้)

### การอัปเดตสถานะเป็น Complete หลัง Sign-off

`Pending Review` แปลว่า "ไฟล์สร้างเสร็จแล้ว แต่ยังไม่มีใครรีวิว/อนุมัติ" — สถานะนี้จะเปลี่ยนเป็น `Complete` ได้ก็ต่อเมื่อผู้ใช้แจ้งกลับมาว่าได้เปิดไฟล์นี้รีวิวแล้ว และกรอก `## QA Review & Sign-off` ท้ายไฟล์เป็น **"การตัดสินใจ: approved"** เท่านั้น (ผู้ใช้ต้องเป็นคนกรอกเอง — ดูข้อควรระวังเรื่องห้าม AI กรอกแทน) เมื่อได้รับการยืนยันแบบนี้ ให้กลับมาอัปเดต `_pipeline-manifest.md` เปลี่ยน Stage `00-pre source-ingest` จาก `Pending Review` เป็น `Complete`

ถ้าผู้ใช้แจ้งว่ากรอกเป็น "rejected" หรือ "needs revision" ให้สถานะคงเป็น `Pending Review` ต่อไป (ไม่ใช่ Complete) จนกว่าจะแก้ไขและได้รับการอนุมัติใหม่ — การแก้ไขให้ทำตาม "การรันซ้ำ/อัปเดต Source Set เดิม" ด้านล่าง

**ข้อสำคัญ**: นี่ไม่ใช่กลไกบังคับแบบเถียงไม่ได้ — เป็นแค่การรักษาความถูกต้องของ manifest ให้สื่อความจริง ถ้าผู้ใช้ต้องการใช้ไฟล์ที่ยังเป็น `Pending Review` ไปทำงานต่อทันทีโดยไม่รอ approve ก็ทำได้ตามปกติ (Skill นี้เองไม่ได้บล็อกอะไร — แต่ Skill ถัดไปที่อ่าน manifest อาจเตือนก่อนถ้าเจอสถานะนี้)

### การรันซ้ำ/อัปเดต Source Set เดิม

ถ้าผู้ใช้ขอเติมแหล่งใหม่หรือแก้แหล่งที่เคย FAILED ให้กับ source set ที่มีอยู่แล้ว (ไม่ใช่เริ่มรวบรวมชุดใหม่ทั้งหมด):

- ใช้ `source_set_id` เดิม ไม่สร้างใหม่ — ID ของแหล่งใหม่ที่เพิ่มเข้ามาต่อจากเลขล่าสุดที่มีอยู่ (เช่นมี SRC-001 ถึง SRC-003 อยู่แล้ว แหล่งใหม่เริ่มที่ SRC-004)
- เขียนไฟล์ใหม่ทั้งฉบับ (ไม่ใช่แค่ต่อท้ายแหล่งใหม่): `## สารบัญแหล่งข้อมูล` ต้องมีแถวครบทุกแหล่งทั้งเดิมและใหม่ `## สรุปจากแต่ละแหล่ง` ต้องครบทุกแหล่งทั้งเดิมและใหม่ และ `## จุดที่ข้อมูลขัดแย้งหรือเป็นช่องว่าง (ต้องเติมก่อนหรือรับทราบก่อนไปขั้น 01)` กับ `## สรุปภาพรวม (Synthesis)` ต้องทบทวนใหม่ทั้งคู่ เพราะแหล่งใหม่อาจคลี่คลายหรือเพิ่มความขัดแย้งที่ไม่เคยมีมาก่อน
- เพิ่มบรรทัด `Updated: <วันที่รันซ้ำ>` ต่อท้ายบรรทัด `Created:` เดิม (ห้ามลบ/แก้ `Created:` เดิม) เพื่อให้เห็นว่าไฟล์นี้เคยถูกอัปเดต
- เพิ่มแถวใหม่ต่อท้ายตาราง `## Revision History` เดิม (ห้ามลบแถวเก่า) — เลข Version เรียงต่อจากแถวล่าสุด (เช่นมีแถว 1 อยู่แล้ว รอบนี้เป็นแถว 2) ช่อง "สรุปการเปลี่ยนแปลง" ให้เขียนสั้นๆ ตรงๆ ว่ารอบนี้เพิ่ม/แก้อะไร (เช่น "เพิ่ม SRC-004, แก้ไขจุดขัดแย้งข้อ 3 ที่ SRC-003 เคย FAILED")
- `## QA Review & Sign-off` ท้ายไฟล์ให้เว้นว่างใหม่ทุกครั้งที่เขียนไฟล์ใหม่ทั้งฉบับ (checkbox ยังไม่ติ๊ก, Reviewer comment/การตัดสินใจยังว่าง) เพราะเนื้อหาเปลี่ยนไปจากรอบก่อน ต้องให้คนตรวจสอบใหม่เสมอ — **ห้าม AI เติมคำตอบใน Reviewer comment หรือการตัดสินใจเองเด็ดขาด** ส่วนนี้เป็นของ QA/มนุษย์เท่านั้น
- อัปเดต manifest ให้ Stage `00-pre source-ingest` กลับไปเป็น `Pending Review` เสมอ (แม้ก่อนรันซ้ำจะเคยเป็น `Complete` แล้วก็ตาม) เพราะเนื้อหาเปลี่ยนไปแล้ว ต้องรอการอนุมัติใหม่

## ข้อควรระวัง

- Skill นี้เป็น optional เสมอ — ถ้าผู้ใช้ไม่มีความจำเป็นต้องรวมหลายแหล่ง (เช่นมี Requirement ไฟล์เดียวอยู่แล้ว) ให้แนะนำว่าข้าม skill นี้ไปใช้ `requirement-review` ตรงๆ ได้เลย
- ห้ามเดาหรือแต่งเนื้อหา Requirement ที่ไม่มีอยู่ในแหล่งข้อมูลที่ได้รับมา รวมถึง**ห้ามแต่งเนื้อหาแทนแหล่งที่ดึงไม่สำเร็จ (FAILED)** เด็ดขาด แม้จะรู้สึกว่าพอเดาได้จากความรู้ทั่วไปก็ตาม — ให้บันทึกเป็นช่องว่างแทนการเดาเสมอ
- ถ้าดึง URL ไม่สำเร็จ ให้บันทึกเหตุผลที่แท้จริงจาก error/response ที่ได้รับจริง ห้ามเดาสาเหตุ ถ้าไม่ทราบแน่ชัดให้เขียนตรงๆ ว่า "ไม่ทราบสาเหตุแน่ชัด"
- "สรุปภาพรวม (Synthesis)" ท้ายไฟล์เป็นการร้อยเรียงให้อ่านง่ายเท่านั้น ห้ามใช้ช่องนี้เป็นทางลัดในการฟันธง/เลือกฝั่งระหว่างแหล่งที่ขัดแย้งกัน — จุดที่ยังขัดแย้ง/ไม่มีคำตอบต้องคงไว้ตรงๆ (ทำตัวหนา) เสมอ แล้วปล่อยให้ `requirement-review` เป็นผู้ตัดสินใจต่อ
- คอลัมน์ **หมายเหตุ** ในตาราง "สารบัญแหล่งข้อมูล" ต้องสั้นเสมอ (แค่วิธีที่ได้เนื้อหามาหรือเหตุผลที่ FAILED) — ห้ามใส่สรุปเนื้อหาของแหล่งนั้นลงไปแทน เพราะเคยทำให้ cell สูงเกินจนตารางแตกหน้าและอ่านยาก เนื้อหาแบบนั้นมีที่ของมันอยู่แล้วคือหัวข้อ "สรุปจากแต่ละแหล่ง"
- `## QA Review & Sign-off` ท้ายไฟล์คือช่องให้คน (QA/ผู้ตรวจสอบ) กรอกเอง — AI สร้างได้แค่โครง checkbox เปล่ากับหัวข้อ "Reviewer comment:" และ "การตัดสินใจ:" เท่านั้น **ห้ามเดา/เติมคำตอบลงไปเองเด็ดขาด** ไม่ว่าจะดูมั่นใจแค่ไหนว่าควร approve
- เขียนทุกส่วนด้วยภาษาที่เป็นธรรมชาติ อ่านง่าย ไม่ทางการจนฟังดูเหมือน AI เขียน หลีกเลี่ยงคำอย่าง "มติ", "ข้อกำหนดที่ปิดจบ/ยืนยันแล้ว", "รอการยืนยันอย่างเป็นทางการ" และหลีกเลี่ยง tag จัดหมวดแบบวงเล็บเหลี่ยม (`[ขัดแย้ง]`, `[ช่องว่าง]`) แต่ก็ยังต้องคงความเป็นทางการในระดับที่เอกสาร QA ใช้งานจริงได้
