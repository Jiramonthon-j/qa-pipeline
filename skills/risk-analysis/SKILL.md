# risk-analysis

Skill นี้เป็น**ขั้นตอนที่ 5 ที่บังคับ** ของ QA Pipeline หน้าที่คือกำหนดค่าคอลัมน์ `Priority` (P0–P3) ให้กับทุก Test Case ใน Workbook ซึ่ง `test-case-generator` (03) จงใจปล่อยว่างไว้ก่อนหน้านี้ ค่า Priority นี้จะถูกใช้ต่อโดย `redmine-logging` (09) ตอนเปิด Ticket และ `qa-report-generator` (08) ตอนสรุปผล Go/No-Go

**สำคัญ**: คำสั่งในไฟล์นี้เขียนขึ้นให้ใช้ได้กับทั้ง Claude และ Gemini 3.6 — ห้ามอ้างอิงชื่อ tool เฉพาะของแพลตฟอร์มใดแพลตฟอร์มหนึ่ง Skill นี้ต้องใช้ environment ที่รันสคริปต์ Python ได้เพื่ออ่าน/แก้ Workbook (.xlsx) เหมือน `test-case-generator` และ `coverage-review`

## ขั้นตอนที่ 1 — ระบุ Feature และตรวจสอบขั้นตอนก่อนหน้า

1. หาโฟลเดอร์รากของโปรเจค (Project Root) และโฟลเดอร์ Feature เหมือน Skill อื่นๆ ในสาย
2. อ่านไฟล์ `_pipeline-manifest.md` ของ Feature นั้น
3. **เช็ค Gate**: Skill นี้ต้องรันต่อจาก `coverage-review` (Skill 04) เสมอ — ตรวจสอบสถานะ Stage `04 coverage-review` (ถ้าไม่มี manifest เลยก็ถือว่ายังไม่เสร็จเช่นกัน — ต้องถามผู้ใช้เสมอ ห้ามสรุปเอาเอง):
   - **ถ้า `Complete`**: ไปต่อขั้นตอนที่ 2
   - **ถ้ายังไม่ `Complete`**: หยุดและถามผู้ใช้ว่า (a) ต้องการไปรัน `coverage-review` ให้เสร็จก่อนไหม (แนะนำ) หรือ (b) ต้องการใช้ Skill นี้แบบ standalone — ถ้าเลือก (b) ให้ขอ Test Case Workbook ที่มีอยู่แล้วมาจากผู้ใช้โดยตรง พร้อม Requirement/E2E Flow ถ้ามี (เพื่อใช้ประกอบการประเมินความเสี่ยง)
4. ถ้ามีไฟล์ `04-coverage-review.md` ให้อ่านดูว่ามีจุดที่ถูกทำเครื่องหมายเป็น **Deferred** ค้างอยู่หรือไม่ — ถ้ามี ให้แจ้งเตือนผู้ใช้สั้นๆ ก่อนเริ่มขั้นตอนที่ 2 ว่ายังมีช่องว่าง Coverage ที่ถูกเลื่อนไว้ (ไม่บล็อกการทำงาน แค่เตือนเฉยๆ)

## ขั้นตอนที่ 2 — อ่านข้อมูลที่ต้องใช้ประเมินความเสี่ยง

1. อ่าน Test Case Workbook **ฉบับล่าสุดจริงๆ** ด้วยคำสั่ง (กรณี Excel):
   ```
   python3 scripts/qa_workbook.py read-cases --path "<path Workbook>"
   ```
   (เหตุผลเดียวกับ `coverage-review`: ผู้ใช้อาจแก้ไข Test Case เองด้วยมือไปแล้ว ต้องอ่านฉบับล่าสุดเสมอ ไม่ใช่จำจากรอบก่อน) — **หมายเหตุโครงสร้าง**: `scripts/qa_workbook.py` ของ Skill นี้เป็น stub ที่โหลดฉบับจริงจาก `qa-pipeline-skills/_shared/qa_workbook.py` มาใช้ร่วมกับอีก 4 Skill ในสาย ถ้าต้องแก้ logic ให้แก้ที่ `_shared/` ที่เดียว ห้ามแก้ stub นี้
2. อ่านชีต "Priority & Risk Matrix" ในไฟล์เดียวกัน (เปิดผ่าน openpyxl โดยตรง) เพื่อใช้เป็นเกณฑ์นิยาม P0–P3 อย่างเป็นทางการ
3. อ่าน `01-requirement-review.md` และ `02-e2e-flow.md` เพื่อเข้าใจบริบท — โดยเฉพาะว่า Business Rule/Flow ไหนเกี่ยวกับความปลอดภัย เงิน ข้อมูลสำคัญ หรือเป็นเส้นทางหลักที่ผู้ใช้ส่วนใหญ่ต้องผ่าน

## ขั้นตอนที่ 3 — ประเมิน Priority ของแต่ละ Test Case

สำหรับ**แต่ละ Test Case** ให้พิจารณาว่าตรงกับนิยามข้อไหนในชีต Priority & Risk Matrix มากที่สุด โดยใช้หลักคิดนี้เป็นแนวทาง (ปรับตามบริบทจริงของแต่ละ Feature ได้ ไม่ใช่กฎตายตัว):

- **P0**: ถ้า Test Case นี้ Fail แล้วทำให้ผู้ใช้ใช้งานฟีเจอร์หลักไม่ได้เลย หรือกระทบความปลอดภัย/ข้อมูล/เงินโดยตรง (เช่น เส้นทางหลักของการ Login, การจ่ายเงิน, การป้องกันการเข้าถึงโดยไม่ได้รับอนุญาต)
- **P1**: ถ้า Test Case นี้ Fail แล้วกระทบฟีเจอร์หลักตามที่ออกแบบไว้ แต่ยังมีทางเลี่ยง/ทางเลือกอื่นให้ผู้ใช้ใช้งานต่อได้
- **P2**: ถ้า Test Case นี้ Fail แล้วกระทบ UX/ความสะดวก แต่ไม่ block การใช้งานหลัก (เช่น ข้อความ error ไม่ชัดเจน, edge case ที่พบยากในการใช้งานจริง)
- **P3**: ปัญหาเล็กน้อย/ความสวยงามที่ไม่กระทบการทำงาน

**ให้เหตุผลสั้นๆ กำกับทุกครั้งที่กำหนด Priority** (จะบันทึกไว้ในรายงานตามขั้นตอนที่ 5) เพื่อให้ผู้ใช้ตรวจสอบย้อนหลังได้ว่าทำไมถึงให้ระดับนั้น — ถ้าไม่มั่นใจว่า Test Case ใดควรเป็น Priority ระดับไหน ให้ถามผู้ใช้แทนการเดาโดยเฉพาะกรณีที่อยู่กึ่งกลางระหว่าง P0/P1

## ขั้นตอนที่ 4 — บันทึกค่า Priority ลง Workbook

**ห้ามรันคำสั่งแก้ไขทีละ Test Case ทีละครั้ง** (จะทำให้ Document Control History มีบรรทัดย่อยเยอะเกินจำเป็น เพราะ Skill นี้มักแก้หลายสิบแถวในรอบเดียว) ให้เตรียมรายการ Priority ที่ประเมินไว้ทั้งหมดเป็นไฟล์ JSON เดียว (list ของ `{"tc_id": "...", "field": "Priority", "value": "P0|P1|P2|P3"}`) แล้วรันครั้งเดียว:
```
python3 scripts/qa_workbook.py update-fields-batch --path "<path Workbook>" --updates-json "<path .json>" --editor "risk-analysis" --note "กำหนด Priority ให้ Test Case ทั้งหมด <จำนวน> เคส"
```
คำสั่งนี้จะใส่สีกำกับ Priority ให้อัตโนมัติตามที่กำหนดไว้ในสคริปต์ และ **bump Version ของ Document Control ขึ้นเพียง 1 ครั้งสำหรับทั้งรอบ** (ไม่ใช่ 1 ครั้งต่อ 1 Test Case) พร้อมบันทึกประวัติไว้ 1 บรรทัดสรุปว่ากำหนด Priority ให้กี่เคส — ถ้าภายหลังต้องแก้ Priority ของ Test Case เดี่ยวๆ เพียงรายการเดียว (เช่นแก้ไขหลังทบทวน) จึงค่อยใช้คำสั่ง `update-field` แบบทีละรายการแทน

## ขั้นตอนที่ 5 — เขียนรายงานและอัปเดต Manifest

สร้างไฟล์ `<โฟลเดอร์ Feature>/05-risk-analysis.md` สรุป Priority ที่กำหนดให้ทุก Test Case พร้อมเหตุผล จัดกลุ่มตามระดับ Priority:

```
# Risk Analysis — <ชื่อ Feature>

Created: <วันที่>

## สรุปจำนวน Test Case แยกตาม Priority
P0: <จำนวน>
P1: <จำนวน>
P2: <จำนวน>
P3: <จำนวน>

## P0 — วิกฤต
### <Test Case ID>: <Test Scenario>
เหตุผล: ...

## P1 — สำคัญ
...

## P2 — ปานกลาง
...

## P3 — เล็กน้อย
...

## หมายเหตุ
<ถ้ามีจุดที่ยังไม่มั่นใจ/ต้องให้ผู้ใช้ยืนยันเพิ่มเติม ระบุไว้ที่นี่>
```

อัปเดต `_pipeline-manifest.md`: ตั้งค่า Stage `05 risk-analysis` เป็น `Complete`, ใส่ path ของไฟล์ output, ใส่วันที่เสร็จ แจ้งผู้ใช้ว่าเสร็จแล้วพร้อมสรุปจำนวนแยกตาม Priority แล้วแนะนำให้ไปต่อ `test-data-generator` (Skill 06)

## ข้อควรระวัง

- ห้ามปล่อย Test Case ใดไว้โดยไม่มีค่า Priority — ทุกแถวในชีต Test Case ต้องถูกกำหนดค่าให้ครบก่อนถือว่า Skill นี้เสร็จสมบูรณ์
- ถ้า Test Case ใดมีการอ้างอิงสมมติฐานที่ยังไม่ยืนยัน (ดูคอลัมน์ Remarks ที่ระบุไว้ตั้งแต่ `test-case-generator`/`coverage-review`) ให้ยังคงประเมิน Priority ตามความเสี่ยงที่คาดว่าน่าจะเป็นไปได้มากที่สุดไปก่อน ไม่ใช่ปล่อยว่างไว้รอคำตอบ — เพราะ Priority มีไว้ช่วยจัดลำดับการทดสอบจริง ไม่ควรบล็อกด้วยประเด็นที่ยังไม่ปิดจบ
- ถ้า manifest ระบุว่า `coverage-review` สถานะ `In Progress` ห้ามอ่านไฟล์มาใช้ทันทีเหมือนเป็นข้อมูลสมบูรณ์ ให้เตือนผู้ใช้ก่อนเหมือน Skill ก่อนหน้า
