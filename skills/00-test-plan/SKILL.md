# test-plan

Skill นี้เป็น**ขั้นตอนที่ไม่บังคับ (optional)** ของ QA Pipeline หน้าที่คือออกแบบ Test Plan ให้ Feature หนึ่งๆ **ทำงานอิสระจาก `source-ingest`** — ใช้ได้ทั้งกรณีที่ `source-ingest` เคยรันมาก่อนแล้ว หรือผู้ใช้นำเข้า Requirement มาตรงๆ ก็ได้

**สำคัญ**: คำสั่งในไฟล์นี้เขียนขึ้นให้ใช้ได้กับทั้ง Claude และ Gemini 3.6 — ห้ามอ้างอิงชื่อ tool เฉพาะของแพลตฟอร์มใดแพลตฟอร์มหนึ่ง ให้อธิบายเป็นขั้นตอนที่โมเดลไหนก็ทำตามได้

## ขั้นตอนที่ 1 — ระบุ Feature และโฟลเดอร์โปรเจค

1. **หาโฟลเดอร์รากของโปรเจค (Project Root)**: ถ้ายังไม่ทราบตำแหน่งโฟลเดอร์ "QA Pipeline Project" ให้ถามผู้ใช้ก่อนว่า Project Root อยู่ที่ path ไหน (ทุก Feature folder อยู่เป็นโฟลเดอร์ย่อยของ root นี้เสมอ)
2. ถามผู้ใช้ว่ากำลังทำ Test Plan ให้ Feature ชื่ออะไร
3. **เช็คโฟลเดอร์ Feature ที่มีอยู่แล้วก่อนสร้างใหม่เสมอ**: ลิสต์รายชื่อโฟลเดอร์ย่อยทั้งหมดใต้ Project Root แล้วเทียบกับชื่อที่ผู้ใช้พิมพ์มาแบบไม่สนตัวพิมพ์เล็ก/ใหญ่และช่องว่างส่วนเกิน ถ้าเจอชื่อใกล้เคียงกันมาก ให้ถามผู้ใช้ยืนยันก่อนว่าเป็นโฟลเดอร์เดิมหรือจะสร้างใหม่ **ห้ามสร้างโฟลเดอร์ใหม่ซ้ำซ้อนกับของเดิมโดยไม่ถามผู้ใช้**
4. เช็คว่ามีไฟล์ `_pipeline-manifest.md` อยู่ในโฟลเดอร์ Feature นั้นหรือไม่
   - **ถ้ามีอยู่แล้ว**: อ่าน manifest เพื่อดูสถานะปัจจุบัน ถ้า `test-plan` เคยรันไปแล้ว (Complete) ให้แจ้งผู้ใช้และถามว่าจะรันซ้ำเพื่อ**อัปเดต Test Plan เดิม** หรือไม่ (ดู "การรันซ้ำ/อัปเดต Test Plan เดิม" ท้ายขั้นตอนที่ 5) หรือต้องการทำฉบับใหม่จริงๆ
   - **ถ้ายังไม่มี**: นี่คือ Feature ใหม่ (แปลว่าผู้ใช้เลือกข้าม `source-ingest` มาเริ่มที่นี่โดยตรง) — สร้างโฟลเดอร์ (ที่ `<Project Root>/<ชื่อ Feature>/`) และไฟล์ manifest ใหม่ (โครงสร้างเดียวกับที่ระบุไว้ใน Skill `source-ingest`) **โดยตั้งค่า Stage `00-pre source-ingest` เป็น `Skipped` ทันที** (ไม่ใช่ `Not Started`) เพื่อให้ manifest สื่อความชัดเจนว่าผู้ใช้ตั้งใจข้าม ไม่ใช่แค่ยังไม่ได้ทำ

## ขั้นตอนที่ 2 — หาที่มาของ Requirement

ถามผู้ใช้ว่าจะใช้ Requirement จากที่ไหน มี 2 ทางเลือก:
- **(a)** ใช้ผลลัพธ์จาก `source-ingest` — เช็คใน manifest ว่ามีไฟล์ `00-pre-source-ingest.md` อยู่ในโฟลเดอร์ Feature นี้หรือไม่ ถ้ามีให้เสนอใช้ไฟล์นั้น แล้ว**จำชื่อไฟล์นั้นไว้** (จะใช้ในขั้นตอนที่ 4 เพื่อใส่บรรทัด "Requirement อ้างอิงจาก:" ที่หัว Test Plan)
- **(b)** ผู้ใช้นำเข้า Requirement โดยตรง (ไฟล์ใหม่ที่ยังไม่เคยผ่าน source-ingest) — ให้รับไฟล์/เนื้อหานั้นมาอ่านตรงๆ ในกรณีนี้บรรทัด "Requirement อ้างอิงจาก:" ให้ระบุว่าผู้ใช้นำเข้าเองโดยตรง (ไม่มีไฟล์จาก source-ingest ให้อ้างอิง)

อ่านเนื้อหา Requirement ที่ได้มาอย่างละเอียดครบถ้วนก่อนเริ่มออกแบบ Test Plan

## ขั้นตอนที่ 3 — กำหนดรหัส `test_plan_id`

รูปแบบ: `TP-<YYYYMMDD>-<NNN>` โดย `YYYYMMDD` คือวันที่วันนี้ และ `NNN` คือเลขรัน 3 หลักเริ่มที่ `001` — เช็คว่าใต้ `<โฟลเดอร์ Feature>/testplans/` มี `test_plan_id` ที่ขึ้นต้นด้วยวันที่วันนี้อยู่แล้วหรือไม่ ถ้ามีให้ใช้เลขถัดไป ถ้ายังไม่มีเลยของวันนี้ให้เริ่มที่ 001 (ถ้าเป็นการรันซ้ำเพื่ออัปเดต Test Plan เดิม ให้ใช้ `test_plan_id` เดิม ไม่ต้องสร้างใหม่ — ดูขั้นตอนที่ 5)

## ขั้นตอนที่ 5 — บันทึกไฟล์และอัปเดต Manifest

1. บันทึกไฟล์ผลลัพธ์ที่ `<โฟลเดอร์ Feature>/testplans/<test_plan_id>-<slug>.md` (`<slug>` คือชื่อ Feature แบบสั้น kebab-case)
2. อัปเดตไฟล์ `_pipeline-manifest.md`: ตั้งค่า Stage `00 test-plan` เป็น **`Pending Review`** (ไม่ใช่ `Complete` — ดูเหตุผลที่ "การอัปเดตสถานะเป็น Complete หลัง Sign-off" ท้ายขั้นตอนนี้), ใส่ path ของไฟล์ output (`testplans/<test_plan_id>-<slug>.md`), ใส่วันที่เสร็จ
3. แจ้งผู้ใช้ว่าเสร็จแล้ว และแนะนำให้ไปต่อที่ `requirement-review` (Skill 01) ซึ่งเป็นขั้นตอนถัดไปที่บังคับ — เตือนเรื่อง Deadline ที่ต้องกรอกซ้ำด้วย (ดูข้อ 9 กำหนดการ) และเตือนสั้นๆ ว่าสถานะยังเป็น `Pending Review` จนกว่าจะมีคนรีวิวและกรอก `## 14. QA Review & Sign-off` เป็น approved
4. **(เพิ่มเติมเพื่อความสะดวกในการอ่าน — ไม่กระทบขั้นตอนอื่นในสาย pipeline)** สร้างไฟล์ Word (.docx) คู่กับไฟล์ `.md` ที่บันทึกไว้ในข้อ 1 โดยใช้ชื่อไฟล์เดียวกัน (เปลี่ยนแค่นามสกุล) เก็บไว้ในโฟลเดอร์เดียวกัน — รัน 4 คำสั่งนี้ตามลำดับ:
   ```
   pandoc "<path .md>" -f markdown+hard_line_breaks -o "<path .docx ชื่อเดียวกัน>" --standalone
   python3 "<path skill>/scripts/resize_table_columns.py" "<path .docx>"
   python3 "<path skill>/scripts/add_table_borders.py" "<path .docx>"
   python3 "<path skill>/scripts/fix_page_breaks.py" "<path .docx>"
   ```
   ขั้นแรกแปลง .md เป็น .docx ขั้นที่สอง**ปรับความกว้างคอลัมน์ของทุกตารางตามเนื้อหาจริง พร้อมลดขนาดฟอนต์ในตารางลงเหลือ 10pt** (ยืนยันแล้วผ่าน Mockup — pandoc หารความกว้างเท่ากันทุกคอลัมน์โดย default ทำให้คอลัมน์ข้อความยาวแคบเกินไปจนคำถูกตัดกลางคำ โดยเฉพาะตารางคอลัมน์เยอะอย่าง "10. ความเสี่ยงของแผนทดสอบ" — สคริปต์นี้คำนวณความกว้างจากความยาวเนื้อหาจริงในแต่ละคอลัมน์ และกันไม่ให้คำภาษาอังกฤษ/ตัวเลขคำเดียวยาวๆ ถูกตัดกลางคำด้วย ไม่ได้ hardcode ตามชื่อหัวตาราง เพราะไฟล์นี้มีหลายตารางโครงสร้างต่างกัน) ขั้นที่สามใส่กรอบให้ทุกตาราง (ประเภทการทดสอบ, Environment, Exit Criteria, บทบาท, กำหนดการ, ความเสี่ยง, Revision History) และกันแถวตารางแตกข้ามหน้า ขั้นที่สี่ป้องกันไม่ให้หัวข้อลอยเดี่ยวท้ายหน้าโดยเนื้อหาไปขึ้นหน้าถัดไป — ทั้งสามสคริปต์แก้เฉพาะไฟล์ `.docx` เท่านั้น ไม่แตะไฟล์ `.md` ต้นทาง ไฟล์ `.docx` นี้เป็นเพียง**สำเนาเพื่อความสะดวกในการอ่านเท่านั้น** — ไฟล์ `.md` ยังคงเป็นไฟล์หลัก (source of truth) ที่ Skill ถัดไปในสาย pipeline ใช้อ่านต่อเสมอ ถ้าเครื่องที่ใช้งานไม่มีคำสั่ง `pandoc` หรือ python พร้อม `python-docx` ติดตั้งไว้ ให้แจ้งผู้ใช้แล้วข้ามขั้นตอนที่ทำไม่ได้ไปได้เลย ไม่ถือเป็นตัวบล็อกการทำงานของ Skill นี้

### การอัปเดตสถานะเป็น Complete หลัง Sign-off

`Pending Review` แปลว่า "ไฟล์สร้างเสร็จแล้ว แต่ยังไม่มีใครรีวิว/อนุมัติ" — สถานะนี้จะเปลี่ยนเป็น `Complete` ได้ก็ต่อเมื่อผู้ใช้แจ้งกลับมาว่าได้เปิดไฟล์นี้รีวิวแล้ว และกรอก `## 14. QA Review & Sign-off` ท้ายไฟล์เป็น **"การตัดสินใจ: approved"** เท่านั้น (ผู้ใช้ต้องเป็นคนกรอกเอง — ดูข้อควรระวังเรื่องห้าม AI กรอกแทน) เมื่อได้รับการยืนยันแบบนี้ ให้กลับมาอัปเดต `_pipeline-manifest.md` เปลี่ยน Stage `00 test-plan` จาก `Pending Review` เป็น `Complete`

ถ้าผู้ใช้แจ้งว่ากรอกเป็น "rejected" หรือ "needs revision" ให้สถานะคงเป็น `Pending Review` ต่อไป (ไม่ใช่ Complete) จนกว่าจะแก้ไขและได้รับการอนุมัติใหม่ — การแก้ไขให้ทำตาม "การรันซ้ำ/อัปเดต Test Plan เดิม" ด้านล่าง

**ข้อสำคัญ**: นี่ไม่ใช่กลไกบังคับแบบเถียงไม่ได้ — เป็นแค่การรักษาความถูกต้องของ manifest ให้สื่อความจริง ถ้าผู้ใช้ต้องการใช้ไฟล์ที่ยังเป็น `Pending Review` ไปทำงานต่อทันทีโดยไม่รอ approve ก็ทำได้ตามปกติ (Skill นี้เองไม่ได้บล็อกอะไร — แต่ Skill ถัดไปที่อ่าน manifest อาจเตือนก่อนถ้าเจอสถานะนี้)

### การรันซ้ำ/อัปเดต Test Plan เดิม

ถ้าผู้ใช้ขอแก้ไข Test Plan ที่มีอยู่แล้ว (ไม่ใช่ทำฉบับใหม่ทั้งหมด):

- ใช้ `test_plan_id` เดิม ไม่สร้างใหม่ และเขียนทับไฟล์ `.md` เดิมด้วยเนื้อหาที่อัปเดตแล้วทั้งฉบับ (ไม่ใช่แค่แก้บางส่วน) เพื่อให้ไฟล์นี้เป็นภาพล่าสุดที่ครบถ้วนเสมอ
- เพิ่มบรรทัด `Updated: <วันที่รันซ้ำ>` ต่อท้ายบรรทัด `Created:` เดิม (ห้ามลบ/แก้ `Created:` เดิม)
- เพิ่มแถวใหม่ต่อท้ายตาราง `## 12. Revision History` เดิม (ห้ามลบแถวเก่า) — เลข Version เรียงต่อจากแถวล่าสุด (เช่น 1.0 → 1.1) ช่อง "สรุปการเปลี่ยนแปลง" เขียนสั้นๆ ตรงๆ ว่ารอบนี้แก้อะไร
- ทบทวนทุกหัวข้อที่อาจได้รับผลกระทบจากการเปลี่ยนแปลง โดยเฉพาะ `## 10. ความเสี่ยงของแผนทดสอบ` และ `## 11. Open Questions` — เงื่อนไข/สมมติฐานที่เคยเปิดค้างไว้อาจถูกยืนยันแล้วหรือมีของใหม่เพิ่มมา
- `## 14. QA Review & Sign-off` ให้เว้นว่างใหม่ทุกครั้งที่เขียนไฟล์ใหม่ทั้งฉบับ (checkbox ยังไม่ติ๊ก, Reviewer comment/การตัดสินใจยังว่าง) เพราะเนื้อหาเปลี่ยนไปจากรอบก่อน ต้องให้คนตรวจสอบใหม่เสมอ
- อัปเดต manifest ให้ Stage `00 test-plan` กลับไปเป็น `Pending Review` เสมอ (แม้ก่อนรันซ้ำจะเคยเป็น `Complete` แล้วก็ตาม) เพราะเนื้อหาเปลี่ยนไปแล้ว ต้องรอการอนุมัติใหม่

## ข้อควรระวัง

- Skill นี้เป็น optional เสมอ — ถ้าผู้ใช้ไม่ต้องการทำ Test Plan แบบเป็นทางการ ให้แนะนำว่าข้ามไปที่ `requirement-review` ได้เลย
- อย่าเดา Timeline, Deadline, ตัวเลข Exit Criteria, หรือชื่อบุคคลใดๆ เอง ต้องถามผู้ใช้เสมอถ้าไม่มีข้อมูลนี้อยู่ใน Requirement ต้นทาง — ใส่ "ยังไม่ระบุ" แทนการเดาเสมอ
- ถ้าเลือกใช้ Requirement จาก `source-ingest` แต่ manifest ระบุว่า stage นั้นยังเป็น `Not Started` หรือ `In Progress` (ไฟล์ยังไม่เสร็จ) ให้แจ้งผู้ใช้ก่อนว่าไฟล์ต้นทางยังไม่พร้อม แล้วถามว่าจะรอให้รัน `source-ingest` ก่อน หรือจะนำเข้า Requirement ทางอื่นแทน
- ถ้า manifest ระบุว่า `source-ingest` เป็น `Pending Review` (ไฟล์เสร็จแล้วแต่ยังไม่มีคนอนุมัติผ่าน QA Review & Sign-off) ยังใช้ไฟล์นั้นได้ตามปกติ แต่ต้องแจ้งผู้ใช้ก่อนว่าต้นทางยังไม่ได้รับการอนุมัติอย่างเป็นทางการ แล้วถามว่าจะรอ approve ก่อน หรือใช้เนื้อหาที่มีอยู่ตอนนี้ไปพลางก่อน — ถ้าเลือกใช้ต่อเลย ให้บันทึกไว้ใน `## 11. Open Questions` ของ Test Plan นี้ด้วยว่า Requirement ต้นทางยังไม่ได้ approve
- `## 10. ความเสี่ยงของแผนทดสอบ` และ `## 11. Open Questions` คือที่ที่ควรดึงช่องว่าง/ความขัดแย้งระดับ Feature มาจาก Requirement ต้นทาง (โดยเฉพาะจาก source-ingest) — ห้ามใช้ช่องไหนในเอกสารนี้เป็นทางลัดในการฟันธง/เลือกฝั่งเมื่อ Requirement ต้นทางยังขัดแย้งกันอยู่ ให้คงความไม่ชัดเจนนั้นไว้ตรงๆ เสมอ
- คอลัมน์ "ผลกระทบ"/"แผนรับมือ" ในตารางความเสี่ยง (ข้อ 10) ต้องสั้นกระชับเสมอ — รายละเอียดยาวให้แยกเป็นย่อหน้าท้ายตารางแทนการยัดในเซลล์เดียว (ดูเหตุผลในขั้นตอนที่ 4)
- ทุกข้อที่เป็นสมมติฐาน (ไม่ใช่ความเสี่ยง) ต้องมีที่มาเสมอ (เช่น "จาก Slack thread วันที่ X") ห้ามเขียนสมมติฐานลอยๆ โดยไม่มีที่มา และห้ามใช้เป็นทางลัดในการ "เดา" สิ่งที่ไม่มีมูลอะไรรองรับเลย
- `## 14. QA Review & Sign-off` ท้ายไฟล์คือช่องให้คน (QA/ผู้ตรวจสอบ) กรอกเอง — AI สร้างได้แค่โครง checkbox เปล่ากับหัวข้อ "Reviewer comment:" และ "การตัดสินใจ:" เท่านั้น **ห้ามเดา/เติมคำตอบลงไปเองเด็ดขาด**
