# qa-retest-closure

Skill นี้เป็น**ขั้นตอนที่ 10a** ของ QA Pipeline แยกออกมาจาก `qa-retest` (10) โดยเจตนา — เหตุผลที่ผู้ใช้ยืนยันไว้ตอนออกแบบคือ**อยากให้มีจุดให้คน Recheck ผลอีกครั้งก่อนที่ Skill จะไปคอมเมนต์/ปิด Ticket จริงใน Redmine** (การปิด Ticket เป็นการเปลี่ยนแปลงระบบภายนอกที่ย้อนกลับเองไม่ได้ง่ายๆ เหมือนกับการเปิด Ticket ใน Skill 09) หน้าที่ของ Skill นี้คือ**คอมเมนต์ + ปิด Ticket** เท่านั้น — **ไม่ทำการ Retest เอง** (นั่นเป็นหน้าที่ของ Skill 10)

**ความสัมพันธ์กับ Skill 10 เป็นแบบวนลูปได้ (loop) ไม่ใช่ทางเดียว**: ถ้า Skill นี้คอมเมนต์แจ้ง Dev ว่ายัง Fail อยู่ (พร้อมส่งอีเมลซ้ำ) แล้ว Dev แก้ไขและคอมเมนต์กลับมาอีกรอบใน Redmine ผู้ใช้ก็จะกลับไปเรียก `qa-retest` (10) ใหม่เพื่อเช็ค Comment/Retest อีกรอบ แล้ววนกลับมาที่ Skill นี้อีกครั้งเพื่อ Recheck+ปิด — ทำแบบนี้ไปเรื่อยๆ ได้จนกว่าทุกเคสจะ Pass และถูกปิดหมด ทั้ง 2 Skill ถูกออกแบบให้เรียกซ้ำได้อย่างปลอดภัย (idempotent) อยู่แล้ว ไม่ต้องมี state พิเศษมาจำว่าวนมากี่รอบแล้ว

## ขั้นตอนที่ 1 — ตรวจสอบขั้นตอนก่อนหน้าและกำหนดขอบเขต (Scope)

1. หาโฟลเดอร์ Project Root และโฟลเดอร์ Feature เหมือน Skill อื่นๆ ในสาย อ่าน `_pipeline-manifest.md`
2. **เช็ค Gate**: ต้องมีผลการ Retest จาก `qa-retest` (10) อย่างน้อย 1 เคสในรอบล่าสุดเสมอ — ตรวจสอบสถานะ Stage `10 qa-retest` ว่ามีการรันจริงมาแล้ว (ไม่ใช่ `In Progress (รอ Dev แก้อยู่ N ใบ)` แบบที่ยังไม่มีเคสไหน Retest เสร็จเลย) ถ้ายังไม่เคยมีเคสไหนผ่านการ Retest จริง ให้แจ้งผู้ใช้ว่าต้องไปรัน `qa-retest` (10) ให้มีผลอย่างน้อย 1 เคสก่อน
3. **กำหนด Scope**: อ่าน Test Case Workbook ชีต "Test Case" **สดจากไฟล์จริงเสมอ** ด้วย `python3 scripts/qa_workbook.py read-cases --path "<path>"` แล้วกรองเฉพาะ Test Case ที่คอลัมน์ **"Issue link" ไม่ว่างเปล่า** (มี Ticket จริงให้จัดการ — เอาทั้งเคสที่ Status ปัจจุบันเป็น Pass และยัง Fail ตามที่ผู้ใช้ยืนยันไว้)

   **หมายเหตุสำคัญ (แก้จากการออกแบบรอบแรก)**: ตอนแรกเคยคิดจะใช้คอลัมน์ "Execution Date มีค่า" เป็นตัวกรองเพิ่มเพื่อแยกเคสที่ "ผ่านการ Retest จาก Skill 10 มาแล้ว" ออกจากเคสที่ "ยังไม่เคย Retest เลย" แต่พบว่าใช้ไม่ได้จริง เพราะ Execution Date ถูกใส่ค่าตั้งแต่ตอน `qa-automation-script` (06a) รันครั้งแรกอยู่แล้ว (ก่อน Skill 09 จะเปิด Ticket ด้วยซ้ำ) ทำให้ทุกเคสที่มี Issue link มี Execution Date อยู่แล้วเสมอไม่ว่าจะเคย Retest จริงหรือไม่ — **จึงตัดเงื่อนไขนี้ออก เหลือแค่ "มี Issue link" เพียงเงื่อนไขเดียว แล้วอาศัยขั้นตอนที่ 3 (Preview + ให้ผู้ใช้ Recheck) เป็นตัวกรองแทน**: ตอนเตรียม cases-json ให้แสดง Actual Result ปัจจุบันของแต่ละเคสในรายงาน Preview ให้ชัดเจน เพื่อให้ผู้ใช้สังเกตได้เองว่าเคสไหนหน้าตาเหมือนผลเดิมตั้งแต่ก่อนเปิด Ticket (ยังไม่เคย Retest จริง) แล้วเลือก Action "(2) เลือกเฉพาะบางเคส" เพื่อข้ามเคสนั้นออกไปก่อน — นี่คือเหตุผลที่ผู้ใช้อยากมีจุด Recheck อยู่แล้วตั้งแต่แรก จุดนี้เป็นตัวอย่างที่ตรงเป๊ะว่าทำไมถึงสำคัญ
4. **กรอง Ticket ที่ปิดไปแล้วออกจาก Scope**: เนื่องจาก Skill นี้เรียกซ้ำได้เรื่อยๆ (loop กับ Skill 10) ต้องเช็คก่อนว่า Ticket ไหนถูกปิดไปแล้วจากรอบก่อนหน้า เพื่อไม่ให้โผล่มาให้ Recheck ซ้ำ — ทำในขั้นตอนที่ 2 (เช็คร่วมกับการดึง Status จริงจาก Redmine เลย ไม่ต้องแยกเป็นขั้นตอนเดี่ยว)

   **ถ้ากรองแล้วว่างเปล่า**: แจ้งผู้ใช้ว่าไม่มีอะไรต้องทำในรอบนี้ (ยังไม่มีเคสไหน Retest เสร็จ) แล้วจบ Skill ทันที

## ขั้นตอนที่ 2 — เช็คว่า Ticket ไหนปิดไปแล้วบ้าง (กรองออกจาก Scope)

1. **ถามผู้ใช้ตรงๆ ทุกครั้งที่รัน Skill นี้ (ห้ามจำ/เก็บค่าจากรอบก่อนไว้ใช้ซ้ำ ห้ามเขียนค่าเหล่านี้ลงไฟล์ใดๆ ในโปรเจคเด็ดขาด)** — กฎเดียวกับ Skill 09/10 ทุกประการ:
   - Redmine URL
   - Redmine API Key
   - **Redmine Status value ไหนบ้างที่แปลว่า "ปิดแล้ว"** (เช่น `Closed`, `Rejected` — ต้องถามเพราะแต่ละ instance ตั้งชื่อไม่เหมือนกัน เหตุผลเดียวกับที่ต้องถามชื่อ Status ที่แปลว่า "แก้เสร็จแล้ว" ใน Skill 10)
2. ตั้ง `REDMINE_URL`/`REDMINE_API_KEY` เป็น environment variable แล้วรัน (ใช้สคริปต์ตัวเดียวกับ Skill 10 — เป็น stub ที่ชี้ไปที่ `_shared/check_redmine_status.py` ตัวเดียวกัน):
   ```
   python3 scripts/check_redmine_status.py check --tc-issue-map "<tc-issue-map จาก Scope ขั้นตอนที่ 1>.json" --resolved-statuses "<ชื่อ Status ที่แปลว่าปิดแล้ว>" --out "<closed-check-result>.json"
   ```
3. ผลลัพธ์คีย์ `ready` = Ticket ที่**ปิดไปแล้ว** (ตัดออกจาก Scope ไม่ต้องทำอะไรอีก) คีย์ `waiting` = Ticket ที่**ยังเปิดอยู่**จริง (คือ Scope จริงที่จะเอาไปทำขั้นตอนที่ 3 ต่อ) คีย์ `failed` = ดึงข้อมูลไม่สำเร็จ (แจ้ง error ตามจริง ถ้ามี 403 จาก proxy ให้สงสัยเรื่อง network egress ก่อนเหมือน Skill อื่น)
4. **ถ้า `waiting` ว่างเปล่าทั้งหมด**: แจ้งผู้ใช้ว่า Ticket ทุกใบที่ Retest แล้วถูกปิดไปหมดแล้วในรอบก่อนหน้า ไม่มีอะไรต้องทำเพิ่ม จบ Skill ทันที

## ขั้นตอนที่ 3 — เตรียมข้อมูลและแสดง Preview ให้ผู้ใช้ Recheck ก่อนเสมอ

1. สำหรับทุก Test Case ใน `waiting` จากขั้นตอนที่ 2 อ่านผลการ Retest ล่าสุดจาก Workbook (Status ปัจจุบัน = Pass หรือ Fail, Actual Result, path Screenshot จากคอลัมน์ Test Photo หรือโฟลเดอร์ `screenshots/<Browser>/<TC-ID>.png`) เตรียมเป็น cases-json ตาม schema ใน docstring ของ `scripts/close_redmine_issues.py`:
   - `retest_result`: `"Pass"` หรือ `"Fail"` ตาม Status ปัจจุบันใน Workbook (ต้องเป็นค่าที่รวมผลข้าม Browser แล้วตามกฎของ `qa-automation-script` (06a) ขั้นตอนที่ 5 ข้อ 2 อยู่แล้ว เพราะ Workbook เก็บแค่ Status เดียวต่อเคส — ไม่ต้องคำนวณซ้ำที่นี่)
   - `actual_result`: ใส่ค่า Actual Result เต็มๆ จาก Workbook ตรงๆ **สำคัญมาก** เพราะเป็นสิ่งเดียวที่ผู้ใช้ใช้ตัดสินตอน Recheck ว่าเคสนี้ผ่านการ Retest จริงหรือยัง (ดูหมายเหตุขั้นตอนที่ 1 ข้อ 3 — Skill นี้ไม่มีทางแยกอัตโนมัติได้ว่า Execution Date มาจาก Retest จริงหรือจากการทดสอบครั้งแรก จึงต้องพึ่งคนดู Actual Result เอง)
   - `reason_if_fail`: **เฉพาะเคส Fail** ให้ AI สรุปสาเหตุที่ยังไม่ผ่านจาก Actual Result ล่าสุดเอง (ไม่ต้องถามผู้ใช้ทีละเคส) เขียนกระชับ อ่านแล้วเข้าใจว่ายังพังตรงไหน — ค่านี้จะถูกใช้ทั้งใน Comment (ขั้นตอนที่ 4) และอีเมลแจ้ง Dev ซ้ำ (ขั้นตอนที่ 5) จุดเดียวกัน ไม่ต้องเขียนสรุปซ้ำสองที่
2. รัน `list-preview` ก่อนเสมอ (ไม่ต้องมี credential เพราะไม่ยิง API จริง):
   ```
   python3 scripts/close_redmine_issues.py list-preview --cases-json "<path>.json"
   ```
3. **เมนู `[?]` ท้ายรายงานไม่ใช่ prompt ที่รอ input จริงจาก Terminal** (หลักการเดียวกับ Skill 09/10 ทุกประการ) — ต้องทำตามนี้เสมอ:
   1. **Paste รายงานที่ได้ให้ผู้ใช้ดูในแชทตรงๆ**
   2. ใช้เครื่องมือถามคำถามจริงถามผู้ใช้ 3 ตัวเลือกเดียวกับในรายงาน (ยืนยันทั้งหมด / เลือกเฉพาะบางเคส / Cancel) — **นี่คือจุด "Recheck" ที่ผู้ใช้ต้องการให้มีก่อนปิด Ticket จริง ห้ามข้ามขั้นตอนนี้ไม่ว่ากรณีใด**
   3. **(1) ยืนยันทั้งหมด**: ไปขั้นตอนที่ 4 โดยไม่ใส่ `--only`
   4. **(2) เลือกเฉพาะบางเคส**: ถามผู้ใช้ต่อว่าจะเอาเคสไหนบ้าง (เลือกจากรายชื่อจริงในรายงาน กันพิมพ์ผิด) แปลงเป็น TC-ID ส่งเป็น `--only "TC-xxx,TC-yyy"` ในขั้นตอนที่ 4
   5. **(3) Cancel**: จบ Skill ทันที ไม่ต้องขอ Redmine URL/API Key เพิ่ม (เพิ่งใช้ไปแล้วในขั้นตอนที่ 2 แต่ไม่ต้องเอาไปทำอะไรต่อ) ไม่ต้องอัปเดต Manifest

## ขั้นตอนที่ 4 — คอมเมนต์ + ปิด Ticket จริง

1. **ถามผู้ใช้เรื่อง Text formatting ของ Redmine instance นี้ (Textile หรือ Markdown)** — เหมือนที่ถามใน Skill 09 (ถ้าเพิ่งถามไปแล้วในการรัน Skill 09/10a ครั้งก่อนหน้าของ instance เดียวกันในบทสนทนานี้ ใช้คำตอบเดิมได้โดยไม่ต้องถามซ้ำ เพราะเป็นค่าที่ผูกกับ instance ไม่ใช่ credential ที่ต้องถามใหม่ทุกครั้ง)
2. **ถามผู้ใช้ว่าจะใช้ชื่อ Status อะไรตอนปิด Ticket** (เช่น "Closed") — ถ้าไม่แน่ใจว่าตัวสะกดตรงกับ Redmine instance นี้ไหม แนะนำให้รันช่วยดูก่อน:
   ```
   python3 scripts/close_redmine_issues.py list-statuses
   ```
   (ต้องมี `REDMINE_URL`/`REDMINE_API_KEY` เป็น environment variable อยู่แล้วจากขั้นตอนที่ 2)
3. รันคำสั่งหลัก:
   ```
   python3 scripts/close_redmine_issues.py apply --cases-json "<path>.json" --close-status "<ชื่อ Status>" --syntax markdown|textile [--only "TC-xxx,TC-yyy"] --out "<result>.json"
   ```
   สคริปต์จะ: อัปโหลดไฟล์ Screenshot ขึ้น Redmine จริง (ถ้าไฟล์มีอยู่จริง — ถ้าไม่เจอไฟล์จะยังคอมเมนต์ต่อได้ไม่ fail ทั้งเคส แค่ไม่มีรูปแนบ) แล้วคอมเมนต์กลับ Ticket ตาม Format ที่ยืนยันแล้ว (ดู `mockup-retest-closure-format.md`) — **เคส Pass จะตั้ง Status เป็นชื่อที่ระบุด้วย (ปิด Ticket) เคส Fail จะคอมเมนต์อย่างเดียวไม่แตะ Status เลย**
4. อ่านผลลัพธ์ (`closed`/`commented`/`failed`) แล้วรายงานผู้ใช้ทราบครบทุกกรณี **ไม่ใช่แค่กรณีที่สำเร็จ**:
   - ถ้ามี `warning` ในบางรายการ (เช่น หาไฟล์ Screenshot ไม่เจอ) ให้แจ้งผู้ใช้ด้วยว่าคอมเมนต์สำเร็จแต่ไม่มีรูปแนบ ไม่ใช่ error ร้ายแรง
   - ถ้ามี `failed` ให้แจ้ง error จริง — ถ้ามี "403"/"Forbidden" จาก proxy ให้สงสัยเรื่อง network egress allowlist ก่อนเหมือน Skill อื่นในสาย

## ขั้นตอนที่ 5 — แจ้ง Dev ซ้ำทางอีเมล (เฉพาะเคสที่ยัง Fail)

ทำเฉพาะตอนผลลัพธ์จากขั้นตอนที่ 4 มีคีย์ `commented` อย่างน้อย 1 รายการ (ถ้าทุกเคสที่ทำรอบนี้เป็น Pass ล้วน ข้ามขั้นตอนนี้ไปเลย)

**หมายเหตุ environment เดียวกับ Skill 09**: SMTP อาจต่อไม่ได้เลยถ้ารันใน environment ที่จำกัด raw TCP egress — ถ้าเจอ timeout ให้สงสัยเรื่อง network ก่อนไม่ใช่ credential ผิด

1. ถามผู้ใช้ผ่านเครื่องมือถามคำถามจริง (ไม่ใช่รอ input จาก Terminal): **ต้องการส่งอีเมลแจ้ง Dev ซ้ำไหม (y/n)** — ถ้าไม่ส่ง ข้ามไปขั้นตอนที่ 6 ได้เลย
2. ถ้าต้องการส่ง: ถามผู้ใช้ **ใหม่ทุกครั้ง** Developer Email Address + SMTP Host/Port/Username/Password ตั้งเป็น environment variable ตามกฎเดียวกับ Skill 09
3. สร้างเนื้อหาอีเมล (Format **"RETEST FAILED REPORT"** — คนละ Format กับตอนเปิดบั๊กครั้งแรกใน Skill 09 ดู `mockup-retest-closure-format.md`):
   ```
   python3 scripts/send_email_notification.py build-retest-failed-body --cases-json "<path เดียวกับขั้นตอนที่ 3>.json" --result-json "<result จากขั้นตอนที่ 4>.json" --run-date "<วันที่ Retest>" --environment "<Environment>" --out "<body>.txt"
   python3 scripts/send_email_notification.py send --to "<developer email>" --subject "[QA] Retest ยังไม่ผ่าน — <N> Ticket(s)" --body-file "<body>.txt"
   ```
4. รายงานผลตามจริงเสมอ (สำเร็จ/ไม่สำเร็จ พร้อมเหตุผล — ถ้า timeout ให้อธิบายว่าน่าจะเป็นข้อจำกัดของ environment)

## ขั้นตอนที่ 6 — อัปเดต Manifest และรายงานสรุป

1. อัปเดต `_pipeline-manifest.md`: ตั้งค่า Stage `10a qa-retest-closure` เป็น:
   - `Complete (รอบนี้)` พร้อมระบุจำนวนที่ปิดสำเร็จ (`closed`) และจำนวนที่คอมเมนต์แจ้ง Dev ซ้ำ (`commented`) — **ใช้คำว่า "รอบนี้" เสมอเพราะ Skill นี้ไม่มีสถานะจบสมบูรณ์ตลอดกาล** ถ้ามีเคส Fail ที่ยังรอ Dev แก้ต่อ วงจร Skill 10 ↔ 10a จะยังวนต่อได้อีก
   - ถ้ามี `failed` ค้างให้ระบุจำนวนไว้ด้วยเพื่อให้ผู้ใช้ตามแก้เอง
2. แจ้งผู้ใช้สรุปให้ครบ: จำนวนที่**ปิด Ticket สำเร็จ** (บั๊กแก้จริงแล้ว จบ), จำนวนที่**คอมเมนต์แจ้ง Dev ซ้ำ**พร้อมส่งอีเมลไปแล้ว (รอ Dev แก้รอบต่อไป), จำนวนที่**ทำไม่สำเร็จ** — ถ้ามีเคสยัง Fail ให้เตือนว่าเมื่อ Dev แจ้งแก้ใหม่แล้ว ต้องกลับไปเรียก `qa-retest` (10) ใหม่เพื่อวนขั้นตอนต่อ (ไม่ใช่เรียก Skill นี้ซ้ำตรงๆ เพราะ Skill นี้ไม่ได้ Retest เอง)

## ข้อควรระวัง

- **ห้ามเก็บ/cache Redmine URL, API Key, หรือรายการ Status ที่นับว่า "ปิดแล้ว" ไว้ข้ามรอบการรัน** ต้องถามผู้ใช้ใหม่ทุกครั้งเหมือน Skill 09/10 ทุกประการ
- **ต้องให้ผู้ใช้ Recheck ผ่านเครื่องมือถามคำถามจริงก่อนคอมเมนต์/ปิด Ticket จริงเสมอ** (ดูขั้นตอนที่ 3) — ห้ามข้ามจุดนี้ไม่ว่าในกรณีใด เพราะเป็นเหตุผลหลักที่ผู้ใช้แยก Skill นี้ออกมาจาก Skill 10
- **Skill นี้ไม่ Retest เอง** — ถ้า Workbook ยังไม่มีผล Retest ล่าสุด (Execution Date ว่าง) ให้แจ้งผู้ใช้ไปรัน `qa-retest` (10) ก่อนเสมอ ไม่ใช่พยายามเดา/รันเองจากที่นี่
- **แนบไฟล์ Screenshot จริงเข้า Redmine เป็นของใหม่ที่เขียนเพิ่มสำหรับ Skill นี้โดยเฉพาะ** ต่างจาก `create_redmine_issues.py` ของ Skill 09 ที่ใส่แค่ path เป็นข้อความ (เคยเข้าใจผิดระหว่างออกแบบว่า Skill 09 แนบไฟล์จริงอยู่แล้ว ต้องแก้ความเข้าใจให้ตรงกันไว้ตรงนี้) — **ทดสอบกับ Redmine จริง (Planio) สำเร็จแล้วเมื่อ 2026-09-16** (ปิด Ticket #8 จริง พร้อมแนบ Screenshot สำเร็จ ไม่มี warning ไฟล์หาไม่เจอ) ยืนยันว่าโค้ด upload attachment ใช้งานได้จริงตาม Redmine REST API ที่อ้างอิงไว้
- **เคส Fail ห้ามแตะ Status ของ Ticket เด็ดขาด** (ดูขั้นตอนที่ 4) — คอมเมนต์อย่างเดียว ปล่อย Ticket เปิดค้างไว้ให้ Dev แก้ต่อ
- ไฟล์ Screenshot ที่หาไม่เจอ**ไม่ทำให้ทั้งเคส fail** — สคริปต์จะคอมเมนต์ต่อโดยไม่มีรูปแนบและแจ้งเป็น `warning` แทน ต้องแจ้งผู้ใช้เห็นด้วยว่าเคสไหนไม่มีรูปแนบ
- ถ้าเจอ error แบบ proxy/network block (403 Forbidden จากตัวกลาง ไม่ใช่จาก Redmine) ให้บอกผู้ใช้ตรงๆ ว่าน่าจะเป็นเพราะ network egress allowlist ของ environment ไม่ใช่ปัญหาที่ credential หรือ Redmine เอง (เหตุผลเดียวกับ Skill อื่นในสาย)
- **รูปแบบ Comment (Format ที่ 1 และ 2) และอีเมล (Format ที่ 3) ยืนยันแล้ว** (ดู `mockup-retest-closure-format.md`) ห้ามพิมพ์เนื้อหาเองมือเปล่าหรือเปลี่ยน field/ลำดับเอง — ถ้าจะเพิ่ม/แก้ field ต้องแก้ที่สคริปต์ให้ตรงกันด้วย
