# test-data-generator

Skill นี้เป็น**ขั้นตอนที่ 6 ที่บังคับ** ของ QA Pipeline หน้าที่คือแปลงคำอธิบาย Test Data ที่เขียนไว้แบบสรุปในแต่ละ Test Case (เช่น "เบอร์โทรผิดรูปแบบ", "OTP ถูกต้อง") ให้กลายเป็นค่าข้อมูลจำลองที่ใช้งานได้จริงตอนทดสอบ ผลลัพธ์จะถูกใช้ต่อโดย `qa-automation-script` (06a) ตอนเขียน Test Script จริง

**สำคัญ**: คำสั่งในไฟล์นี้เขียนขึ้นให้ใช้ได้กับทั้ง Claude และ Gemini 3.6 — ห้ามอ้างอิงชื่อ tool เฉพาะของแพลตฟอร์มใดแพลตฟอร์มหนึ่ง Skill นี้ต้องใช้ environment ที่รันสคริปต์ Python ได้เพื่ออ่าน Workbook (.xlsx) เหมือน Skill ก่อนหน้า (แต่ไม่แก้ไข Workbook — ดูข้อควรระวัง)

## ขั้นตอนที่ 1 — ระบุ Feature และตรวจสอบขั้นตอนก่อนหน้า

1. หาโฟลเดอร์รากของโปรเจค (Project Root) และโฟลเดอร์ Feature เหมือน Skill อื่นๆ ในสาย
2. อ่านไฟล์ `_pipeline-manifest.md` ของ Feature นั้น
3. **เช็ค Gate**: Skill นี้ต้องรันต่อจาก `risk-analysis` (Skill 05) เสมอ — ตรวจสอบสถานะ Stage `05 risk-analysis` (ถ้าไม่มี manifest เลยก็ถือว่ายังไม่เสร็จเช่นกัน — ต้องถามผู้ใช้เสมอ ห้ามสรุปเอาเอง):
   - **ถ้า `Complete`**: ไปต่อขั้นตอนที่ 2
   - **ถ้ายังไม่ `Complete`**: หยุดและถามผู้ใช้ว่า (a) ต้องการไปรัน `risk-analysis` ให้เสร็จก่อนไหม (แนะนำ) หรือ (b) ต้องการใช้ Skill นี้แบบ standalone — ถ้าเลือก (b) ให้ขอ Test Case Workbook ที่มีอยู่แล้วมาจากผู้ใช้โดยตรง

## ขั้นตอนที่ 2 — อ่าน Test Case ทั้งหมด

อ่าน Test Case Workbook **ฉบับล่าสุดจริงๆ** ด้วยคำสั่ง (กรณี Excel):
```
python3 scripts/qa_workbook.py read-cases --path "<path Workbook>"
```
(**หมายเหตุโครงสร้าง**: `scripts/qa_workbook.py` ของ Skill นี้เป็น stub ที่โหลดฉบับจริงจาก `qa-pipeline-skills/_shared/qa_workbook.py` มาใช้ร่วมกับอีก 4 Skill ในสาย ถ้าต้องแก้ logic ให้แก้ที่ `_shared/` ที่เดียว ห้ามแก้ stub นี้)

ดึงข้อมูลของทุก Test Case โดยเฉพาะคอลัมน์ `Test Case ID`, `Test Scenario`, `Pre-condition`, `Test Step`, `Test Data`, `Expected Result` — ใช้ทั้งหมดนี้ประกอบกันเพื่อเข้าใจบริบทว่าค่าข้อมูลที่ต้อง mock ควรมีลักษณะอย่างไร (ไม่ใช่อ่านแค่คอลัมน์ Test Data เพียงอย่างเดียวโดยไม่ดูบริบท)

## ขั้นตอนที่ 3 — แปลงเป็น Mock Data จริง

สำหรับ**แต่ละ Test Case** ที่มีคอลัมน์ `Test Data` ระบุไว้ (ไม่ว่าง) ให้แปลงเป็นค่าจริงที่ใช้ทดสอบได้ทันที โดยยึดหลักดังนี้:

- **ห้ามใช้ข้อมูลจริงเด็ดขาด**: ห้ามใช้เบอร์โทร/อีเมล/ชื่อ/เลขบัตรที่อาจเป็นของจริงหรือชนกับของจริงโดยบังเอิญ ให้ใช้รูปแบบที่ยอมรับกันทั่วไปว่าเป็นข้อมูลทดสอบ (เช่น โดเมนอีเมล `@example.com`, เบอร์โทรที่ใช้ prefix สำหรับทดสอบถ้ามีการระบุไว้ใน Env & Config, ชื่อสมมติที่ระบุชัดว่าเป็นข้อมูลทดสอบ)
- **ต้องสอดคล้องกับ Business Rule**: ถ้า Business Rule กำหนดรูปแบบไว้ (เช่น เบอร์โทรต้องขึ้นต้นด้วย 0 และยาว 10 หลัก) ค่า mock สำหรับ Test Case เชิงบวก (positive) ต้องผ่านกฎนั้นจริง ส่วน Test Case เชิงลบ/edge case ต้องจงใจสร้างค่าที่ละเมิดกฎนั้นตามที่ Test Scenario ต้องการทดสอบ
- **แยกแยะค่าที่ mock ล่วงหน้าได้ กับค่าที่ระบบต้อง generate เองตอนรัน**: บาง Test Data (เช่น OTP ที่ระบบสุ่มส่งจริง, Token, ID ที่ระบบสร้างอัตโนมัติ) **ไม่สามารถกำหนดค่าคงที่ล่วงหน้าได้** เพราะเป็นค่าที่ระบบภายใต้การทดสอบสร้างขึ้นเองแบบสุ่ม/แบบไดนามิก สำหรับกรณีนี้ **ห้ามสร้างค่าปลอมขึ้นมาแทน** ให้ระบุไว้ชัดเจนว่าเป็น "ค่า Dynamic — ต้องอ่านจากระบบจริงตอนรัน Test Script" พร้อมอธิบายว่าจะดึงค่านั้นมาจากไหน (เช่น อ่านจาก log, อ่านจาก mailbox ทดสอบ, อ่านจาก response ของ API sandbox) เพื่อให้ `qa-automation-script` (06a) รู้ว่าต้องเขียนโค้ดดึงค่านี้แบบไดนามิกแทนการ hardcode
- **ใช้ค่าเดียวกันซ้ำได้ถ้าเหมาะสม**: ถ้าหลาย Test Case ต้องการ pre-condition แบบเดียวกัน (เช่น "บัญชีทดสอบที่ผูกเบอร์โทรไว้แล้ว") ให้ตั้งชุดข้อมูลกลางไว้ใช้ร่วมกัน แล้วอ้างอิงชื่อชุดนั้นในแต่ละ Test Case แทนการสร้างค่าใหม่ซ้ำๆ

## ขั้นตอนที่ 4 — เขียนไฟล์ผลลัพธ์

สร้างไฟล์ตามโครงสร้างนี้:

```
# Test Data — <ชื่อ Feature>

Created: <วันที่>
อ้างอิงจาก: 03-test-case-workbook.xlsx (คอลัมน์ Test Data) เวอร์ชัน <Version ของ Document Control ตอนอ่าน>

## ชุดข้อมูลกลาง (ใช้ร่วมกันหลาย Test Case)
### <ชื่อชุดข้อมูล>
<รายละเอียดค่า>
ใช้โดย: <รายชื่อ Test Case ID ที่ใช้ชุดนี้>

## Mock Data รายเคส
### <Test Case ID>: <Test Scenario>
<ค่าข้อมูลจำลองที่ใช้ พร้อมระบุชัดว่าค่าไหนคงที่ ค่าไหน Dynamic (ถ้ามี)>

### <Test Case ID ถัดไป>: ...
...

## หมายเหตุ
<ถ้ามี Test Case ที่ไม่มีข้อมูล Test Data ให้ mock (เช่น Test Case ที่ไม่ต้องใช้ input ข้อมูลอะไรเลย) ให้ระบุไว้ว่าข้ามเพราะเหตุผลอะไร>
```

## ขั้นตอนที่ 5 — บันทึกไฟล์และอัปเดต Manifest

1. บันทึกไฟล์ผลลัพธ์ที่ `<โฟลเดอร์ Feature>/06-test-data.md`
2. อัปเดตไฟล์ `_pipeline-manifest.md`: ตั้งค่า Stage `06 test-data-generator` เป็น `Complete`, ใส่ path ของไฟล์ output, ใส่วันที่เสร็จ
3. แจ้งผู้ใช้ว่าเสร็จแล้ว สรุปจำนวน Test Case ที่มี Mock Data พร้อมใช้ และจำนวนที่เป็นค่า Dynamic (ถ้ามี) แล้วแนะนำให้ไปต่อ `qa-automation-script` (Skill 06a)

## ข้อควรระวัง

- **ห้ามแก้ไข Test Case Workbook (.xlsx) ในขั้นตอนนี้เด็ดขาด** — Skill นี้อ่านอย่างเดียว ผลลัพธ์ทั้งหมดต้องอยู่ในไฟล์ `06-test-data.md` แยกต่างหากเท่านั้น (ต่างจาก `coverage-review`/`risk-analysis` ที่มีสิทธิ์แก้ Workbook)
- ห้ามใช้ข้อมูลจริงไม่ว่ากรณีใดก็ตาม แม้ผู้ใช้จะเสนอข้อมูลจริงมาให้ใช้ก็ตาม ให้อธิบายเหตุผลด้านความปลอดภัย/ความเป็นส่วนตัวแล้วเสนอใช้ข้อมูลจำลองแทน
- ถ้า manifest ระบุว่า `risk-analysis` สถานะ `In Progress` ห้ามอ่าน Workbook มาใช้ทันทีเหมือนเป็นข้อมูลสมบูรณ์ ให้เตือนผู้ใช้ก่อนเหมือน Skill ก่อนหน้า
